## Expected Behavior

用户在「我的设备」里删除某台控制器后，该设备应立即**完全无法**再向本机下发任何指令。
解除配对 = 授权撤销。撤销必须是**凭据级**的（旧密钥/旧凭据失效），不能只是「列表里少一行」。

## Actual Behavior

撤销只做三件事：① 从 `rc_paired` 列表移除；② 把 id 写进 `rc_revoked`；③ 停掉该设备在途的指令组/通话。
而**消息密钥仍然只是「本机配对码」**，撤销不改变配对码 ⇒ 被撤销方手里那把「钥匙」完好无损。

准入判据依赖 `msg.from`：

```dart
// endpoint_service.dart:3709-3713
if (senderRevoked) return RcAdmission.rejectRevoked;
if (type == RcCmd.pairRequest) return RcAdmission.allowPairing;
if (senderId.isEmpty) return RcAdmission.allowUnidentified;   // ← 空 from 放行
if (senderPaired) return RcAdmission.allowPaired;
return RcAdmission.rejectUnpaired;
```

`from` 是发送方**自报**的字段（`protocol.dart:46` 注释即写「不参与鉴权」）。
构造一条**不带 `from` 或 `from` 为空串**的命令，即可命中 `allowUnidentified`，
绕过全部撤销与配对判定。代码注释自己承认了这个缺口（`:3687-3695`「已知缺口」）。

## Trigger Conditions

1. 攻击者曾与该端点配对过（或被用户在列表里删除过）⇒ 持有端点的 8 位配对码；
2. 攻击者自行实现 MQTT 客户端，或把官方客户端的 `from` 改成 `''`；
3. 向 `sonicshield/v1/{端点ID}/cmd` 发布 `from: ""` 的命令；
4. 端点已启用远程遥控并在线。

## Forward Call Chain

```
MQTT publish
  → client.updates.listen (:673)
  → _handleRaw(topic, wire) (:825)
  → 解密成功（密钥未变）
  → reserveInboundId (:890，首次必过)
  → decideRcAdmission(senderId: msg.from='') → allowUnidentified (:3711)
  → 限流（30/60s，足够）
  → _peerOf(msg) (:1108，构造占位对端)
  → _dispatch (:1121) → 任意 handler
```

## Reverse Call Chain

`removePaired`（`remote_store.dart:407`）只改 `rc_paired` / `rc_revoked` / `rc_selected`；
`onPeerRevoked`（`endpoint_service.dart:516`）只退订 evt 主题 + 停在途作业。
**没有任何一处**改动 `_ownCode` 或使旧密文失效。

## Data Flow / State Transition

```
paired[A] --removePaired--> paired \ {A};  revoked += {A}
_ownCode 不变  ⇒  key(A→B) 不变

A 发 from=""  ⇒  admission = allowUnidentified  ⇒  执行
A 发 from=A   ⇒  admission = rejectRevoked      ⇒  拒绝（仅"诚实"客户端被拦）
```

## Reproduction Steps（仅设计，未执行）

1. 设备 B 与控制器 A 正常配对，B 的「我的设备」中出现 A；
2. 在 B 上删除 A（触发 `removePaired` + `onPeerRevoked`）；
3. 用 A 侧代码把 `RcEndpointService.sendTo` 里的 `from: store.deviceId` 改为 `from: ''`（一行改动），
   或直接用 mosquitto_pub + 预先抓取的密文重放（90s 内）；
4. A 发 `sound.play` / `task.upsert` / `call.invite` → B 照常执行并回执
   （回执因 `targetPeerId=''` 退化为广播）。

## Root Cause

**「凭据」与「授权」被设计成同一个东西：能解密 = 已授权。**
而解密能力来自**共享的、不可按设备轮换的**配对码，因此「撤销某个设备」在密码学上无法表达。
`from` 是唯一的身份声明，却没有完整性保护（虽在密文内，但任何持有配对码者都能写任意值）。

## Alternative Hypotheses

| 假设 | 评估 |
|---|---|
| 「撤销后必须轮换配对码才生效」是有意设计 | 部分成立（`rotatePairingCode` 注释与 UI 二次确认都这么说）。但若如此，缺陷应改写为「删除设备的 UI 语义与真实效果不一致」，**仍至少 P1**；按合规红线仍判 P0 —— 用户点「删除」时不会预期「它还能控制我」 |
| `from` 为空仅用于 `tool/rc_probe.dart` 探针，是有意兼容 | 成立，但**不应以生产鉴权缺口为代价** |
| broker 的 topic ACL 可补偿 | 默认公共 broker **无 ACL**（`remote_store.dart:173`），仅自建 broker 可能 |

## Business Impact

「解除配对」这一**唯一**的授权回收手段失效。
家庭守护场景下（老人机被子女控制），一旦控制端设备被转手/丢失/恶意安装，
端点无法单方面切断控制，除非重置配对码 —— 而那会让**所有**控制器一起失联。

**这是 `docs/08-合规与安全使用白皮书.md` §2「未经授权控制他人设备」红线的直接命中项。**

## Recommended Fix

1. **短期（不改密钥模型）**：删除 `allowUnidentified` 分支 —— `senderId` 为空一律 `rejectUnidentified`
   （`pair.request` 已单独在最前放行，不受影响）；`tool/rc_probe.dart` 改为填 `from`。
   同时把「删除设备」的 UI 文案改为「删除并吊销（需重置配对码）」或直接引导重置。
2. **根治（密钥模型级）**：配对时由**端点生成每控制端独立的 32 字节密钥**（而非复用控制端全局配对码），
   随 `pair.request` 的 ack 下发；`removePaired` 删除该密钥即真正吊销；
   `from` 不再参与鉴权，身份由「用哪把密钥解开」决定（每条命令按候选密钥试解，命中即身份）。
3. 撤销表增加「生效时间」并在 UI 展示，避免用户误以为删除即吊销。

## Regression Risks

- 去掉 `allowUnidentified` 会让 `tool/rc_probe.dart`、`tool/rc_e2e_controller.dart` 的探针链路失败
  （它们不填 `from`）—— 需同步改工具，否则端到端验证手段失效。
- 旧版控制端（若不填 `from`）会全部被拒；`sendTo` 自 v1.3 起统一填充，风险低但需确认。
- 根治方案会改变「按接收方身份派生 + 双方互扫」这一 **HANDOVER §4.6 的既定决策**，
  属架构级变更，必须与 `docs/14`、`docs/25` 同步，并需老板裁决。
