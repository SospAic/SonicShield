## 2. 失败用例 1：VC05「toMap 键集合精确」

### 判定：**测试锁未同步**，不是产品缺陷（`CONFIRMED`）

| 项 | 结论 |
|---|---|
| 产品侧 | `VibrateCaps.toMap/fromMap` **闭合正确**（8 键一一对应） |
| 测试侧 | 门禁跑的是**旧测试**（断言 6 键），模型已加 2 键 |
| 现状 | 测试已于 **17:01:34** 补齐，**但此后没有复跑** ⇒ R93 无绿色证据 |

### 决定性证据

1. `/tmp/gates_功能层.log:681-704` 完整失败体：
   ```
   Expected: { 6 键 }        ← 旧测试
   Actual:   { 8 键 }        ← 新模型（多 ringerMode / dndActive）
   Which: has different length and has extra map key 'ringerMode'
   栈: test\cov_services_test.dart 94:7
   ```
2. 失败栈指向 `cov_services_test.dart:94:7`，而**当前**工作区该 `expect(` 在 **97 行**
   （94 行现在是 `ringerMode: 1,`）。差 **3 行** = `git diff` 新增的 3 行 ⇒ **门禁跑的是旧测试**。
3. 时间线（决定性）：
   ```
   15:50:46  模型改（vibrate_caps.dart +2 字段 +toMap 2 键）
   16:56:44  功能层跑完（VC05 判红）
   17:01:34  测试才补
   17:07:04  门禁结束（RC=1）
   ```
   ⇒ 补测试发生在门禁**运行期间但功能层之后**，该结论只对 16:56 前的工作区有效。
4. 静态推演：当前 `toMap()` 产出 8 键，测试期望也是 8 键同值 ⇒ **按当前工作区，VC05 必过**。

### 修复

重跑门禁取证（`GATES_RC=0` 落 `_pt/r94gate.log`）；建议 VC05 改为**双向差分**断言
（`actual.keys − expected.keys` 与反向均为空），失败信息可直接指出多/少了哪个键。

## 3. 失败用例 2：WT-02「parseUri 1 万次 ≤ 300ms」

### 判定：**墙钟抖动（min-of-1 测量缺陷）**，不是算法退化（`CONFIRMED`）

| 项 | 结论 |
|---|---|
| 是否回归 | **否**：同轮重跑 24/24 通过 + 9 份历史记录通过 + 被测实现自 2026-10-13 未变 |
| 是否算法问题 | **否**：O(n) 3 段字符串处理，无循环/无正则/无 I/O |
| 根因 | 该用例用**裸 `Stopwatch` 单次采样**（min-of-1），违背**文件头自己的约定**与 BUG-053/055 纪律 |
| 实测 | 321ms vs 预算 300ms（超 7%），发生在 CPU 负载 **67%** 的机器上 |

### 证据

1. `_pt/r93gate.log:31-36`：`Expected: ≤ 300` / `Actual: <321>`。
2. `/tmp/gates_压测层首次.log:172-180`：失败行 `performance_v2_test.dart:70:7`。
3. **`_pt/r93gate.log:52-53`：同轮重跑 `02:04 +24 All tests passed`** —— 同一代码、同一机器、几十分钟后通过。这是"测量问题而非回归"的最强单条证据。
4. 门禁**自己**在开跑前打印：`整机 CPU 负载 = 67% —— 压测层（墙钟预算）结果可能不可信`。
   且 `gates.sh:137` `LOAD_SUSPECT=60`、`:637` `perf_verdict` 在负载 ≥60% 时把压测失败定性为 **BLOCKED（RC=3）而非 FAIL**。
   ⇒ 按项目**自己的判据**，67% 负载下的 321ms **本就不足以判定回归**。
5. 历史单跑：`_pt/envchk_perf.txt:114-115` 显示 WT-01 与 WT-02 在同一秒内完成（**< 1s**）。
   另有 9 份历史记录（`aa3.log` / `bb3.log` / `cc3.log` / `f_step3.log` / `r72_perf.log` /
   `s3.log` / `step3.log` / `u3.log` / `x3.log`）WT-02 全部通过。
6. 被测实现未变：`lib/remote/protocol.dart:728-737` 最近改动 `7ca4590`（2026-10-13），R93 未碰。

### 根因（更深一层）

`test/performance_v2_test.dart:26-31` 文件头明确写着「已统一用 `benchMs`/`benchMsAsync`（预热 + 取最小值）」，
`test/perf_bench.dart:10-20` 解释了原因（单次采样测的是 JIT 冷启动 + GC + 页错误）。
`docs/12` §28.3（BUG-053）与 §29.6（BUG-055）已两次定案「任何用例都不得用 `runs: 1`」「余量要和噪声幅度比」，
§29.6 实测同一代码在负载下放大 **5.2×**。

**但 WT-01/02/03、GT-06 四条仍在用裸 Stopwatch** —— `docs/12 §28` 的修复**只覆盖了 GT-07**，没覆盖 WT 组。
统计：**16/24 压测用例**用裸 Stopwatch 单次采样 → QUA-02（P1）。

## 6. CI 现状（重要，但不是"偷偷弱化"）

- `ci.yml:11-19` **自述**：`2026-10-10：CI 收敛为只构建产物（不再跑 analyze/test/coverage/emulator —— 那部分由本地 scripts/gates.sh 门禁承担，省 Actions 计费）`。
- 实际步骤只有：`pub get` → 恢复 keystore → `flutter build apk --release` → `apksigner verify` → 上传；
  以及 iOS `build ios --no-codesign` → 打 IPA → 上传。**零 analyze、零 test、零覆盖率**。
- 这不是漏配，而是被 `test/gate_entrypoint_consistency_test.dart:113-136` 的 **GEC-06 机器锁强制**为当前形状
  （`!code.contains('analyze-test')`、`!code.contains('--min-covered=')`）—— **想把测试加回 CI，反而会判红**。

**判定**：不构成"规则 6：隐瞒式跳过测试"（有注释、有机器锁、有本地门禁承接）。
但客观后果必须登记：**PR/push 上没有任何自动化测试门**，唯一质量门是"人记得在本地跑 `gates.sh`"，
**而这道门当前是红的**（`GATES_RC=1`）→ QUA-04（P2）。
