## 1. 需求拆解 × 现有能力对照

| 需求原话 | 拆解 | 现有能力 | 缺口 |
|---|---|---|---|
| 「随机振动」 | 一次触发内**随机节奏 + 随机强度**的脉冲串 | `VibrateAction{patternMs}` 只有固定数组 | 缺随机化参数 |
| 「随机间隔」 | 两次振动之间间隔随机 | ✅ `RandomIntervalTrigger`（`[minGap,maxGap]` + 活动窗口 + 每日上限）**已实现**（FR-14） | **零新调度代码** |
| 「持续振动」 | 一段时长内连续振动 | 无 | 全新 |
| 「可设定随机振幅」 | 强度在 `[min,max]` 内随机 | ✅ 范式已有：`PlayAudioAction.volumeMin/Max`（FR-23）、DPRNG 物化期落地 | 需扩展到振动 |
| 「其他可调节项」 | 渐强/渐弱、占空比、锐度、波动周期 | ✅ `rampUpSec`（FR-30 先例） | 全新 |
| （隐含）计划可回溯 | "为什么这次是 0.72 振幅" | ✅ "计划即审计"（docs/04 §3） | 需把振动参数纳入 occurrence/exec_logs |

**结论**：本轮**不需要新触发器**——"随机间隔的随机振动" = `RandomIntervalTrigger` × `RandomVibrateAction`
两个正交能力的组合，与 docs/19 §1「两条正交机制」同一设计哲学。

## 2. 现状取证（代码 + 官方文档，均可复核）

### 2.1 代码现状

| 位置 | 现状 | 结论 |
|---|---|---|
| `action.dart:172` `VibrateAction` | 唯一字段 `patternMs`（默认 `[0,300,200,300]`） | 固定节奏，无随机 |
| `native_bridge.dart:117` | `vibrate(List<int> patternMs)` → `{pattern: [...]}` | 只有"节奏"一个入参 |
| `NativeBridgePlugin.kt:317` | `createWaveform(pattern, -1)` | **无振幅、无循环、无 attributes、无 cancel** |
| `ios/Runner/` | 仅 `AppDelegate.swift` / `SceneDelegate.swift` | **iOS 无任何震动桥** |
| `AndroidManifest.xml:35` | `<uses-permission android:name="android.permission.VIBRATE"/>` | ✅ 权限已就位 |
| `background_engine.dart:403` | `on Object { /* 无震动能力平台静默 */ }` | ⚠️ **静默降级**，与 FR-34 一致，但与本项目"承诺不得静默降级"的通则冲突 → §2.3 |
| `task_wire.dart:183` | `'vibrate'` 分支校验 `patternMs` 长度 ≤ `maxVibrateSteps=32` | ✅ 入站夹紧已有，**新 kind 必须补分支**（否则落进 `default` 不校验） |
| `app_database.dart:112,125` | `occurrences.volume/duration_ms`、`exec_logs.volume/duration_ms` | 无 amplitude 列 → §4.4 |

### 2.2 Android 官方文档已确认（`developer.android.com`）

1. **`Vibrator.hasAmplitudeControl()`**：设备不支持振幅控制时，**所有非零振幅一律被当作 100%**
   （退化成 on/off）。文档原文："If a vibrator does not have amplitude support, all amplitude
   values will map to off/on based on whether they are zero/non-zero."
   → **这是本设计最重要的降级事实**：同一份配置在不同设备上体感完全不同，且**不报错**。
2. **Android 16 / API 36 新增包络振动**：
   `VibrationEffect.BasicEnvelopeBuilder`
   `.setInitialSharpness(f).addControlPoint(intensity[0..1], sharpness[0..1], durationMs).build()`
   - 设备支持查询：`Vibrator.areEnvelopeEffectsSupported()`
   - 元数据：`vibrator.envelopeEffectInfo.minControlPointDurationMillis`（框架要求最低 20ms）
   - ⚠️ **效果必须以 `intensity == 0` 的控制点结尾**，否则抛 `IllegalStateException`
   - ⚠️ **系统不为包络效果提供 fallback**，不支持时会被**完全忽略** → 必须自建降级
   - ✅ **本机真机 `960f853` 就是 Android 16 / SDK 36** → 这条路是首选
3. **后台振动必须携带 vibration attributes**：文档明确"当应用处于**后台**时发起振动，
   **必须**提供振动属性（以 `AudioAttributes` 形式），因为**后台仅支持 attentional haptics**"，
   文档给出的后台示例正是 **`USAGE_ALARM`**（前台触摸反馈才是 `USAGE_ASSISTANCE_SONIFICATION`）。
   → ⚠️ **现有代码一个 attributes 都没传**（`NativeBridgePlugin.kt:325`）→ **疑似既有缺陷**，
   见 §2.3 BUG-069。
4. `Vibrator.cancel()` 是停止振动的方式（文档在 waveform 语境给出）。

### 2.3 两个由本轮取证衍生的缺陷候选

**BUG-069（候选，P0 必须定性）——后台振动未携带 vibration attributes。**
现状：`createWaveform(pattern, -1)` 无 attributes。而本项目**所有**振动都发生在
**前台服务/无界面后台**（`background_engine.runSingle`，由 AlarmManager 或守卫驱动）。
按官方文档，后台振动**必须**带 attributes。
→ **可能后果**：Android 较新版本上后台振动被系统忽略或降级（与"静默降级"同类），
表现为"任务到点了但没震"。**必须在真机上取证**（§13 P0）：
① 带 attributes 与不带，后台各调一次；② `adb shell dumpsys vibrator_manager` 看是否真的
产生了振动记录。**未取证前不得断言是缺陷**（本项目已有多次"推断结论被推翻"的先例）。

**FR-34 的口径要改。** 现 FR-34 验收写"无震动设备静默降级"。但本项目通则（BUG-048/056/059 血泪）是
**"承诺了就必须做到；做不到必须留痕并让用户知道，不得静默降级"**。
→ FR-34 改为：**"无震动能力/无振幅控制设备必须明示告知用户，并在审计中留痕"**（§11）。

## 3. 设计总览

```
                    ┌──────────────────────────────────────────┐
  触发层（复用）      │ RandomIntervalTrigger  [minGap,maxGap]    │  ← 零新代码
                    │ 随机间隔 = "什么时候震"                    │
                    └──────────────────┬───────────────────────┘
                                       ▼
                    ┌──────────────────────────────────────────┐
  模型层（新）        │ RandomVibrateAction     随机脉冲串         │  ← §4
                    │ ContinuousVibrateAction 持续 + 随机振幅     │
                    │ （VibrateAction 固定节奏保留，向后兼容）     │
                    └──────────────────┬───────────────────────┘
                                       ▼
                    ┌──────────────────────────────────────────┐
  物化层（扩展）      │ ScheduleEngine.materialize                │  ← §4.3
                    │ resolveVibrateParams(rng) → 写 occurrence  │  "计划即审计"
                    └──────────────────┬───────────────────────┘
                                       ▼
                    ┌──────────────────────────────────────────┐
  执行层（新）        │ VibrateSession（活跃振动表）               │  ← §7
                    │ 分片续发 ≤20s/片，独立 keep-alive 定时器     │
                    │ 失效安全：进程死 / 重启 / 停止 → 必停        │
                    └──────────────────┬───────────────────────┘
                                       ▼
                    ┌──────────────────────────────────────────┐
  原生层（新）        │ Android: capabilities / waveform+amp /    │  ← §5
                    │          envelope(API36) / stop           │
                    │ iOS:     CoreHaptics 桥（§6）              │
                    └──────────────────────────────────────────┘
```

**贯穿原则**：① 随机在**物化期**用 DPRNG 落地（可复现、可审计）；② 任何降级**必须明示**；
③ 任何"能开"的能力都必须"能停"。

## 4. 模型层设计

### 4.1 为什么**不**扩展 `VibrateAction`（关键设计决策）

候选方案对比：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 给 `VibrateAction` 加一堆可空字段（`mode` + 各模式参数） | 不动 `ActionType` 枚举 | 得到 **nullable 字段汤**：`patternMs?` `durationSecMin?` `amplitudeMin?`… 消费点必然写出 `??` 链猜值 → **正是 BUG-068 的成因**；`sealed` 穷尽性检查也帮不上忙 | ❌ 否决 |
| B. 新增两个 `sealed` 子类 + 两个 `ActionType` 枚举值 | ① 向后兼容（老任务 `action_json` 一字不改）② 参数语义清晰无歧义 ③ **穷尽 switch 会强制所有消费点显式处理**（编译器替我们找漏网点） | 需动 `ActionType` 枚举 → 一批穷尽 switch 报错（这**是收益**不是成本） | ✅ **采纳** |
| C. 用 `CompositeAction`/`ActionSetAction` 拼 | 零模型改动 | 无法表达"持续"与"随机振幅" | ❌ 否决 |

**采纳 B。** 新增：

```dart
// ActionType 新增两项（保留 vibrate = 固定节奏，向后兼容）
enum ActionType { …, vibrate, randomVibrate, continuousVibrate, … }
```

### 4.2 `RandomVibrateAction`（随机振动）

语义：**一次触发** → 在总时长区间内，以**随机脉冲序列**振动；每个脉冲的**时长/强度/间隔**均随机。

| 字段 | 类型 | 默认 | 含义 | 夹紧 |
|---|---|---|---|---|
| `durationSecMin/Max` | int | 3 / 10 | 本次振动总时长区间 | 1 .. `maxDurationSec` |
| `pulseOnMsMin/Max` | int | 150 / 400 | 单脉冲振动时长区间 | 20 .. 2000 |
| `pulseOffMsMin/Max` | int | 100 / 600 | 脉冲间停顿区间 | 0 .. 5000 |
| `amplitudeMin/Max` | double | 0.4 / 1.0 | **强度区间**（核心） | 0 .. 1，且 `min ≤ max` |
| `maxPulses` | int | 200 | 脉冲数上限（**防爆护栏**） | 1 .. 1000 |
| `rampUpSec` | int | 0 | 渐强（音量式，对标 FR-30） | 0 .. 60 |
| `respectDnd` | bool | true | 是否遵循勿扰（false → `USAGE_ALARM`） | — |

> ⚠️ `maxPulses` 不是可选装饰：`pulseOn=20ms + pulseOff=0ms` 在 10 分钟内会产生 3 万个
> 时间点，直接撑爆 Android waveform 数组（现有 `maxVibrateSteps=32` 是给固定节奏的）。
> 超限时**截断并审计**，不抛异常（与"无法判定按满足处理"同一容错哲学）。

### 4.3 `ContinuousVibrateAction`（持续振动）

语义：**一段时长内连续振动**，强度可在区间内**随机波动**，支持渐强/渐弱与占空比。

| 字段 | 类型 | 默认 | 含义 | 夹紧 |
|---|---|---|---|---|
| `durationSecMin/Max` | int | 10 / 30 | 总时长区间（**本地不设上限**，见 D1） | 1 .. `maxVibrateDurationSec`（**传输层**夹紧，§10） |
| `amplitudeMin/Max` | double | 0.5 / 1.0 | **随机振幅区间**（核心） | 0 .. 1 |
| `jitterMs` | int | 0 | 强度波动周期：每 N ms 重取一次随机强度（0=恒定） | 0 .. 5000 |
| `sharpnessMin/Max` | double | 0.0 / 0.0 | 锐度区间（**仅 Android 16 包络支持**） | 0 .. 1 |
| `dutyCyclePct` | int | 100 | 占空比：100=不停顿；50=振一半停一半 | 10 .. 100 |
| `rampUpSec` / `rampDownSec` | int | 0 / 0 | 渐强 / 渐弱 | 0 .. 600 |
| `respectDnd` | bool | true | 同上 | — |

**能力降级链**（§5.2 详述，这里是契约）：

| 设备能力 | 实现 | 用户可见行为 |
|---|---|---|
| Android 16 + `areEnvelopeEffectsSupported()` | `BasicEnvelopeBuilder` 控制点序列 | 强度/锐度**完整生效** |
| API 26+ 且 `hasAmplitudeControl()` | `createWaveform(timings, amplitudes, repeat=0)` | 强度生效，锐度忽略（**明示**） |
| API 26+ 无振幅控制 | on/off waveform | 强度**全部拉满**（**必须明示**，§11） |
| < API 26 | 旧 `vibrate(long[], repeat)` | 强度忽略（**明示**） |

### 4.4 随机参数在**物化期**落地（"计划即审计"）

新增纯函数（`lib/domain/scheduling/vibrate_resolve.dart`，可完全单测、无 I/O）：

```dart
/// 物化期确定振动执行参数；同一 occurrence 任意次重算逐位一致。
class VibratePlan {
  final int durationMs;        // 总时长
  final double baseAmplitude;  // 基准强度（区间内取一个）
  final int chunkCount;        // 分片数（§7.2）
  final int jitterSeed;        // 波动序列种子（执行期复现用）
}

VibratePlan resolveVibratePlan(ActionConfig action, Random rng, String occurrenceId);
```

- **物化期确定**：总时长、基准强度、分片数；
- **执行期确定**：波动序列由 `Random(planSeed('$occurrenceId#jitter', …))` 派生 →
  **同一次执行任意时刻重算，波动曲线一致**（可回答"为什么 14:37 那一刻是 0.72 强度"）；
- `ScheduleEngine.materialize` 现在只对 `PlayAudioAction` 派生 `volume/durationMs`
  （`schedule_engine.dart:79-98`）→ 扩展为对三种振动动作也派生。

**审计落库**：`exec_logs.volume` 列在**振动动作**语义下承载**强度/振幅**（列名复用，
`action` 列已足以区分语义，避免 schema 迁移）；若后续要做强度统计看板，再加列并走
`_onUpgrade`（`app_database.dart:148` 迁移框架已就位）。→ **需在 docs/07 数据模型文档补一句语义说明**。

## 5. 原生层（Android）

### 5.1 新增桥方法（`NativeBridgePlugin.kt` + `NativeBridge`）

```dart
// lib/services/native_bridge.dart 新增
static Future<VibrateCaps> vibrateCapabilities();           // 能力探测
static Future<bool> vibrateWaveform({
  required List<int> timings,       // 交替 静止/振动
  List<int>? amplitudes,            // 0..255 或 null=on/off
  int repeat = -1,                  // -1=不重复；0=无限循环
  bool useAlarmUsage = false,       // → USAGE_ALARM（后台必须）
});
static Future<bool> vibrateEnvelope({
  required List<({double intensity, double sharpness, int durationMs})> points,
  bool useAlarmUsage = false,
});
static Future<void> vibrateStop();  // → Vibrator.cancel()
```

Kotlin 侧要点：

1. **能力探测**（一次性，结果缓存到 kv）：
   `hasVibrator` / `hasAmplitudeControl()` / `areEnvelopeEffectsSupported()`（API 36，用
   `@RequiresApi` + `Build.VERSION.SDK_INT` 守卫）/ `envelopeEffectInfo.minControlPointDurationMillis`。
2. **attributes 必传**（BUG-069 修复方向）：API 33+ 用 `VibrationAttributes.createForUsage(...)`，
   API 26–32 用 `AudioAttributes`；后台场景 `USAGE_ALARM`。
   ⚠️ 注意 `respectDnd=false`（`USAGE_ALARM`）会**穿透勿扰** —— 这与音频 `AudioChannel.alarm`
   同一合规口径，**UI 必须显式提示**（对齐 FR-30 的处理）。
3. **包络必须收尾于 0**：构建器在 `points.last.intensity != 0` 时**自动追加** `(0, lastSharpness, 20ms)`，
   否则必抛 `IllegalStateException`。这条要在宿主机锁里断言（§12）。
4. **waveform 与 envelope 互斥**：同一时刻只允许一个效果；新调用前先 `cancel()`。

### 5.2 降级决策表（纯函数，宿主机可测）

```dart
/// 输入设备能力 + 动作配置 → 输出实际下发参数 + 降级说明列表（非空即需明示用户）
({VibrateCommand cmd, List<String> degradations}) planVibrate(
    VibrateCaps caps, ContinuousVibrateAction a);
```

降级说明会：① 进 `exec_logs.message`；② 汇总到设置页「设备振动能力」卡片；
③ 首次遇到时弹一次提示（**不静默**）。→ 这是对 §2.3 FR-34 口径修正的落地。

## 6. 原生层（iOS CoreHaptics）

新增 `ios/Runner/HapticBridge.swift`，在 `AppDelegate` 注册同名 `MethodChannel('sonic_shield/native')`：

| 桥方法 | CoreHaptics 映射 |
|---|---|
| `vibrateCapabilities` | `CHHapticEngine.capabilitiesForHardware().supportsHaptics` |
| `vibrateWaveform` | `CHHapticPattern` 瞬态事件序列（`CHHapticEventTypeHapticTransient`），强度/锐度按 amplitude 归一化 |
| `vibrateEnvelope` | `CHHapticAdvancedPatternPlayer` + `sendParameters` 动态改 `hapticIntensity`/`hapticSharpness` → **真正实现"持续 + 随机振幅"** |
| `vibrateStop` | `player.stop(atTime:)` / `engine.stop()` |

⚠️ **iOS 能力边界必须在 UI 明示**（对齐 FR-45"能力差异在 UI 明示"）：
- **后台振动受限**：App 退到后台后 CoreHaptics 会被系统暂停 → 后台"持续振动"在 iOS 上
  **做不到**，只能靠本地通知的触感兜底。**不得假装支持**（§11）。
- 无 Taptic Engine 的设备（旧 iPad 等）→ `supportsHaptics=false` → 明示降级。

## 7. 执行层（`background_engine.dart`）

### 7.1 新增动作分支

```dart
case final RandomVibrateAction v:      return vibrateAndLog(task, v, source);
case final ContinuousVibrateAction v:  return vibrateAndLog(task, v, source);
```

`vibrateAndLog` 职责：能力探测 → 降级决策 → 建 `VibrateSession` → 写审计（含降级说明）。

### 7.2 分片续发架构（"不设上限"能成立的前提）

```
VibrateSession（内存 Map + kv 持久化）
   occurrenceId → {plan, startedAt, remainingMs, lastChunkAt}
        │
        │  VibrateKeepAlive：独立 Timer.periodic(3s)   ← 不是 engineTick(15s)
        ▼
   每片 ≤ VIBRATE_CHUNK_MS = 20_000
        │  提前续发（chunk 20s，检查周期 3s → 17s 容错）
        ▼
   native.vibrateWaveform(...) / vibrateEnvelope(...)
```

**为什么不用 `SchedulerConfig.engineTick`（15s）**：片长若取 10s < tick 15s，会出现 5s 空隙
（振动断续，用户可见）。故**振动续发用自己的定时器**（3s 周期 / 20s 片长），
同时**避免改动 `engineTick`** —— 后者被 NFR-04 性能基线覆盖，动它会牵连压测层。

**四条不可裁剪的失效安全约束**（D1 的代价）：

| # | 约束 | 机制 | 为什么必须 |
|---|---|---|---|
| S1 | **进程死亡即停** | 分片续发：进程一死就没人续发 → 振动在 ≤20s 内自然停止 | 若改用 `repeat=0` 无限循环，进程死了振动**可能还在**（不可接受） |
| S2 | **重启绝不续发** | 启动时扫描活跃振动表：**一律停止**，不恢复 | 宁可少震一次，不可失控。与"补执行限流 `catchUpLimit`"同一哲学 |
| S3 | **全局停止入口** | 任务列表 + 设置页 + 通知栏「停止所有振动」；远程 `vibrate.stop` | D1 承诺的"可停止"必须是**任何时刻都能停**，不只是等它到期 |
| S4 | **低电量自动降级** | 电量 < `PowerConfig.saverBatteryLevel`(15%) 且未充电 → 拒绝启动新的持续振动，已在跑的**立即停止并审计** | 对齐 FR-44"省电模式暂停随机类任务"；持续振动是耗电大户 |

> 另：`durationSecMin/Max` 超过 `VIBRATE_CONFIRM_THRESHOLD`（建议 300s）时，
> **保存任务需二次确认弹窗**（"将持续振动 X 分钟"），并在审计写明"用户已确认"。
> 这是软护栏，不阻止使用，只阻止"误配一个 3 小时振动然后忘记"。

### 7.3 与其他子系统的交互

| 子系统 | 交互 | 处理 |
|---|---|---|
| 通话保护 | 震动不干扰通话音频 | 沿用条件层 `skipInCall`（用户可配），**不硬编码** |
| `sound.play` 并发 | 无资源冲突 | 允许同刻；`SoundscapeAction` 同理 |
| `script.stop`（远程指令组） | 指令组被终止 | **同时停止该指令组发起的振动**（否则"停止"名不副实） |
| `PowerService` 模式切换 | 省电模式 | 见 S4 |
| 删除/禁用任务 | 有活跃振动 | 立即停止该任务的振动 |

## 8. 夜间独立豁免机制（D4，**跨功能**，非仅震动）

现状：免打扰由 `ComplianceGuardrails.defaultQuietStart/EndHour`（22:00–07:00）+ 物化期
`ScheduleEngine._applyQuiet` + `QuietPolicy{skip,shift}` 三重保障，docs/08 §4 标注为
**"UI 只能调窄不可调宽"**。D4 要求为**所有功能**增加夜间独立豁免 → **这是削弱护栏**。

### 8.1 双重开关（Two-Key Safety）

| 层级 | 字段 | 默认 | 位置 |
|---|---|---|---|
| 主开关 | `Settings.allowQuietExempt` | **false** | 设置页（需二次确认弹窗，文案写明后果） |
| 任务级 | `Task.quietExempt` | **false** | 任务编辑器（主开关关闭时**置灰不可点**） |

两者皆 true 时，`_applyQuiet` 对该任务**放行**，并写审计
`action=quietExempt, message='用户豁免免打扰（任务级）'`。

### 8.2 三条硬约束

1. **远程命令不得开启豁免。** `TaskWire.fromWire` 必须**显式丢弃**入站的 `quietExempt`
   （与 §10 的"白名单式透传"同一处理，`task_wire.dart:364` 已有先例）。
   理由：允许远程开启豁免 = 允许**已配对的对端绕过合规护栏**，直接触碰项目红线
   （"未授权控制他人设备"）。→ **必须有"能失败"的锁**（§12）。
2. **不得静默生效。** 每次豁免执行都留痕；设置页展示"本月豁免 N 次"。
3. **文档同步。** docs/08 §4 表格该行从"不可绕过"改为
   **"默认强制（22:00–07:00）；用户可经双重开关显式豁免，全部留痕；远程不可开启"**，
   并在 §2 Redline 增补一句：**"豁免仅用于用户自身场景（如夜间静默提醒/闹钟），
   不得用于在夜间制造对他人有影响的干扰"**。CHANGELOG 需单列该行为变更。

## 11. 合规与安全边界

**合法用途定位**（写进 docs/08 §1 Whitelist，与现有条目同构）：

- **静默提醒**：久坐/喝水/服药/习惯养成 —— 震动**不产生噪声**，比声音提醒**更不打扰他人**，
  在合规上优于现有音频提醒；
- **无障碍**：听力障碍用户的触觉提醒通道；
- **守护提示**：独居家人的定时确认（无音频场景）；
- **寻找设备**：持续振动辅助定位自己的手机。

**红线重申**（docs/08 §2 已有，本轮不改）：**不得利用随机振动/持续振动骚扰、恐吓、
报复任何他人**；豁免仅用于用户自身场景。

**护栏清单（本轮新增/变更）**：

| 护栏 | 值 | 位置 | 变更 |
|---|---|---|---|
| 免打扰 | 22:00–07:00（可调窄） | `_applyQuiet` | **新增任务级豁免（默认关，双重开关，远程不可开）** |
| 最小冷却 | ≥60s | `ComplianceGuardrails` | 不变 |
| 持续振动硬上限 | **无**（D1） | — | 由 S1–S4 四条失效安全约束替代 |
| 脉冲数上限 | `maxPulses` ≤ 1000 | 模型 assert + UI | 新增（防数组爆炸） |
| 超长二次确认 | > 300s | UI | 新增 |
| 低电量降级 | <15% 且未充电 → 停止 | `PowerService` | 新增（对齐 FR-44） |
| 能力降级明示 | 无振幅控制 → 告知 | UI + 审计 | 新增（FR-34 口径修正） |
| 全量审计 | 每次振动留痕（含降级说明） | `exec_logs` | 不变（`volume` 列承载强度） |
