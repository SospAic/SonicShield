# 59 — 锁屏后自动化任务执行：机制、现状与彻底解决方案

> 2026-10-15 阿岩。问题：「手机锁屏之后好像无法执行自动化任务」。
> 结论先行：这不是一个 bug，是 **四层系统机制** 在同一时刻叠加的结果；
> 「彻底解决」= 分层击穿 + 把设备侧准备固化为脚本/基础设施。本文给出根因、
> 项目现状（带行号证据）、3 个真实缺口、分层方案与验证方法。

---

## 1. 根因：四层机制叠加

| 层 | 机制 | 锁屏后发生什么 | 谁管得住 |
|---|---|---|---|
| L0 屏幕语义 | 灭屏 = Activity 不可见 | UI 自动化（flutter drive / Appium / UiAutomator）**直接失驱动** | 设备设置（stayon / 无锁屏） |
| L1 Doze（API 23+） | 灭屏 + 静止进入 DeviceIdle | 网络禁用；Alarm/JobScheduler 推迟到 maintenance window（间隔越拉越长：15min → 1h → 2h）。`setExactAndAllowWhileIdle` 也受限：**每 9 分钟最多一次** | Doze 白名单 + 特权闹钟通道 |
| L2 App Standby | 不常用 app 降桶 | 后台任务延迟数小时；受限桶（restricted）几乎全停 | `am set-standby-bucket active`（adb/shell）+ 白名单 |
| L3 厂商 ROM | MIUI/EMUI/ColorOS/OxygenOS 私有省电 | **AOSP 白名单管不到**：自启动权限、关联启动、神隐模式、冻结后台。这是「彻底解决」的终极 BOSS | ROM 深链引导用户手动开 + adb 预配置（测试设备） |
| L4 FGS 启动限制 | Android 12+ 后台起 FGS 受限；15+ 禁止 BOOT_COMPLETED 起 mediaPlayback/dataSync | 进程被杀后自愈路径被斩断 | 精确闹钟豁免路径（本项目已落地，见 §3） |

**一句话**：锁屏后任务不执行 = L0/L1/L2 让「唤醒」迟到或不到 + L3 让「进程」根本不存在 + L4 让「自愈」起不来。

## 2. 领先理念（2025-2026 主流实践，联网检索结论）

1. **分层唤醒栈，逐层降级并留痕**：`setAlarmClock`（特权通道）→ `setExactAndAllowWhileIdle`
   （精确）→ WorkManager expedited work（可继承 FGS 启动权）→ 普通 worker。
   每层都要有**自检和诊断出口**（本项目 `alarmDiag` 即是此理念的雏形）。
2. **「任务意图」优于「任务时间」**（iOS BGTaskScheduler 能耗意图模型、Android
   WorkManager constraints 的共同方向）：声明「充电 + Wi-Fi + 空闲」等约束交给
   系统择机。对非准时任务更省电、更不容易被杀。但对「必须准时」的任务（定时播放/
   振动），唯一正解是下一条。
3. **`AlarmManager.setAlarmClock()` 是 Doze 中唯一保证准时的公开通道**：系统把它当
   用户可见闹钟，Doze 中准时触发、**不受 9 分钟最小间隔限制**、状态栏显示闹钟图标
   （用户知情契约）。闹钟类应用（正点闹钟、DJ 报时）全部走这条。
4. **测试设备即基础设施**：CI 真机农场（Firebase Test Lab、AWS Device Farm）自动保持
   亮屏/无锁/白名单；自建流水线应把 `adb` 预配置固化为一步。
5. **自愈必须可观测**：看门狗闹钟 + 代次（generation）校验 + 失败用户通知，比「悄悄
   重试」更接近「彻底」——用户能看见「为什么没执行」。

## 4. 三个真实缺口（本轮定位，待老板拍板是否升级）

### 缺口 1（P0，准时性）：调度闹钟没用 `setAlarmClock` 特权通道

- 证据：`packages/native_bridge/android/src/main/kotlin/com/sonicshield/native_bridge/NativeBridgePlugin.kt:267`
  （及 BootReceiver.kt:72、ExactAlarmPermissionReceiver.kt:64）全部使用
  `am.setExactAndAllowWhileIdle(...)`。
- 后果：深度 Doze / 部分厂商 ROM 上，锁屏后的定时触发仍可能被推迟（9 分钟最小间隔 +
  maintenance window 语义）。对「定时必须准时」的产品承诺，这是仅剩的最大不确定性。
- 升级方案（改动小、风险低）：给 `scheduleExactAlarms` 增加 `setAlarmClock` 变体 ——
  对「用户可见的定时任务」用它（系统允许，且状态栏闹钟图标就是用户知情）；
  内部看门狗/补偿类闹钟继续用 `setExactAndAllowWhileIdle`。需要评估：状态栏图标
  对 7×24 常驻产品的观感（可做成 Settings 开关，默认开）。

### 缺口 2（P1，桶降级）：没有 App Standby bucket 的自检/兜底

- `am set-standby-bucket <pkg> active` 需要 shell/系统权限，app 内无法自提权；
  但**可以自检**：`UsageStatsManager.getAppStandbyBucket()` 读到 rare/restricted 时，
  在 UI 上提示用户（与既有 OEM 深链同一位置）。当前未见该自检。

### 缺口 3（P2，测试基建）：无防锁屏预配置脚本 → 本轮已交付

- `integration_test/` 有 10 个 UI 自动化用例（含 `vibrate_background_test.dart`、
  `guard_toggle_device_test.dart` 等后台/真机行为测试），灭屏即失驱动。
- **本轮交付**：`prepare_device.bat`（仓库根目录，与 install_all.bat 作伴）：
  防锁屏 + Doze 白名单 + standby bucket + 精确闹钟授权 + 一键恢复 + 只读 verify。
  mock adb 冒烟 26/26 通过（`_test_install/prep_smoke.py`），未动真机。

## 5. 分层方案（按优先级）

```
L6  iOS      BGTaskScheduler「任务意图」+ 静默推送(30s窗口) + 音频保活
             ⚠ 平台实话：iOS 锁屏 ≈ suspended，准时执行做不到，只能系统择机
L5  可观测    alarmDiag 留痕 + 看门狗代次校验 + 失败通知（已有雏形，补 §4.2 自检）
L4  测试基建  prepare_device.bat（已交付）→ CI 固化一步
L3  ROM 对抗  OEM 深链引导（已有）+ adb 预配置白名单（prepare_device.bat）
L2  保活      FGS mediaPlayback 常驻（已有）+ PARTIAL_WAKE_LOCK 播放期 CPU
L1  准时唤醒  setAlarmClock 特权通道（缺口 1）+ setExactAndAllowWhileIdle 兜底
L0  屏幕      设备侧 stayon/无锁屏（自动化场景）；产品侧亮屏广播（已有原生能力）
```

### 5.1 设备预配置命令集（prepare_device.bat 已封装）

```bat
adb shell svc power stayon true                                   REM 充电时常亮
adb shell settings put global stay_on_while_plugged_in 3          REM USB|AC 时常亮
adb shell settings put system screen_off_timeout 2147483647       REM 永不超时
adb shell locksettings set-disabled true                          REM 无锁屏
adb shell dumpsys deviceidle whitelist +com.sonicshield.sonic_shield  REM Doze 白名单
adb shell am set-standby-bucket com.sonicshield.sonic_shield active    REM 活跃桶
adb shell appops set com.sonicshield.sonic_shield SCHEDULE_EXACT_ALARM allow
```

### 5.2 Doze 压测（CI 验证准时性用，主动进入 Doze 而非干等）

```bat
adb shell dumpsys battery unplug        REM 模拟拔电，设备才会真正进 Doze
adb shell dumpsys deviceidle force-idle REM 立即进入深度 Doze
adb shell dumpsys deviceidle step        REM 单步推进状态机
adb shell dumpsys deviceidle unforce     REM 恢复
adb shell dumpsys power | find "mWakefulness"   REM 观察灭屏状态
```

### 5.3 缺口 1 的落地实现（2026-10-16 已实施）

`NativeBridgePlugin.scheduleExactAlarms(ctx, times, useAlarmClock)`：

```kotlin
if (useAlarmClock) {
    am.setAlarmClock(AlarmManager.AlarmClockInfo(t, null), pi)   // 特权通道
} else if (SDK_INT >= M) {
    am.setExactAndAllowWhileIdle(RTC_WAKEUP, t, pi)              // 既有路径
}
// 特权通道排布失败 ⇒ 逐条回退 setExactAndAllowWhileIdle，
// 并把降级原因写进回执 error（引擎 alarmDiag 如实呈现，不静默）
```

- Dart 侧：`NativeBridge.setExactAlarms(times, useAlarmClock:)` → 返回结构化
  `AlarmScheduleResult`（P1-04 契约不变）；
- 引擎：`pushExactAlarms` 读 prefs `alarmClockChannel`（**默认 true**）选通道；
- UI：设置页「后台保活」→「闹钟特权通道（Doze 准时唤醒）」开关，
  副标题明说「关闭 = 准时性降级」（不许让用户以为只是观感问题）；
- 回归锁：`test/reactive_noise_gate_test.dart` 同批；通道选择由
  `AlarmScheduleResult` 的结构化回执覆盖（既有 `alarmDiag` 断言链）。

### 5.4 缺口 2 的落地实现（2026-10-16 已实施）

- 原生：`standbyBucket` → `UsageStatsManager.appStandbyBucket`，映射
  `active/working_set/frequent/rare/restricted/unknown`；API<28 或未授予
  `PACKAGE_USAGE_STATS`（appop）⇒ `unknown`（**读不到 ≠ 确定状态**）；
- Dart：`PowerService.standbyBucket / standbyRestricted / standbyBucketLabel`；
- UI：设置页仅在 **rare/restricted** 显示警告卡 + 「去设置」深链
  （`openOemAutostart`）；`unknown` 一律不显示（BUG-041 同款纪律）。

### 5.5 缺口 3 的落地实现（2026-10-16 已实施）

- `scripts/prepare_device.bat`（仓库内，自包含；与仓库根 `prepare_device.bat`
  同能力）：apply / --restore / --verify / -s 单机 四态；
- mock adb 冒烟 26/26（`_pt/ci_prep_smoke.py`）；
- CI 接法：真机步骤前跑 `scripts\prepare_device.bat`，跑完 `--restore`；
  Doze 压测命令见 §5.2。

## 6. iOS：必须对老板说的实话

- 锁屏后 app 数秒内转 suspended；`BGTaskScheduler` 的 `BGProcessingTask` 由系统择机
  （充电 + Wi-Fi + 空闲才可能跑），**不可控、不可准时**；静默推送给 30 秒窗口；
  音频 background mode 能保活但 iOS 26+ 持续收紧。
- **iOS 上「锁屏后准时执行」在平台层面不成立**。产品承诺应写成「系统择机执行」，
  或引导用户「前台保持」/「充电时」。—— 不把平台限制包装成「已解决」。

## 8. 验证与测试（2026-10-16）

### 8.1 沙箱内真跑 `flutter test`（本轮打通）

本机沙箱**拦 Dart 父进程 spawn 子进程**（`CreateFile failed 231` /
`ERROR_PIPE_BUSY`），`flutter test` / `flutter analyze` 自身都起不来。
已用**两段手工链路**替代（与 flutter_tools 同契约）：

1. **编译测试 kernel**：`frontend_server_aot.dart.snapshot`
   （`--sdk-root …/flutter_patched_sdk/`、`-Ddart.vm.product=false`、
   **`--native-assets build/native_assets/windows/native_assets.json`**）
2. **执行**：`flutter_tester.exe`
   （`--enable-checked-mode --verify-entry-points --use-test-fonts
   --flutter-assets-dir=build/unit_test_assets`，环境变量 `FLUTTER_TEST=true`）

**三个必踩坑**（都已实测踩过）：
- 缺 `--native-assets` ⇒ `sqflite_common_ffi` 报
  `Couldn't resolve native function 'sqlite3_initialize'`（DB 类测试全崩）；
- 缺 `--flutter-assets-dir` ⇒ Material 组件报
  `Asset 'shaders/ink_sparkle.frag' not found`（展开卡片即炸）；
- 测试跑完后 `flutter_tester` **进程不退出**（未清理的定时器/连接）⇒
  必须**流式读取 + 检测到 `All tests passed!` 立即终止**，否则每个文件白等超时
  （实测：固定等超时让 45 个文件耗掉 23 分钟；改成提前终止后单文件 ~2s）。

### 8.2 ⚠️ 撤回一条不可信结论（analyzer 假绿）

本轮早期曾报「真分析器 11 文件 `No issues found!`」。**该结论已作废**：
给同一包装喂**故意写错类型**的文件（`int x = "string";`），它同样回
`No issues found!` ⇒ 该包装从未真正收集到 errors。
**用假绿当门禁比没有门禁更危险**，故本条明确撤回，真门禁改用「测试编译 + 执行」。

### 8.3 baseline 对照法（判定"是不是改动引起的"）

把改动文件临时还原到 `HEAD~1` 跑同一测试，对比红绿。两条纪律：
- **恢复必须从备份复制，绝不能用 `git checkout HEAD -- <file>`** ——
  后者会抹掉 HEAD 之后的所有未提交改动（实测丢过两个文件的修复，靠备份救回）；
- 比较哈希要**归一化行尾**（CRLF/LF 差异会被误判为"内容变了"）。
