# 16 · 视频通话模块设计（v1.4，方案 A）

> 能力：App 内向已配对端点发起视频/语音通话，被叫端可**自动接通**。
> 定位：家人守护（老人/儿童看护）与本人设备间协作。
> 选型：**WebRTC P2P（flutter_webrtc）+ 声盾 MQTT E2EE 信令**（方案 A）。
> 落选：云 SaaS（声网/TRTC，隐私定位冲突）、自建 SFU（单人对单人过重）。

---

## 1. 架构与信令

```
呼叫端                                          被叫端
call.invite {callId,video,sdp} ──MQTT E2EE──► 自动接通判定 → setRemote(offer)
call.candidate {ice}        ◄────────►        onIceCandidate 互发
        ◄───────────── call.answer {sdp} ──────────────
        ◄═══════ DTLS-SRTP 媒体直连（P2P） ═════════►
call.end {reason} ─────────────────────────► teardown
```

- 信令复用 v1.2 远程模块：配对密钥 → HKDF → AES-256-GCM；AAD 绑定主题；
  时间窗 + 去重防重放——**信令层零新增安全面**。
- 媒体：WebRTC 内建 DTLS-SRTP（传输加密），P2P 直连不经服务器。
- ICE：**国内可达 STUN 优先**（`stun.miwifi.com` / `stun.chat.bilibili.com` /
  `stun.qq.com`）+ Google 兜底；对称 NAT 需自建 TURN（「远程 → 设置」可配，
  自动补 UDP + TCP 两条传输，见 §10.2）。
  ⚠️ 历史教训：初期只用 `stun.l.google.com`，**中国大陆普遍不可达**，
  导致"建连慢、直连失败"——这正是 §10 一轮优化的起因之一。

## 2. 状态机（CallPhase）

```
idle → ringing（被叫）/ connecting（主叫）→ connected → ended → idle
```

- 主叫：getUserMedia → createOffer → setLocal → invite → setRemote(answer)
- 被叫：invite → 自动接通判定 → getUserMedia → setRemote(offer) →
  createAnswer → 回 answer
- Phase 经 Stream 广播给 UI（Overlay 全屏来电/通话界面）。

## 3. 自动接通

- 设置项 `rc_call_auto_answer`（默认关闭），仅对**已配对设备**生效；
- 占线保护：通话中收到新 invite → 自动回 `call.end{reason:busy}`；
- **平台限制（诚实声明）**：
  1. 被叫 App 进程存活（端点服务运行）时才可能自动接通——强杀后
     broker 无法唤起进程；
  2. Android 14+ while-in-use：camera|microphone FGS 必须前台启动——
     自动接通路径为「fullScreenIntent 亮屏 → 前台接通」，后台静默
     开摄像头不存在（平台禁止，且产品上明令禁止，见 §6）；
  3. 摄像头/麦克风权限需提前授予（开启自动接通时引导申请）。

| 页面 | 路由 | 内容 |

  v1.5 拆分「仅响铃待确认」模式）。

## 6. 合规红线（不可协商）

1. **仅限本人设备或已获明确授权的设备**（配对即授权记录）；
2. **无隐蔽模式**：接通即亮屏、通话 UI 可见、系统摄像头指示灯正常——
   平台层面 Android 14+ 也禁止后台静默开摄；
3. 在他人不知情时开启其摄像头/麦克风属侵犯隐私，可能涉刑——
   本应用不提供、不会提供该能力；
4. 文档与商店话术统一为「家人守护视频通话」。

## 8. 关于「免同意控制」的安全决策

需求评估结论（2026-09-14）：**「未经对端同意直接控制他人设备」不予实现**——
技术上可行，但属未授权访问（多数辖区刑事犯罪），违反 docs/08 红线。
合法替代：**二维码扫码配对**（物理在场即强同意证明，比手输配对码更便捷）+
已配对设备自动信任（v1.2 现状）。此决策同时保护设备持有方，
是 KDE Connect 等行业产品的共同选择。

## 9. 设备完全控制命令（v1.6，合法边界内）

扩展四条仅限已配对设备的设备级命令（远程中心 · 控制台 Tab）：

| 命令 | 端点行为 | 回执事件 | 安全边界 |
|---|---|---|---|
| device.status | 电量/充电/版本/待执行计划数快照 | rc.device | 只读，无风险 |
| location.get | 守护定位回传（geolocator，显式授权） | rc.location | 定位属敏感个人信息：仅守护场景、接收端可随时取消配对、全程审计 |
| volume.set | 媒体/闹钟音量（0..1） | rc.ack | MODFY_AUDIO_SETTINGS 已声明；不影响铃声音量 |
| camera.snap | 拍照回传 | rc.photo | **v1.6 暂缓启用**：camera 插件（camerax）与 AGP9 内置 Kotlin 不兼容；协议与 UI 保留，等待插件迁移；启用前先审 docs/08 红线 |

**明确不做**（永久红线，docs/16 §8 延续）：解锁屏幕、绕过密码、
静默开启摄像头/麦克风（无可见提示）、读取短信/聊天记录、
未经授权的他人设备控制。拒绝理由与合法替代（扫码配对）见 §8。

### 9.1 信息架构（v1.7 重构：底部导航 6 → 5 TAB）

原 6 项（守护/任务/音源/守卫/日志/设置）超出 Material 3 建议的 3–5 项，
触达率与可辨识度都会下降。现按**语义聚合**为 5 项，视频通话与对讲并入「远程」：

```
底部导航（5）
├─ 守护      本机 + 远程状态总览
├─ 自动化    任务 / 音源 / 守卫        同一条流水线：守卫监听 → 任务命中 → 播放音源
├─ 远程      设备 / 任务 / 指令组 / 通话   共享配对表与在线状态
├─ 日志      审计 / 统计              同一份 exec_logs 的明细视图与聚合视图
└─ 设置      含远程模块设置、配对管理
```

远程分组页的四个子 TAB 按「**先选设备 → 看状态 → 再操作**」排列：

```
/remote（远程 · 4 子 Tab，子 TAB 用 ?t= 深链）
├─ 设备    端点选择 + 实时状态卡 + 快捷命令（Ping/状态/音量/守卫/定位/拍照）
├─ 任务    端点任务全貌（名称/触发器/动作/启停/跳过/待执行统计）
├─ 指令组  收藏模板一键发送 + 新建组装器入口
└─ 通话    视频/语音入口卡 → /remote/call；对讲入口 → /remote/ptt（整页）
```

对讲采用**整页**而非子 TAB：按住说话是持续按压交互，塞进子 TAB 会与
横滑切换手势冲突。

**回执事件流**：`RcEndpointService.events`（解密后广播）。注意端点回执的
业务字段全部在信封的 **`payload` 之内**，UI 侧统一用 `rcPayloadOf()` 取值
（v1.7 前直接读顶层字段导致所有回执面板恒为空——BUG-023）。
命令-回执按 `payload.for == msg.id` 关联。

**状态保持**：底部导航用 `StatefulShellRoute.indexedStack`，各分支保持
独立导航栈与滚动位置，切 TAB 不重建。

## 10. 媒体档位与性能优化（v1.9，治「一建立通话就爆卡」）

> 现象（2026-10-06 用户反馈）：**建立视频/语音通话时，发起方与接收方机器同时"爆卡"**
> （整机卡顿、掉帧、发热）。根因**不在信令**，而在**编码器负载没有上限**——
> 症状看着像"网络问题"，实际是本机 CPU 被编码吃满。

### 10.1 三个结构性缺口（旧实现）

1. **编码器无码率/帧率上限**。`getUserMedia` 只写死 `width:640,height:480`、
   **完全不设帧率**，且 `call_service.dart` 与 `multi_call_service.dart`
   **从不调用 `RTCRtpSender.setParameters`**。WebRTC 的默认行为是
   "带宽有多少就用多少"——BWE（带宽估计）会把码率一路抬到编码器跑不动为止；
   低端机上编码线程一旦吃满 CPU，**整机**都会卡（不只是画面卡）。
2. **降级偏好缺省 `balanced`**。CPU/带宽吃紧时它**同时**掉分辨率和帧率——
   用户主观感受是"又糊又卡"。实时通话要的是"宁可糊一点，也要跟手"。
3. **多路各自编码**。本模块是 **P2P + MQTT 信令（无 SFU）**，Simulcast/SVC
   无法复用编码器：N 路视频 = N 个独立编码器同时跑。行业实测把
   "低配机上同时跑太多路视频"列为卡顿头号来源。

### 10.2 行业做法（调研出处）

| 结论 | 出处 |
|---|---|
| `setParameters` 可在**不重新协商**的前提下改 `maxBitrate` / `maxFramerate` / `scaleResolutionDownBy` / `degradationPreference` | [MDN: RTCRtpSender.setParameters()](https://developer.mozilla.org/en-US/docs/Web/API/RTCRtpSender/setParameters) |
| `degradationPreference` 三值语义：`balanced`（默认，两者都降）/ `maintain-framerate`（降分辨率保帧率）/ `maintain-resolution`（降帧率保分辨率） | [W3C: MediaStreamTrack Content Hints](https://www.w3.org/TR/2024/WD-mst-content-hint-20241031/) · [MDN: getParameters()](https://developer.mozilla.org/en-US/docs/Web/API/RTCRtpSender/getParameters) |
| 通话场景应取 `maintain-framerate`；`maintain-resolution` 只适合共享内容/PPT | 降级策略对照表 · [Sora Android SDK](https://sora-android-sdk.shiguredo.jp/signaling)（默认即 `MAINTAIN_FRAMERATE`） |
| 自适应降级应"先砍分辨率/帧率，再砍码率"，并给出**阶梯**（resolution ladder） | [nat.io: WebRTC Performance Optimization](https://nat.io/blog/webrtc-performance-optimization) · [Red5: Adaptive Live Encoding](https://dev.to/maria-artamonova/how-to-create-webrtc-publisher-clients-with-adaptive-live-encoding-2fpd) |
| 低配机同时跑过多视频流是卡顿主因，需按**路数**主动降级 | 同上（nat.io） |

### 10.3 落地：`lib/remote/call_media_profile.dart`（单一真源）

档位表与约束生成集中在**一个文件**，单路 / 多路共用，**避免参数漂移**
（历史教训：同一份媒体参数写在两处，改一处漏一处）。

**采集档**（`getUserMedia` 约束，`callVideoCapture`）：`640×480 @ 24fps`。
- 用 `ideal` 而**非精确值**：精确值在"摄像头不支持该分辨率"的机型上会让
  **整通电话直接起不来**；`ideal` 让平台挑最接近的一档。
- `frameRate` 必须显式给 **`max`**：否则部分机型会以 30/60fps 采集。
- 24fps 而非 30：肉眼几乎无感，却能把编码负载降约两成——"先砍帧率"的第一级。

**发送档**（`RTCRtpSender.setParameters`，`sendProfileFor(并发视频路数)`）：

| 并发视频路数 | 码率上限 | 帧率上限 | 缩放 | 说明 |
|---|---|---|---|---|
| 1 | 600 kbps | 24 | 1.0 | 单路：480p 够用，留足清晰度 |
| 2 | 400 kbps | 20 | 1.0 | 两台设备：各降码率，帧率略降 |
| 3 | 260 kbps | 15 | 1.5 | 480×320：编码像素数降约 55% |
| ≥4 | 150 kbps | 12 | 2.0 | 320×240：保底"看得见"，优先不卡 |

- **全部档位取 `maintain-framerate`**（宁可糊，不要卡）。
- 参数区间取自行业推荐表（480p/24fps ≈ 600kbps；360p/15fps ≈ 250kbps；
  240p/12fps ≈ 150kbps），四舍五入到整档；`CMP-03..09` 逐档写死数字并锁"单调不增"。

**下发时机**（`setParameters` 的硬约束：必须在本地描述就位之后）：
- 单路：`call_service` 在 `setLocalDescription(offer)`（主叫）/ `setLocalDescription(answer)`
  （被叫自动接通）之后各调一次 `_applySendProfile()`（固定 `sendProfileFor(1)`）。
- 多路：`multi_call_service` 在每路 `setLocalDescription` 后 `_applyProfilesToAll()`；
  **新增一路 → 全体降级**，**挂断一路 → 剩余恢复档位**（路数下降即回画质）。
- 收尾时清空 sender 列表，避免"下一通只下发一次"被上一通的残留污染。

### 10.4 测试与可断言性

- `test/call_media_profile_test.dart`（**纯逻辑**，CMP-01..10）：约束 `ideal`/`max`、
  逐档数字、非法路数（0/负数）、单调性、降级偏好穷尽映射。
- `test/call_service_webrtc_test.dart` 组 `CS-K`（CS-43..46）：视频 sender **真的**收到
  600kbps/24fps/`maintain-framerate`；语音无视频 sender 则**不下发**；被叫自动接通同样下发；
  收尾后列表清空。
- `test/multi_call_service_connect_test.dart` 组 `MC-G`（MC-26..29）：单路 600 →
  加第二路两路都 400 → 挂断一路恢复 600；语音多路不下发。
- ⚠️ 为让上述断言**不是假绿**，`test/support/webrtc_stub.dart` 做了保真升级：
  `addTrack` 返回**真实形状**的 track（旧桩恒回空 track 会让"只调视频轨"的分支
  恒提前 return）、`getUserMedia` 按约束回轨（`video:false` 不再返回视频轨）、
  新增 `rtpSenderSetParameters` 观测面记录下发内容。

### 10.5 边界（不做什么）

- **不引入 SFU / 不自建 Simulcast**：本模块是 P2P 单人链路，投入产出比不符（§1 选型）。
- **不做精确分辨率**：见 §10.3 `ideal` 的理由。
- **档位下发失败不挡通话**：退回 WebRTC 默认自适应，通话仍能建立——
  与 `_setSpeakerphone` 同款的取舍，属**刻意**的非致命降级，不是静默失败。
