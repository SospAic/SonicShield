# 18 · 临时协助会话设计（临时码 + 访问密码，v1.7）

> 状态：**技术选型完成，待实现**。本文是「从架构开始的技术选型」交付物。
> 关联：docs/14（远程遥控）、docs/16（视频通话）、docs/08（合规红线）、docs/03（技术架构）。

## 0. 需求

对标向日葵 / ToDesk 的**临时设备码 + 访问密码**远程协助：控制端输入一组短码
与一个密码即可接入，**无需预先扫码配对**。

附加约束（用户明确要求）：

1. 全网调研行业领先理念与优秀实现；
2. 从架构开始做全面技术选型；
3. 遵循项目既有规范开发；
4. 可提供服务器，但**优先无服务端（serverless）方案**。

## 1. 行业调研结论

| 产品 | 临时接入模型 | 会合/中继 | 加密 | 可借鉴点 |
|---|---|---|---|---|
| 向日葵 | 识别码 + 临时密码/本机验证 | 自建云 | TLS + 会话加密 | 免登录、识别码口述 |
| ToDesk | 设备代码 + 临时密码 | 自建云 | 自研加密通道 | 免登录直连认证、密码随会话轮换 |
| **RustDesk** | ID + **一次性密码** | `hbbs`（会合/ID）+ `hbbr`（中继） | Ed25519 + NaCl 密钥交换 → 每会话对称密钥；**中继只见密文** | 开源可考：权限位、失败锁定、2FA、会话超时、自建会合 |
| AnyDesk | 地址 + 无人值守/临时密码 | 自建云 | TLS 1.2 + RSA/AES | 「有人值守 vs 无人值守」分离 |

**关键共识（四条）**

1. **必须有会合点**：跨 NAT 的两个端点在互相发现前无法直连——这是物理约束，
   与实现无关。厂商的「云」本质就是会合 + 中继。
2. **中继必须盲**：中继只转发密文，端到端加密在两端完成（RustDesk 明确如此）。
3. **临时码是公开的、密码才是秘密**：所以鉴权强度取决于密码熵 + 抗离线爆破能力。
4. **有人值守 = 明示同意**：行业把「需要对方读出临时码」视为同意证据；
   「无人值守」是另一条产品线，且需用户预先显式开启。

## 2. 合规前置结论（本设计的硬边界）

docs/08 与 docs/14 §7.5、docs/16 §8 已判定：**「免同意控制」不予实现**（未授权访问
在多数辖区属刑事犯罪）。

**本模式为何合规**：临时码只在**端点屏幕上**生成，且必须由端点使用者**主动读出/告知**
控制端——这与「二维码物理在场扫码」等价，都是**明示同意**。而「免同意控制」指的是
在设备持有者不知情、未同意时建立控制。

**由此导出的不可协商设计约束**：

| # | 约束 | 落地方式 |
|---|---|---|
| C1 | 会话只能由**端点侧发起** | 无「控制端唤醒端点建会话」的命令，从协议层杜绝 |
| C2 | 会话**全程可见** | 端点常驻横幅：控制端名称 + 剩余时长 + 【立即终止】 |
| C3 | **无隐蔽模式** | 不提供隐藏横幅/静默会话；与会话权限位无关 |
| C4 | 临时码**一次性 + 短 TTL** | 默认 10 分钟，会话结束即作废，不落盘明文 |
| C5 | 权限**默认全拒** | 会话建立时所有能力关闭，由端点用户逐项放行 |
| C6 | **全程审计** | `exec_logs`：`source=assist`，记录建立/权限变更/终止/对端标识 |

## 3. 总体架构（三平面）

```
┌──────────────┐  ①信令/控制面  ┌─────────────────────┐  ①信令/控制面  ┌──────────────┐
│  控制端 App   │◄─────────────►│  公共 MQTT Broker    │◄─────────────►│   端点 App    │
│ (Controller) │  MQTT + E2EE  │ (broker.emqx.io)    │  MQTT + E2EE  │  (Endpoint)  │
└──────┬───────┘               └─────────────────────┘               └──────┬───────┘
       │                                                                     │
       │                    ②媒体面（WebRTC / DTLS-SRTP）                    │
       └─────────────────────────────────────────────────────────────────────┘
                  STUN（公共免费）→ P2P 直连；对称 NAT → ③ 可选 TURN 中继
```

**平面职责与「是否需要自建服务端」**

| 平面 | 职责 | 本方案实现 | 自建服务端 |
|---|---|---|---|
| ① 信令/控制面 | 会合、鉴权握手、命令/回执、通话信令 | **复用现有 MQTT E2EE 通道** | **不需要**（复用已配置 broker） |
| ② 媒体面 | 视频/音频流 | **复用现有 WebRTC**（docs/16） | **不需要**（STUN 用公共免费节点） |
| ③ 中继面 | 对称 NAT 兜底 | 可选 TURN | 可选，**仅对称 NAT 场景** |

> **结论：默认全链路 serverless。** 唯一可能需要自建的是 TURN，且只在对称 NAT
> （业界经验约 8–15% 的连接）时启用；不配 TURN 时视频降级为纯语音/命令，不影响遥控。

这与 RustDesk 的 `hbbs`/`hbbr` 同构，区别在于：**我们不部署 hbbs/hbbr，而是复用
现成的公共 MQTT 作为会合，用公共 STUN + 可选 TURN 承担中继**。

## 4. 核心设计：密码认证会合主题（Password-Authenticated Rendezvous）

这是本方案相对「照搬厂商做法」的关键改进，解决**临时码可枚举**带来的离线爆破风险。

### 4.1 凭据

| 凭据 | 形态 | 熵 | 用途 |
|---|---|---|---|
| **临时码** `code` | 9 位数字（ToDesk 式，便于口述） | ≈30 bit | **仅**用于展示与用户输入，**不单独作为安全边界** |
| **访问密码** `pw` | 8 位 Crockford Base32（去易混字符） | ≈40 bit | **真正的共享秘密**，端点随机生成 |

### 4.2 会合主题派生

```
topic = "sonicshield/v1/assist/" + Base32( SHA-256( code + "|" + pw ) )[0:16]
```

**为什么这样设计**（这是本方案的安全核心）：

- 只窃听到 `code` 的攻击者**无法算出 topic** → 无法订阅 → **拿不到任何握手密文**
  → **不存在可供离线字典攻击的素材**；
- 想发起攻击必须先猜中 `pw` 才能算出 topic，而猜中 `pw` 就已经能正常接入了
  → 攻击收益不高于直接猜密码，天然具备 **PAKE 式「不可离线攻击」** 性质；
- topic 由 SHA-256 派生，**不泄露** `pw`（原像抗性）。

> 对比：若把 `code` 直接做 topic（厂商常见做法），攻击者可枚举全部 30 bit 的 topic
> 并长期收集握手密文，再离线爆破密码。本设计从根上消除该路径，且**零额外依赖**。

### 4.3 密钥派生

```
sessionSecret = HKDF-SHA256(ikm = pw,
                            salt = "sonicshield-assist-v1|" + code,
                            info = "assist")           → 32B
ctlKey = HKDF-SHA256(sessionSecret, info="ctl")  → 控制端→端点 方向
epKey  = HKDF-SHA256(sessionSecret, info="ep")   → 端点→控制端 方向
```

沿用现有 `RcCodec` 的 AES-256-GCM + **AAD = topic**（防跨主题移植密文）。

### 4.4 握手时序

```
控制端                                          端点
  │  assist.hello {nonce, ver, ctrlName}          │   （发布到 assist topic，ctlKey 加密）
  ├──────────────────────────────────────────────►│
  │                                               │  校验：TTL 内？失败计数未超限？
  │  assist.accept {sessionId, expiresAt, perms}   │
  │◄──────────────────────────────────────────────┤   （epKey 加密；perms 初始全 false）
  │                                               │  端点 UI：横幅「正在被 X 协助」
  │  ← 会话建立：复用既有 cmd/evt 通道与命令集 →   │
  │  assist.close / 端点【立即终止】/ TTL 到期     │
  │◄─────────────────────────────────────────────►│  审计 session.end
```

### 4.5 攻击面与缓解

| 威胁 | 缓解 |
|---|---|
| 离线字典爆破密码 | 密码认证 topic（§4.2）——无密文可爆破 |
| 在线猜测 | 端点失败计数：同一会话 5 次失败 → 立即作废；TTL 10 分钟 |
| 重放 | 沿用 ±90s 时间窗 + 消息 ID 去重（10 分钟滚动表） |
| 中间人 | broker 只见密文；AAD 绑定 topic；密钥不经过 broker |
| 会话劫持 | `sessionId` 随机 + 每会话独立密钥，TTL 到期即失效 |
| 暴力枚举 topic | topic 需已知密码才能计算，枚举等价于猜密码 |
| 公共 broker 隐私 | 沿用 docs/14 §6 提示；生产建议自建 broker（本设计不强制） |

## 5. 与现有「二维码配对」的关系

| 模式 | 授权方式 | 生命周期 | 典型场景 |
|---|---|---|---|
| 二维码配对（v1.5，现有） | 物理在场互扫 | **永久互信** | 家人/自有设备长期守护 |
| **临时协助会话（v1.7，新增）** | 端点展示码 + 人工告知 | **一次性，TTL 10 分钟** | 临时求助（远程帮长辈设置） |

两者**共用同一套 MQTT E2EE 与命令集**，差异仅在**密钥来源与生命周期**。
实现上：会话建立时把 `PairedEndpoint(secret = sessionSecret)` 注入**内存态**（不落盘），
使既有 `sendTo` / `_send` / `_dispatch` 全链路**零改动复用**；端点侧 `_handleRaw`
改为**密钥环**（先试常驻配对码，再试活动会话密钥）。

## 6. 技术选型对比与决策

| 候选 | 会合 | 媒体 | 自建服务端 | 跨 NAT | 评价 |
|---|---|---|---|---|---|
| A 纯 P2P + 手动 SDP（QR 互扫） | 无（QR 交换 SDP） | WebRTC | **无** | 需同地两次扫码 | 真 serverless，但**不支持远程求助**（本需求核心场景） |
| **B MQTT 会合 + WebRTC 媒体** | **公共 MQTT（现有）** | WebRTC + 公共 STUN | **无**（TURN 可选） | ✅ | **选用**：复用现网、跨 NAT 可用、E2EE、媒体 P2P 低延迟 |
| C 自建 rendezvous + relay（RustDesk 式） | 自建 | 自建 | **需 VPS** | ✅ | 可控性最强，但违背「尽量无服务端」；作为可选升级路径 |
| D 全走 MQTT（不用 WebRTC） | 公共 MQTT | MQTT 传帧 | 无 | ✅ | 延迟/带宽不适合视频，仅够命令；作为无 TURN 时的降级 |

**决策：选 B。** 理由：

1. **零新增基础设施**——会合复用已配置的 MQTT，媒体复用已实现的 WebRTC；
2. **跨 NAT 可用**——MQTT 是出站 TCP，不受 NAT 入站限制；
3. **中继盲**——E2EE 在两端完成，broker 只见密文（与 RustDesk 同级）；
4. **降级路径清晰**——无 TURN 时视频降级语音/命令，遥控能力不受影响；
5. **升级路径保留**——若日后需要更强可控性，把会合从公共 broker 换到自建
   EMQX/Mosquitto（docs/14 §6 已列），**协议不变**。

### 8.1 S2 实现要点（踩坑记录）

**① 密钥不散落网络层。** `RcEndpointService` 只提供字节通道（`_MqttAssistTransport`
实现 `AssistTransport` 的 subscribe/unsubscribe/publishWire），密文由
`RcAssistHost` 加密后传入；会话密钥**不出** `assist_host.dart`。

**② 会合主题与配对主题命名空间隔离。** `_handleRaw` 首先按
`topic.startsWith(RcAssist.topicPrefix)` 分流 —— 协助通道不依赖本机配对码，
两者的密钥来源、生命周期、权限模型完全不同，混在一条分派链里必然出错。

**③ 业务命令的权限门控在托管内、执行在端点服务。** 会话建立后复用 v1 命令集：
`onWire` 解密 → `RcAssistCmd.isControl` 判定 → 业务命令走 `_onBusiness`
（会话未激活直接拒；`requiredPerm` 未登记即 `_denyAll` 失败关闭）→ 通过后
回调 `onCommand`（指向 `_dispatch`）。**门控与执行分离**，避免端点服务里
散落权限判断。

**④ 回执通道用 Zone 承载（`assistReplyZone`）。** 协助会话的对端**不是已配对
设备**，收不到 `sonicshield/v1/{deviceId}/evt`；执行层回执必须原路返回会合主题
（epKey 加密）。`_send()` 读 `Zone.current[assistReplyZone]` 决定通道 —— 用 Zone
而非实例标志位，是因为协助命令与配对命令可能**并发在途**（每个 await 都是交错
点），标志位会串台；Zone 随异步链自动传播，且不必给 `_dispatch` 每个调用点加参数。
漏掉这一步的症状是"命令确实执行了，但控制端毫无反应"，且不报任何错。

**⑤ 失败计数只统计"等待期解密失败"。** 两个反 DoS 细节：
- **同一密文重放不计失败**（`_seenWires` 按密文原文去重）：消息 ID 要解密后
  才能读到，而解密失败的报文恰恰是计失败数的那些 —— 只靠 ID 去重的话，
  重放一次抓到的密文 5 遍就能把会话锁死；
- **会话激活后的解密失败不计失败**：端点自己发布的 `accept` 报文会让 broker
  侧观察者得知会合主题，若这类垃圾报文也计数，攻击者可 spam 5 条锁死会话。
  锁死虽属失败关闭（只减权限不增权限），但白送一个拒绝服务面没有意义。

**⑥ 重连补订会合主题。** `refreshSubscriptions()` 除配对主题外，还会补订
进行中会话的会合主题 —— 与 BUG-013 同类：订阅集合不补齐，对端永远收不到回执。

### 8.2 S3 实现要点（踩坑记录）

**① 门控表必须放在协议层，两端共用。** `RcPermGate` 最初在 `RcAssistHost` 内。
S3 需要同一张"命令 → 所需权限位"映射来**灰化控制端按钮**，而端点侧需要它来
**拒绝越权命令**。两处各写一份必然漂移，漂移的后果是"按钮可点但命令被拒"
（体验损坏）或更糟的"按钮灰着但其实能发"（安全错觉）。因此上移到 `assist.dart`，
`RcAssistHost` 只做转发。

**② 控制台的命令通道必须抽象出来，否则会出现第二份命令面板。**
`RemoteConsoleTab` 原本直接依赖 `PairedEndpoint` + `sendTo`。协助会话的对端
**没有配对关系**，若复制一份适配，新增命令只加一边 → 功能必然漂移。
引入 `RcCommandChannel` 后，控制台对"配对/协助"完全无感。

**③ 一台设备可能**同时**托管会话又接入别人的会话 → 入站必须按主题精确路由。**
`_handleRaw` 里 `topic.startsWith(topicPrefix)` 只分流"是不是协助通道"，
还需再判定归属：`RcAssistHost.instance.session?.topic == topic` 才交给托管，
`AssistJoinClient.instance.topic == topic` 才交给接入客户端。
漏掉这层判定会把控制端的 `accept` 又投回端点自己。
（注意：同一台设备托管并接入**同一个**会合主题是无意义的 —— 此时
`accept` 会被路由回端点侧。这不是缺陷，正常使用不会出现。）

**④ `hello` 必须重试。** MQTT 的 `SUBSCRIBE` 生效有往返延迟，且端点可能刚生成
凭据（订阅尚未建立）。单发一次 `hello` 在真实网络上经常石沉大海，表现为
**"码是对的但一直连不上"** —— 这是最难排查的一类故障。端点侧对重复 `hello`
幂等（重发 `accept`），因此重试安全。生产间隔 1.5s，单测注入 1ms
（`helloRetryInterval` 字段）以免拖慢整个套件。

**⑤ 密码错误必须**表现为超时**，不能有可区分的失败信号。**
密码错 → 主题不同 → 端点根本收不到 `hello`。因此攻击者无法区分
"密码接近"与"端点离线"。这一性质由 `AJ-22` 锁定。

**⑥ 审计顺序不能依赖传输延迟。** `send()` 必须**先记"发出"再发布**；
若在发布完成后再记账，快通道（测试环回、局域网、broker 与端点同机）上
端点的回执会先落账，轨迹变成"先收到、后发出"，排障时把人带偏（BUG-032）。

**⑦ 权限变更要单独推送，不能搭业务回执的车。** 控制台按权限灰化按钮，
而权限是**对端随时可变**的。若只在收到业务回执时重建，端点单独放行权限时
按钮灰化会停留在旧值（BUG-030）。故 `RcCommandChannel` 增 `updates` 流。

### 8.3 已知可测性限制

`RcAssistHost` 与 `AssistSession` 的时间判断直接用 `DateTime.now()`，
因此 `testWidgets` 的 FakeAsync **只能虚拟化 Timer，无法推进倒计时**
（`tester.pump(Duration)` 瞬间返回，剩余时间几乎不变）。当前处理：
TTL 的真实推进由 `test/assist_host_test.dart` 的 AH-14/AH-15 用**真实延时**覆盖，
widget 测试只锁定渲染格式。若日后需要精确的假时钟测试，需注入 `DateTime Function()`
时钟源（同时改造 `AssistSession.expired/remaining`）。

## 10. 未决项

**功能待办**

1. **TOTP 二次验证**（对标 RustDesk 2FA）——v1.8 评估；
2. **局域网直连**（mDNS/UDP 广播，同网段可完全不经 broker）——可进一步「去服务端」；
3. **临时码口述友好性**——9 位数字是否再降为 6 位 + 校验位（需权衡熵）；
4. **会话内屏幕共享**——当前仅摄像头视频；屏幕共享涉及更高隐私风险，单独评估。

**验证待办（本轮未执行，边界见 docs/12 §14.5）**

5. **真机 ↔ 模拟器（两个独立 Android 进程）握手**——无真机接入；双模拟器 UI
   自动化在本机不可行（宿主持续重载导致 `System UI ANR`，且无深链只能盲点坐标）。
   **已用真实 broker 单机双连接集成测试替代覆盖**
   （`integration_test/assist_e2e_test.dart`，见 docs/12 §14.4.1），
   残余未覆盖维度仅「两个不同 Android 进程/机型」；
6. **对称 NAT 场景验证**（S5 验收项）——需真实移动网络双端；
7. **真实扬声器出声验证**——真实 broker 链路上已验到命令被端点接受并进入
   `_dispatch`；模拟器无有效音频输出，需真机；
8. **NFR-04 的 AOT 绝对验收**——性能套件本身已全绿（24/24 连续三次），但那是
   JIT 下的回归护栏；绝对验收文件 `integration_test/perf_nfr_test.dart` 已就绪，
   因沙箱拦截 profile/release 构建（黑名单程序 `reg.exe`）而未能执行
   （docs/12 §14.6）；
9. **`MT-01` 阈值口径**（BUG-034）——其 4000ms 严于 NFR-04 自身外推（5000ms），
   需决定是"对齐规范"还是"确认这是更严的内部目标"。
