## 二、本轮缺陷：下载节假日信息联动导入反击计划

### 2.1 现象

用户在设置页点「**一键更新节假日（联网）**」之后，**反击计划被整族重建**：原有任务被删除，
按新节假日表重新生成了一批任务。

### 2.2 三宗罪

| # | 罪状 | 说明 |
|---|---|---|
| ① | **未声明副作用** | 按钮文案只承诺"更新节假日表"，实际执行的是"重建反击计划" |
| ② | **不可逆数据损失** | 用户手工调过的任务（音量 / 时长 / 间隔 / 时段开关）被静默覆盖 |
| ③ | **职责错位** | 节假日表是**数据**，反击计划是**派生排期**；更新数据不该重算派生 |

### 2.3 根因

`lib/services/counter_plan_service.dart` 的 `refreshHolidays` 在写完覆盖表之后，**继续走**
`apply(..., replace: true)` —— 即"整族删除并重建"；该分支**未在任何文档/文案中声明**。

### 2.4 修复（A：副作用解耦）

```dart
Future<CounterApplyResult> refreshHolidays(
  Map<String, DayKind> autoOv, {
  DateTime? now,
}) async {
  final at = now ?? DateTime.now();
  await _store.setAutoOverrides(autoOv, at: at);   // ← 只写表
  if (autoOv.isEmpty) {
    return CounterApplyResult.ok2('已清除联网节假日表（回到内置表）');
  }
  return CounterApplyResult.ok2(
      '已更新节假日表（${autoOv.length} 天）；'
      '节假日暂停窗口即刻按新表生效，反击计划将在下次续算时按新表排期');
}
```

删掉了 `if (!_store.enabled)` 与 `loadPlan()` 两个分支。新表由**两条独立通路**生效：

| 通路 | 生效时机 | 影响面 |
|---|---|---|
| `BackgroundEngine.pausedAt`（**实时读表**） | **即刻** | 节假日暂停窗口按新表判定 |
| `refreshIfNeeded`（**续算**） | 下次续算 | 反击计划按新表排期 |

**节假日更新不再触碰任何反击任务。**

## 三、本轮主题 B：反击计划自动续算接线

### 3.1 问题（顺带发现的死代码）

`CounterPlanService.refreshIfNeeded()` 在生产代码里**一个调用方都没有** —— 是**死代码**。
后果：反击计划**物化窗口走完之后会静默停掉**（窗口外没有任何任务，也不会自动补），
用户看到的现象是"反击计划过一阵子就不响了"。

### 3.2 修复

新增 `BackgroundEngine.extendCounterPlan()`：

```dart
Future<void> extendCounterPlan() async {
  final store = CounterPlanStore(prefs);
  if (!store.enabled) return; // 未启用：无事可做，且省掉一次 DB 查询
  final svc = CounterPlanService(
    tasks: tasksRepo,
    store: store,
    resolveAudioIds: (ids) async =>
        resolvePresetAudioIds(await AssetRepository(db).listAll(), ids),
    replan: replan,
  );
  final r = await svc.refreshIfNeeded();
  if (r.taskCount > 0) {
    await logs.append(
      source: 'schedule',
      action: 'counterExtend',
      status: 'success',
      message: '反击计划自动续算：${r.message}',
    );
  }
}
```

并**接入两处**：引擎 `tick`（`Timer.periodic`）与**启动序列**（通道 B 唤醒后同样走这里）。

### 3.3 ⚠️ 顺序有语义：必须排在 `replan` 之前

```
await stepGuarded('executeDue(tick)', executeDue);
await stepGuarded('extendCounterPlan(tick)', extendCounterPlan);   // ← 先续算
final pending = await occs.pendingCountAfter(DateTime.now());
if (pending < SchedulerConfig.planExtendThreshold.inHours) {
  await stepGuarded('replan(tick)', replan);                        // ← 再重排
}
```

续算**只写 `tasks`**；计划条目由紧随其后的 `replan` 的 `occs.reconcile` 生成。
**反过来会让刚铺好的任务被当成"陈旧"再重排一遍**（重复劳动 + 抖动）。

## 四、测试锁

### 4.1 新增 6 例源码契约锁（`test/engine_reentrancy_test.dart`）

| 锁 | 判据 |
|---|---|
| `CEXT-00` | 抽取器锚定到正确的函数（防签名变更后**锁空转**） |
| `CEXT-01` | 续算必须被 `tick` 与启动序列**真正调用**（不是只有定义） |
| `CEXT-02` | 续算必须排在 `replan` **之前** |
| `CEXT-03` | 续算必须走 `replace: false`（只 upsert，绝不删历史） |
| `CEXT-04` | 节假日更新必须与反击计划**完全解耦**（不得 `apply(` / `deleteCounterTasks` / `refreshIfNeeded`） |
| `CEXT-90` | ★ **反面样本必须被判红、正面样本不得误报**（4 反面 + 2 正面 ⇒ 证明上面 4 条**非恒真**） |

### 4.2 既有锁改判

| 锁 | 旧判据 | 新判据 |
|---|---|---|
| `HU-12`（`test/holiday_update_service_test.dart`） | 未启用 → 存表不报错；启用 → **落库并重排** | **只写表** —— `replans == 0`、`deletedPlanIds` 为空、`upserted` 为空、提示语不含「反击计划已生效」 |
| `COV67-04`（`test/counter_plan_service_test.dart`） | 已启用但无计划本体 → 存表并提示 | 仍**只写表**（不重排）；断言语改为 `contains('已更新节假日表')` |

### 4.3 ⚠️ 抽取器踩坑（后果是「锁空转」）

既有 `functionBlock()` 只找"签名后第一个 `{`"，会把**具名参数** `{DateTime? now}` 误判成函数体 ——
**抽取到错误的体仍然判绿**。故新增 `functionBodyBlock()`：**先配对圆括号跳过参数表**，
再从 `)` 之后找第一个 `{`。

### 6.1 阈值下调留痕

- **原因**：本轮修缺陷时**净删除 5 行已被覆盖的生产代码**（`refreshHolidays` 的联动重建分支）。
- **不是测试退化**：功能层用例数 **2603 → 2609（+6）**，只增不减；未删任何用例、未削弱任何断言。

- **做法**：按 floor 同步下调 5 行，保住「**实测 − 8 行抖动余量**」纪律（12661 − 8 = 12653）。
- **同步三处**：`scripts/gates.sh`（默认值 + 注释）、`scripts/gates.ps1`（默认值 + 注释）、
