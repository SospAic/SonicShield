## 二、本轮缺陷：下载节假日信息联动导入反击计划

### 2.1 现象

用户在设置页点「**一键更新节假日（联网）**」之后，**反击计划被整族重建**：原有任务被删除，  
按新节假日表重新生成了一批任务。

### 2.2 三宗罪

| # | 罪状          | 说明                                   |
| - | ----------- | ------------------------------------ |
| ① | **未声明副作用**  | 按钮文案只承诺"更新节假日表"，实际执行的是"重建反击计划"       |
| ② | **不可逆数据损失** | 用户手工调过的任务（音量 / 时长 / 间隔 / 时段开关）被静默覆盖  |
| ③ | **职责错位**    | 节假日表是**数据**，反击计划是**派生排期**；更新数据不该重算派生 |

### 2.3 根因

`lib/services/counter_plan_service.dart` 的 `refreshHolidays` 在写完覆盖表之后，**继续走**  
`apply(..., replace: true)` —— 即"整族删除并重建"；该分支**未在任何文档/文案中声明**。

### 2.4 修复（A：副作用解耦）

```dart
Future<CounterApplyResult> refreshHolidays(
  Map<String, DayKind> autoOv, {
  DateTime? now,
}) async {
  final at = now ?? DateTime.now();
  await _store.setAutoOverrides(autoOv, at: at);   // ← 只写表
  if (autoOv.isEmpty) {
    return CounterApplyResult.ok2('已清除联网节假日表（回到内置表）');
  }
  return CounterApplyResult.ok2(
      '已更新节假日表（${autoOv.length} 天）；'
      '节假日暂停窗口即刻按新表生效，反击计划将在下次续算时按新表排期');
}
```

删掉了 `if (!_store.enabled)` 与 `loadPlan()` 两个分支。新表由**两条独立通路**生效：

| 通路                                    | 生效时机   | 影响面          |
| ------------------------------------- | ------ | ------------ |
| `BackgroundEngine.pausedAt`（**实时读表**） | **即刻** | 节假日暂停窗口按新表判定 |
| `refreshIfNeeded`（**续算**）             | 下次续算   | 反击计划按新表排期    |

**节假日更新不再触碰任何反击任务。**

## 三、本轮主题 B：反击计划自动续算接线

### 3.1 问题（顺带发现的死代码）

`CounterPlanService.refreshIfNeeded()` 在生产代码里**一个调用方都没有** —— 是**死代码**。  
后果：反击计划**物化窗口走完之后会静默停掉**（窗口外没有任何任务，也不会自动补），  
用户看到的现象是"反击计划过一阵子就不响了"。

### 3.2 修复

新增 `BackgroundEngine.extendCounterPlan()`：

```dart
Future<void> extendCounterPlan() async {
  final store = CounterPlanStore(prefs);
  if (!store.enabled) return; // 未启用：无事可做，且省掉一次 DB 查询
  final svc = CounterPlanService(
    tasks: tasksRepo,
    store: store,
    resolveAudioIds: (ids) async =>
        resolvePresetAudioIds(await AssetRepository(db).listAll(), ids),
    replan: replan,
  );
  final r = await svc.refreshIfNeeded();
  if (r.taskCount > 0) {
    await logs.append(
      source: 'schedule',
      action: 'counterExtend',
      status: 'success',
      message: '反击计划自动续算：${r.message}',
    );
  }
}
```

并**接入两处**：引擎 `tick`（`Timer.periodic`）与**启动序列**（通道 B 唤醒后同样走这里）。

### 3.3 ⚠️ 顺序有语义：必须排在 `replan` 之前

```
await stepGuarded('executeDue(tick)', executeDue);
await stepGuarded('extendCounterPlan(tick)', extendCounterPlan);   // ← 先续算
final pending = await occs.pendingCountAfter(DateTime.now());
if (pending < SchedulerConfig.planExtendThreshold.inHours) {
  await stepGuarded('replan(tick)', replan);                        // ← 再重排
}
```

续算**只写 `tasks`**；计划条目由紧随其后的 `replan` 的 `occs.reconcile` 生成。  
**反过来会让刚铺好的任务被当成"陈旧"再重排一遍**（重复劳动 + 抖动）。

### 4.3 ⚠️ 抽取器踩坑（后果是「锁空转」）

**为什么判为"偶发"而非"回归"**：

1. **失败形状**是"墙钟被拉长"（数值停在 ramp 中途），**不是**逻辑断言错；
2. **两次失败落在不同用例** ⇒ 竞态，而非确定性缺陷；
3. 该文件与其被测生产文件 `lib/services/playback_service.dart` **均不在本轮改动清单内**  
   （`git status --short` 只有 5 个文件：`background_engine.dart` / `counter_plan_service.dart` +

4. 该文件**头部自述**早已记录同类脆弱性（2026-10-04 门禁实测 `_rampUp` 末值仅 **0.363**），  
   并已为此把 `_playWallCeilingMs` 上界从 1000 放宽到 8000 —— 本次是同源问题在 `PA-05/PA-06`  
   上的另一处表现。

**处置（原）**：本轮**如实登记**（不冒充通过、也不掩盖）；门禁以**全量复跑全绿**为准。

**🔧 收口补修（2026-10-08，用户拍板「修 PA-05/PA-06」）**：根因**不是** `setVolume` 慢
（替身无延迟），而是**定时器本身被饿死** —— 门禁 `--coverage` + 整层默认并发（30+ 测试进程
超订）下 `Future.delayed(5ms)` 实测要 **~0.5s** 才回调（**≈100×**），渐强 40 步要 **~20s+**；
而 `play()` 返回只代表**窗口**到点，**不代表**渐强爬到终点。修法 = 把「睡固定时长后取末值」
改为**有界轮询**到终点真正落地：

```dart
Future<void> _waitUntil(
  bool Function() cond, {
  Duration timeout = const Duration(seconds: 120),
}) async {
  final deadline = DateTime.now().add(timeout);
  while (!cond() && DateTime.now().isBefore(deadline)) {
    await Future<void>.delayed(const Duration(milliseconds: 5));
  }
}
```

- `PA-05`：删掉原来的 `rampDeadline` 5 秒内联循环 ⇒ `await _waitUntil(() => audio.volumes.last >= 0.79);`
- `PA-06`：原来**无任何轮询** ⇒ 补 `await _waitUntil(() => audio.volumes.last >= 0.99);` 后再断言 `closeTo(1.0, 1e-9)`
- ⚠️ **上限为什么是 120s**：先取 20s，**门禁实测仍假红**（20s 只爬到 **0.743** / 37 步）⇒ 按实测再放 ~3× 余量。
  它只是**反挂死护栏**、**不是**业务判据：到点仍未满足**照常失败**并由 `expect` 报出**真实末值**。
  **业务判据一字未放宽**（终点仍须兑现目标音量）。
- ⚠️ **`group()` 不能带 `timeout:`**：`flutter_test` 的 `group()` **无**该具名参数
  （`flutter_test/lib/src/test_compat.dart:208`）⇒ 写 `group(..., timeout: Timeout(...))`
  **编译不过**（`Error: No named parameter with the name 'timeout'.`）。正解 = **文件级**
  `@Timeout(Duration(minutes: 3))` + `library;`（同仓既有写法：`test/bi_gap_closure2_test.dart:22`、
  `test/call_service_webrtc_test.dart:42`）。⚠️ 该错误的形状是**整个文件加载失败**
  （`Compilation failed for testPath=…`），与"断言红了"完全不同，勿误读。

### 12.4 本提交的推送方式（`github.com` 隧道不通时的替代路径）

本轮 `git push` 连续 **8 次**失败（`CONNECT tunnel failed, response 502` /
`schannel: server closed abruptly` / `Empty reply from server`）。诊断：

```
api.github.com  经代理  http=200     ← 通
github.com      经代理  http=000     ← 不通
github.com      直连    http=000     ← 也不通
```

⇒ 改走 **GitHub Git Data API**（`gh api` → `api.github.com`）：blob → tree → commit 逐级
**校验 SHA**，最后才 `PATCH /git/refs/heads/main`。因 git 对象是**内容寻址**，
构造出的 commit 与本地 **SHA 逐位相同**（`d6f5720…`）⇒ 远端拿到同一个 commit，
**零分叉**，本地 `git status -sb` 直接 `## main...origin/main`。
✅ 该方式**会正常触发 workflow**（run `37728710126` 即时 `in_progress`）。
