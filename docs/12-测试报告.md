### 11.3 BUG-022 修复验证

**根因**：后台引擎运行在 `flutter_background_service` 的**独立 FlutterEngine**，
与主 isolate 不是同一个插件实例 —— `AppDatabase` 的进程内静态单例 `_instance`
只能在一个引擎内去重，两个引擎各持**一条独立原生连接**写同一数据库文件，
默认 rollback journal 模式下写锁互斥，`BEGIN EXCLUSIVE` 直接报
`SQLITE_BUSY`。

**修复**（`AppDatabase._onConfigure`，连接级 PRAGMA）：

| PRAGMA | 作用 |
|---|---|
| `journal_mode = WAL` | 读不阻塞写、写不阻塞读；两个连接可并发 |
| `busy_timeout = 5000` | 写锁冲突时**等待**而非立即失败 |
| `synchronous = NORMAL` | WAL 下不必每次提交 fsync，兼顾吞吐与断电安全 |

**验证状态**：
- **已通过**：`test/` 全量 115/115（含依赖真实 SQLite 的 v2_features 套件），
  说明 PRAGMA 变更未破坏任何既有 DB 行为；
- **待补**：设备端冷启动复现（需在新 APK 上连续冷启并抓
  `[sonic_shield][engine]` 日志确认 `SQLITE_BUSY` 消失）。
  该 PRAGMA 组合是 WAL 场景的标准做法，但**未实测前不作为"已修复"结论**。

### 13.3 本轮暴露的设计问题（测试驱动修正）

1. **重放计入失败 → DoS 面**（AH-12）：消息 ID 要解密后才能读到，而"解密失败"
   恰恰就是计失败数的那些报文 —— 只按 ID 去重挡不住重放。修正：新增按**密文原文**
   去重的 `_seenWires`（FIFO 上限 512），重放直接忽略、不计数。
2. **激活后垃圾计入失败 → DoS 面**（AH-13）：端点自己发布的 `accept` 会让 broker
   观察者得知会合主题。修正：`phase == active` 后的解密失败静默丢弃，不消耗失败额度。
3. **回执通道错位**（AH-43/44）：协助会话的对端不是已配对设备，`_send()` 的既有
   路径会把回执发到 `{deviceId}/evt` 并静默丢弃。修正：用 `assistReplyZone`（Zone）
   承载通道标记 —— 不用实例标志位是因为协助命令与配对命令可能**并发在途**
   （每个 `await` 都是交错点），标志位会串台。
4. **`Duration.zero` TTL 不可用于构造"已过期"**（AH-14）：`expiresAt` 与随后的
   `DateTime.now()` 会落在**同一毫秒**，`isAfter` 为 false（Windows 毫秒级时钟）。
   测试改用真实短 TTL + 延时。

7. `sound.play`（未放行）→ 端点回 `rc.ack{ok:false}`（**显式拒绝而非静默**）；
8. 控制端审计同时记录了"发出的 ping"与"端点的拒绝回执"；
9. `host.grant(media)` → 经 `assist.perm` 同步到控制端，`allows(sound.play)` 转为 true；
10. 控制端挂断 → 端点会话终止（`host.session == null`）。

> **残余边界**：两条连接同处一个进程，因此未覆盖"两个不同 Android 进程/机型"
> 这一维度（例如跨机型的时钟偏差、厂商后台策略差异）。该维度仍需真机补测。

### 15.2 重大环境纠正：`env` 不是 `env`（推翻了上一轮的核心阻塞结论）

**上一轮的结论**（HANDOVER §7、docs/17 §12.6）：
> `flutter build apk --profile` 与 `flutter drive --profile` 被沙箱 SIGTERM
> （工具链调用黑名单程序 `reg.exe`），故 AOT 性能验收在本环境无法执行。

**本轮实测证伪**。真正的原因是**上一轮所有命令都写成**：
```bash
env "PROGRAMFILES(X86)=C:\Program Files (x86)" flutter test ...
```
而 PATH 上**名为 `env` 的第一个可执行文件**是：
```
/c/Users/sospa/WBProfilesAI/bdd2/.local/bin/env
```
其内容是一段 **uv 风格的 PATH 修补脚本**（设计用途是 `source`，不是执行）：
```sh
#!/bin/sh
case ":${PATH}:" in
    *:"$HOME/.local/bin":*) ;;
    *) export PATH="$HOME/.local/bin:$PATH" ;;
esac
```
它被当作**程序**调用时，只是在自己的子 shell 里改了 `PATH` 然后退出，
**不会把参数转发给任何命令** → 退出码 0、无输出、**目标命令根本没跑**。

**证据（本轮实测，三条对照）**：

| 命令 | 耗时 | 输出 | 说明 |
|---|---|---|---|
| `flutter analyze` | **29.7s** | `No issues found!` | 真正执行了 |
| `env "PROGRAMFILES(X86)=C:\Program Files (x86)" flutter analyze` | **0.35s** | 无 | 被吞，未执行 |
| `env "FOO=bar" bash -c 'echo env-works-$FOO'` | ~0s | **无** | 连 `echo` 都没执行 → 坐实 `env` 本身失效 |

**正确做法**：
- **直接用 `/usr/bin/env`**（绝对路径绕过同名脚本），或
- **完全不包装**：本机环境中宿主已注入 `ProgramFiles(x86)=C:\Program Files (x86)`，
  裸跑 `flutter test` / `flutter analyze` 均正常（本轮全部门禁都是裸跑取得的）。

1. ~~"profile/release 构建被沙箱拦截"~~ —— 本轮 `flutter build apk --profile`

> **诚实边界**：无法追溯上一轮究竟是被沙箱杀掉，还是被 `env` 吞掉 ——

### 15.4 BUG-035（P2）设备上日志写入吞吐不达标 → 已修

**发现**：AOT 首跑即暴露 `exec_logs 5000 条写入 + recent` = **7755ms / 预算 3000ms**
（超标 2.6×），且**两次复跑位级一致（均 7755ms）** → 稳定、可复现，**不是噪声**。
JIT 套件测不出来，因为它跑在 `sqflite_common_ffi` 的**内存库**上，没有平台通道。

**根因（交叉验证得出，非猜测）**：

| 用例 | 调用次数 | 实测 | **每次调用成本** |
|---|---|---|---|
| exec_logs 5000 条写入 | 5000 | 7755ms | **1.55ms** |
| 任务 CRUD 500（upsert+get） | 1000 | 1477ms | **1.48ms** |

两个**完全不同的负载**，每次调用成本却一致 → 瓶颈是
**每次 sqflite 调用的一次 `Dart → 平台通道 → 原生 SQLite` 往返（≈1.5ms）**，
而不是磁盘 I/O、也不是索引缺失（`idx_logs_created` 已存在）、
也不是 PRAGMA（WAL + `synchronous=NORMAL` 已启用）。

**修复**：`LogRepository` 新增 `appendMany(Iterable<LogRecord>)`，
用 `batch()` 把整批压成**一次**平台调用（范式与既有
`OccurrenceRepository.commitAll` 一致；同批 `created_at` 取同一时间戳）。

**效果（AOT 实测）**：**7036ms → 275ms，25.6×**；原 ≤3000ms 预算从"不可达"
变为**10.9× 余量达标**。

**口径处理**：逐条路径保留为**设备特性记录 + 数量级护栏**（实测 1.41–1.55ms/次，
护栏 4ms/次），不当作缺陷 —— 生产路径每次执行只写 1–2 条日志，1.5ms 无影响；
批量路径才承担原预算。

**新增回归测试**（`test/db_repository_test.dart`，2 例）：
`appendMany 批量写入：条数与字段完整`、`appendMany 空集合不产生任何写入`。

### 16.4 BUG-038（P3）`_pendingAcks` 对专用事件类命令无界增长 —— 已修

### 17.2 本轮实现（新增 / 修正）

**① 条件层新增「通话中不执行」（安全默认开启）**

行业依据：MacroDroid 的 *Constraint: Call State*、Tasker 的 *Call* 状态，
都把通话状态作为一等条件。

**关键设计：用 `AudioManager.mode` 而不是 `TelephonyManager`。**
读通话状态若走 `TelephonyManager` 需要 `READ_PHONE_STATE` 运行时权限 ——
一个"定时放音"工具没有任何理由申请"读取通话状态与手机身份"（docs/08 最小权限）。
`AudioManager.getMode()` 是公开 API、**零权限**，且对 VoIP/视频通话
（`MODE_IN_COMMUNICATION`）同样有效，覆盖面比只认蜂窝通话的 TelephonyManager 更广。

**默认开启且对老任务生效**：`TaskCondition` 缺键时 `skipInCall` 取 `true`；
引擎对 `condition == null` 的**历史任务**用 `const TaskCondition()` 兜底
（而不是直接放行），因此不存在"没配过条件就漏掉通话保护"的洞。
使用者在编辑器显式关闭时会落库 `skipInCall=false` 覆盖默认值。

**② 条件层新增「仅 Wi-Fi 下执行」**

不引入 `connectivity_plus`（本项目有 AGP9 插件兼容矩阵的血泪史），
改为**扩展自有的 `native_bridge` 本地插件**用 `ConnectivityManager` +
`NetworkCapabilities` 实现（后者替代 API 29 起废弃的 `NetworkInfo.getType()`）。
仅新增 `ACCESS_NETWORK_STATE`（normal 权限，安装即授予、无运行时弹窗）。

**③ 音频焦点修正（media 通道不再打断他人音乐）**

原实现对两个通道都用 `AndroidAudioFocusGainType.gain`（**永久抢占**）。
对 alarm 合理（必须被听见），但对 media 是错的：会让使用者正在听的音乐
**暂停再恢复**，是明显的体验损伤。依据 Android 官方《管理音频焦点》，
短提示音应请求 `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`（他人**降低音量继续播放**）。

已抽成 `PlaybackService.focusGainFor(channel)` 纯函数并加测试锁定 ——
这条决策藏在 `AudioSession.configure` 的参数里，**改错了不会编译报错、
也不会运行期抛异常**，只会"听起来很烦"，没有自动化信号能捕获。

**④ 审计原因精确化**

原 `conditionFailed` 返回 `c.describe()`（"配了哪些条件"）。改为
`TaskCondition.firstUnmet()` 返回**首个未满足条件**（"这次为什么没执行"）。
同时删除了 `evaluate()` 上那个永远无法写入的 `reasonOut` 参数（死参数）。

## 18. 第九轮（2026-09-18）：v1.7 条件层的**设备端验证**

### 18.1 本轮要解决的问题

第八轮给条件层加了两个新原生桥接方法（Kotlin `callState` / `networkType`，
支撑 `skipInCall` / `requireWifi`），但当轮**只验证到编译通过**
（`NativeBridgePlugin.class` 是新鲜产物）。编译通过 ≠ 运行正确：

| 编译验证覆盖不到的失败模式 | 后果 |
|---|---|
| Dart 侧 `_invoke('callState')` 与 Kotlin 侧 `"callState" ->` 字符串不一致 | `notImplemented` → `_invoke` 的 `PlatformException` 分支**静默返回 null** → "通话中不执行"这条安全护栏**静默失效**（永远不会拦） |
| `networkType` 返回值不在文档枚举内（Kotlin 会返回 `vpn`，Dart 文档没写） | `isOnWifi()` 判定语义无书面依据，后续维护者按文档改代码即引入漂移 |

| 读取通话状态其实需要权限 | 与 docs/08 最小权限承诺冲突 |

这类"每一端自己都对、链路却是断的"缺陷，单测与 mock 都发现不了（各部件自身都对），

### 18.7 BUG-040（P3，已修）：`networkType()` 的 Dart 契约漏了 `vpn`

Kotlin 实现会返回 `vpn`（`TRANSPORT_VPN` 分支），而 Dart 侧 `networkType()`
的文档注释只列了 `wifi / cellular / ethernet / none / other / unknown` 六种。
契约与实现不一致的后果是：后续维护者按文档理解 `isOnWifi()`，会误以为
"返回值只可能是这六种"，从而对 `vpn` 场景做出错误推断。

### 19.2 方法一：用模拟器内置虚拟 AP 制造 Wi-Fi（可复用技巧）

AVD 自带一个开放虚拟热点 `AndroidWifi`，无需真机即可切换网络类型：

```bash
adb -s emulator-5554 shell cmd wifi list-networks      # 可见 AndroidWifi (open)
adb -s emulator-5554 shell cmd wifi connect-network AndroidWifi open
adb -s emulator-5554 shell dumpsys connectivity | grep -A2 "Active default network"
# → Active default network: 101
#   NetworkAgentInfo{network{101} ni{WIFI CONNECTED} Transports: WIFI}
adb -s emulator-5554 shell svc wifi disable            # 回落：100（MOBILE[NR]）
```

> 顺带解释第九轮的一个观察：模拟器的"移动网络"跑在 `eth0` 接口上，
> 却报告 `TRANSPORT_CELLULAR`（`ni{MOBILE[NR] CONNECTED extra: epc.tmobile.com}`），
> 所以 `networkType()` 给的是 `cellular` 而不是 `ethernet`。

**同一套设备端用例跑三次**，构成 A→B→A 往返（每次都 `+6 All tests passed!`）：

| 运行 | 活跃网络 | `networkType()` | `isOnWifi()` | `firstUnmet()` |
|---|---|---|---|---|
| R1 移动网络 | `100` MOBILE[NR] | `cellular` | `false` | `不在 Wi-Fi 下` |
| R2 **Wi-Fi** | `101` WIFI | **`wifi`** | **`true`** | **`null`**（全部满足） |
| R3 关 Wi-Fi 回落 | `100` MOBILE[NR] | `cellular` | `false` | `不在 Wi-Fi 下` |

R2 证明 `wifi` 分支成立；R3 证明取值**跟着真实网络状态走**，
而不是被某种缓存或一次性状态污染。

### 19.3 方法二：`NativeBridge` 的宿主机契约回归锁

第九轮把桥接方法拿到设备上跑通了，但那只是**一次性证据**，不是回归锁 ——
而且设备端测试只在有模拟器时才跑。日常 `flutter test` 完全不会碰它。

新增 `test/native_bridge_test.dart`（39 例），用
`TestDefaultBinaryMessenger.setMockMethodCallHandler` 装一个可编程的"原生端"，
分三层锁定：

| 层 | 锁什么 | 为什么 |
|---|---|---|
| **字面量** | 通道 `sonic_shield/native` + 方法名 `callState` / `networkType` | 方法名拼错 → `notImplemented` → `MissingPluginException` → **静默 null** → 约束失效。等设备上才发现，代价太高 |
| **契约** | 每个方法在「有值 / 返回 null / 抛异常 / 无实现」四种输入下的返回值 | 这些分支此前**一行都没测过** |
| **后果** | 桥的读数 × `TaskCondition` 的最终决策 | 用户可见面是"拦不拦"，不是"返回什么" |

顺带补齐既有方法（`exactAlarmSupported` / `setExactAlarms` / `serviceShouldRun` /
`isIgnoringBatteryOptimizations` / `setVolume`）的降级默认值 —— 同样是零覆盖的静默降级面。

### 19.4 BUG-041（P2，已修）：`isOnWifi()` 把"无法判定"当成了"不满足"

这是**写测试时发现的真实缺陷**（不是测试写错）。

`networkType()` 的 `unknown` 语义是**"无法判定"**：原生侧在
`ConnectivityManager` 取不到、或拿到了活跃网络却读不出 capabilities 时返回它；
桥不可用时 Dart 侧也回落到它。而原实现是：

```dart
static Future<bool?> isOnWifi() async {
  final t = await _invoke<String>('networkType');
  if (t == null) return null;
  return t == 'wifi';        // ← unknown 落到这里 → false
}
```

`unknown` → `false`。而 `false` 在条件层的含义是**"确定不在 Wi-Fi 下"** →
任务被拦下，审计里写下 `不在 Wi-Fi 下` —— **一个我们其实并不知道的原因**。

这直接违反 `TaskCondition` 类文档写明的既有约定：

> `inCall` / `onWifi` 传 `null` 表示本平台无法判定……此时按"条件满足"处理……
> 这样不会因为某个平台读不到状态就把全部自动化静默停掉。

即：**"读不到"被误报成了"不满足"**，正好踩中该约定要避免的坑。
触发条件不常见（capabilities 读取失败），但一旦触发就是
**静默跳过自动化 + 错误审计原因** —— 两者都是最难排查的形态。

**修复**：

```dart
if (t == null || t == 'unknown') return null;   // 无法判定 → 调用方按"满足"处理
return t == 'wifi';
```

同时把 `none` 与 `unknown` 的差别写进文档：`none` 是"确实没有活跃网络"这个
**确定状态**（→ `false`，拦下是对的）；`unknown` 是"读不出来"（→ `null`）。

### 19.5 回归锁的证伪（三个探针，全部确认"能失败"）

按项目既有纪律，新锁必须证明不是恒真断言：

| 探针 | 临时改动 | 实测结果 |
|---|---|---|
| **A** | `isOnWifi()` 的 `null` 分支改为 `return false` | **3 例失败**：`Expected: null / Actual: <false>`（"无法判定→null"、"桥异常→null"、串联"桥读不到不拦"） |
| **B** | `isInCall()` 方法名 `callState` → `callStateX` | **NB-H01 失败**：`Expected: ['callState'] / Actual: ['callStateX']` |
| **C** | `isOnWifi()` 的 `unknown` 分支改回旧行为 `return false` | **2 例失败**：`Expected: null / Actual: <false>`；串联用例 `Expected: null / Actual: '不在 Wi-Fi 下'` ← **把 BUG-041 的用户可见后果从推理变成了实测** |

## 20. 第十一轮（2026-09-18）：`TaskRepository.upsertMany`（BUG-042）+ AOT 门禁归一化（BUG-043）

### 20.1 任务选取

取 docs/17 §17.7 第 5 项的后半句：**`TaskRepository` 无批量 API（AOT CRUD 余量 1.3×）**。
这是 BUG-035（日志写入）修好之后，**唯一还在"每次调用 = 一次平台通道往返"模式下的
真实批量写入路径**。

### 20.2 缺陷实质：不是"慢"，是"要么全成、要么全不成"

`upsertMany` 的两个收益里，**原子性比速度更重要**：

- 速度：500 条从 500 次往返压到 **1 次**；
- 原子性：旧实现是 `for (…) await repo.upsert(t)`，**中途失败会留下半批数据**。
  使用者在设置页看到"导入失败"，回任务列表却发现**已经多了一截任务** ——
  而且这些"半截任务"是**启用状态**的，会真的开始放音。
  这是可观察的错误状态，不只是性能问题。

### 20.3 实现

`lib/data/repositories/task_repository.dart`：

- 抽出 `static Map<String, Object?> _row(Task t)`，`upsert` 与 `upsertMany` 共用，
  **避免两条路径的行映射漂移**（`trigger_json`/`action_json`/`asset_ids` 三处编码）；
- 新增 `upsertMany(Iterable<Task>)`：`db.batch()` 累积 → **一次** `commit(noResult: true)`；
  空集合直接 return，**不产生任何数据库操作**。

真实调用方（唯一）在 `lib/features/settings/settings_screen.dart` 的任务导入流程：
原来是逐条 `await repo.upsert(task)` 循环，现改为先解析到 `final parsed = <Task>[]`
再 `await repo.upsertMany(parsed)`。

### 20.4 新增回归锁（`test/db_repository_test.dart`，+5 例）

| 用例 | 锁的是什么 |
|---|---|
| 批量写入：条数与字段完整 | 批量路径的字段映射与逐条**一致** |
| 保留条件层 JSON（含新字段） | `requireWifi`/`skipInCall` 经批量路径不丢 |
| 空集合不产生任何写入 | 空导入不误伤既有数据 |
| 同批重复 id 幂等 | `ConflictAlgorithm.replace` 语义在批内成立 |
| **原子性：提交前失败不留下半批数据** | **BUG-042 的核心断言** |

原子性用例需要一个"在**行映射阶段**抛错"的注入点。做法是新增
`class _ExplodingTask extends Task` 覆写 `toRow() => throw StateError('boom')`：
批次已组好、但**尚未 `commit()`** —— 正好落在"要么全成、要么全不成"的临界位置。

> 注入点选择很关键：若在 `commit()` **之后**注入失败，测试就变成恒真（本来就已经提交了）。

### 20.5 证伪：确认原子性锁**真的会失败**

把 `upsertMany` 临时改回逐条 `await insert()` 循环，实测：

### 20.7 BUG-043（P2，已修）：`任务 CRUD 500 次` 是**冷启必红**的假门禁

**现象**：本轮第一次 AOT 跑（模拟器**冷启**后首跑）

```
[NFR-AOT] 任务 CRUD 500 次: 3340ms / 预算 2000ms → OVER   ❌
```

**排查**（先怀疑测量，别急着怪机器）：

| 证据 | 冷启 | 热机 | 上一轮记录 |
|---|---|---|---|
| 每次平台往返（`exec_logs` 逐条路径实测） | 2475µs | **1565µs** | 1550µs |
| 任务 CRUD 500 次 | 3340ms | 1764ms | 1477–1679ms |

- **同一台机器、同一份 APK**，只是模拟器冷暖不同；
- 关键交叉证据：**我本轮没有改动的** `exec_logs` 逐条路径**同步**从 1.55ms/次
  劣化到 2.475ms/次（1.6×）—— 说明是**机器级**的整体劣化，不是任务路径的代码回归；
- 热机复跑 1764ms 落在上一轮记录的区间内，**代码无回归**。

**根因**：逐条 DB 路径的成本 **∝ 平台通道往返次数**，而单次往返成本随机器状态浮动
（1.6×）。而 `任务 CRUD 500 次` 的 2000ms 预算，在热机下余量仅 **1.13×** ——
**任何"绝对 ms"预算在这条路径上都是冷启必红**。这与 BUG-034/036 同源：
**规范没错，是阈值口径与测量条件不匹配**。

**修法（自归一化，而非放宽绝对值）**：把基准测量提到最前，用**同一次运行内**实测的
每次往返成本做基准，逐条路径的预算一律改为

```
预算 = 本次往返成本 × 调用次数 × 3
```

- 与机器冷暖**解耦**，同时仍能抓**结构性回归**（每次调用多一次往返 = 工作量翻倍 → 超 3× 余量）；
- 基准行自身**不**用归一化预算（否则等于"3× 自己"、恒真），保留 4ms/次 绝对护栏。

**验证**：归一化后复跑，该次运行每次往返 **2587µs —— 比冷启那次（2475µs）还慢**，
`任务 CRUD 500 次` 2833ms 若按旧预算仍是 OVER，而归一化后预算 7762ms → **PASS**。
即"旧门禁会红的条件下，新门禁不再红"。

### 20.9 本轮经验（可复用）

- **批量 API 的第一收益是原子性，第二才是速度**。逐条循环写一半失败会留下

- **证伪的注入点必须落在"修复所改变的那个瞬间"**：原子性要注入在 `commit()` **之前**，

- **性能门禁的"绝对值"只对纯计算成立**。凡是成本 ∝ 平台通道往返次数的路径，
  预算都必须**归一化到同一次运行的实测基准**，否则门禁会随机器状态（冷启/热机/内存压力）
  红绿翻转。**判定一个 AOT 红灯，先看同一次运行里"你没改过的那条路径"有没有同步劣化**
  —— 那是区分"代码回归"与"机器状态"最省事的交叉证据。
- 冷启模拟器（`-no-snapshot-save`）会**系统性**抬高单次往返成本约 1.6×；
  性能测量若在意绝对值，应**先热机再测**，或直接归一化。

## 21. 第十二轮（2026-09-18）：条件层**每轮复用**（BUG-044）+ 设备冒烟测试复活（BUG-045）

### 21.1 任务选取

取 §20.10 第 5 项的残余部分：**条件评估 ≈4ms/任务（量大时应改为每轮复用）**。
这是待办清单里**唯一非硬件阻塞**的项（其余 4 项都缺真机/真实网络）。

### 21.2 缺陷实质：成本随任务数线性增长

一次条件评估要读 4 次平台状态（电量 / 充电 / 通话 / 网络），
每次都是一次**平台通道往返**（设备上 ≈1.5–2.9ms，BUG-035/BUG-042 已交叉验证）。

调度引擎的一轮 `executeDue()` 会遍历**所有**到期计划，于是：

| 一轮到期任务数 | 平台往返次数 | 单轮开销（按 2.9ms/次） |
|---|---|---|
| 1 | 4 | ≈12ms |
| 50 | **200** | **≈580ms** |
| 500 | **2000** | **≈5.8s** |

单任务看只有 ≈4ms（"可忽略"的由来），但**随 N 线性增长**，
而且这些开销**全部花在重复读取同一个物理环境上**。

### 21.3 实现：把"读平台"与"判定条件"解耦

新增 `lib/services/condition_env.dart`：

- `RoundConditionEnv` —— 一轮内的环境快照缓存，**惰性**（首次需要时才读）；
- 缓存的是 **Future 而不是结果值**（见 §21.7 的自我证伪）。

`lib/domain/models/condition.dart`：

- 新增 `ConditionEnv` 值对象（电量/充电/通话/网络四个**平台来源**输入）；
- 新增 `TaskCondition.firstUnmetIn(ConditionEnv, {required DateTime now})`，
  **判定逻辑完全复用 `firstUnmet`**（不存在"两条路径判得不一样"的可能）。

`lib/services/background_engine.dart`：

- 原 `conditionFailed(task)`（每次自己读平台）拆成
  `readConditionEnv()`（读平台）+ `conditionFailedIn(task, env)`（纯判定）；
- `executeDue()` 与 `onSoundEvent()` 两个**遍历循环**各持一个
  `RoundConditionEnv`，轮内所有任务复用同一快照；
- `runNow`（单任务路径）直接读一次，无需缓存。

**`now` 刻意不进快照**：它是本地时钟（无平台通道开销），
保持实时取值让时段窗口判定更准，且不增加任何成本。

### 21.4 新增回归锁（`test/condition_env_test.dart`，12 例）

| 组 | 锁的是什么 |
|---|---|
| 每轮只读一次 | 取 N 次只触发 1 次读取；同一实例；**惰性**（不取值则零读取）；**并发在途也只读一次** |
| `ConditionEnv` 默认值 | 逐字复刻改造前引擎初值（100/false/null/null），**行为不得顺手改变** |
| 两条路径等价 | 8 条件 × 8 环境 = **64 组穷举**，`firstUnmetIn` 与 `firstUnmet` 结论必须一致 |
| `now` 不进快照 | 同一快照配不同 `now` → 时段窗口内外正确翻转 |
| 判定优先级 | 通话中优先于其它原因被报出 |

**关键设计**：`RoundConditionEnv.readCount` 是"每轮只读一次"这一性质的
**可断言出口** —— 没有它，这个优化只能靠读代码相信，无法写回归锁。

### 21.5 证伪：确认复用锁**真的会失败**


### 21.6 AOT 实测（真实平台读取，`flutter drive --profile`）

### 23.2 BUG-047（P2，已修）：60 条预置音效**逐条写入**，且失败留下半套库

| 位置 | 改造前 | 后果 |
|---|---|---|
| `_importPresets()` | 循环内 `await db.insert(...)` × **60** | ①60 次平台往返（每次 ≈1.5ms）；②第 k 条失败 → 前面 k−1 条**已落库**，界面却提示"导入失败" |
| `_import()`（本地导入） | 逐条 `copy + insert` | 中途失败留下**孤儿文件 + 半批记录** |
| `_listAssets()` / 删除按钮 | 直接 `db.query` / `db.delete` | `AssetRepository` **已存在却只有端点服务在用**，界面自成一套（表结构/行映射两处漂移风险） |

1. **`AssetRepository.upsertMany`**（`batch()` 单事务 / **单次往返**）——
   与 `TaskRepository.upsertMany` / `LogRepository.appendMany` 同一范式；
   空集合直接返回，不开事务。
2. **`AudioAsset.toRow()`**：`upsert` / `upsertMany` 共用同一份行映射（防漂移），
   并把注入点暴露出来（见 23.4 探针 A）。
3. **`AssetRepository.nameSet()`**：只取 `name` 一列，作为预置库导入的**幂等判据**。
4. **新增 `lib/services/preset_import.dart`（`AssetLibraryImporter`）**：
   幂等跳过 → 全部落盘 → **一次**写库 → 失败回滚（库内零新增 + 清理已落盘文件）。
   抽出来的理由：界面依赖 `FilePicker` / `rootBundle` / `path_provider`，
   宿主机跑不起来 —— 而"失败会不会留下半套库"**恰恰是唯一值得写回归锁的性质**。
5. 界面改为**只经 `AssetRepository`**（新增 `assetRepoProvider`）：
   列表用 `listAll()` 返回**强类型** `AudioAsset`（UI 不再自己 `jsonDecode(tags)`）；
   删除改为**先删记录、再删文件**（反过来会留下指向不存在文件的记录，点试听即报错）。
6. `_importer(repo, {existingNames})`：**幂等跳过是可选参数** ——
   预置库传 `repo.nameSet`，本地导入不传（同名可多份，与改造前行为一致）。

### 24.3 转向：BUG-048（P2）—— `sound.play` 的点名被静默替换

真机受阻后，本轮取 §23.7 第 7 项（`rc.assets` / `rc.presets` 无 UI 消费）。
审计该链路时发现端点侧一个**更实质的缺陷**。

协议把 `sound.play` 的 payload 声明为
`{preset|assetId|category, volume, durationSec, loop}`（`RcCmd.soundPlay`），
但 `endpoint_service.dart` 的 `_playRemote` 此前实现是：

```dart
final category = msg.payload['category'] as String?;   // assetId / preset 被丢弃
var path = await _resolvePreset(category);
path ??= await _anyAssetPath();                        // 解析不到 → 库里最新一条
```

两个**用户可见的静默错误**：

| # | 现象 | 后果 |
|---|---|---|
| 1 | `assetId` / `preset` **完全被忽略** | 控制器点名播 A，端点播**另一段声音**，回执仍 `ok=true` |
| 2 | 点名分类无匹配音源时**静默回落**到任意一条 | 点"闹钟"却响起敲击声 |

> 与 BUG-041（`unknown` 被当成 `false`）同属一类：
> **无法满足请求时必须让失败可见，而不是悄悄换一个能满足的结果。**
>
> 值得记的是它的**隐蔽性**：`assist_host_test.dart` 里有一条用例
> 发送 `sound.play {assetId: 'a1'}` 并通过 —— 但它走的是 `host.onCommand`
> 注入点（只验权限门控），**从未到达 `_playRemote`**。于是"两端各自都有测试、
> 链路却是断的"。

### 24.4 修复

| 层 | 内容 |
|---|---|
| 新增 `lib/remote/remote_playback.dart` | `PlaybackSelector`（解析 payload，优先级 `assetId` > `preset` > `category`；空串/非字符串视为未点名）+ `resolvePlayback()`（纯解析，注入 `byId`/`byTag`/`any`）+ `performRemotePlay()`（解析 → 播放 → 汇总）。**不依赖 DB 与平台通道**，故整条决策链可在宿主机断言。 |
| 端点 | `_playRemote` 退化为薄适配层（取 payload → 调 `performRemotePlay` → 写审计 / 回执）；新增 `_assetPathById()` 按主键精确取音源；审计 `message` 改为**写明解析依据**（`· 音源 a-7` / `· 无此音源：missing`）。 |
| 控制台（接线 §23.7 第 7 项） | 新增「**端点音源库**」「**预置分类**」两个入口（`trackAck: false`，响应是专用事件）；消费 `rc.assets` / `rc.presets` 渲染卡片；**点音源行 → `sound.play {assetId}`**，点分类 chip → `sound.play {preset}`。 |

点选依然会播错（BUG-048 的第 1 条）；只修 `assetId` 不加列表，
用户无从知道端点有哪些音源。两者是**同一个功能的两个半边**。

兜底 —— 因为 `rc_script.dart` 明确把该步定义为
「**随机**播放（可指定分类）」，兜底是**有意行为**而非缺陷。

### 25.5 转向非硬件项：把三向覆盖比对**机器化**

第十三轮用**人工**三向覆盖比对（端点处理 / 控制器发送 / UI 消费）一次定位过

| 用例 | 断言 |
|---|---|
| 协议常量可被解析 | `RcCmd` ≥ 25 / `RcEvt` ≥ 18，无重名（**防空解析**：锁本身必须真在检查） |
| RcCmd 三向之一 | 每条命令 `endpoint_service.dart` 有 `case` |
| RcCmd 三向之二 | 每条命令在 `RcPermGate.requiredPerm` **显式登记** |
| RcCmd 三向之三 | 每条命令有发送方 |
| RcEvt 三向之一 | 每个事件端点会发出 |
| RcEvt 三向之二 | 每个事件有人消费 |

**为什么"权限闸门显式登记"值得单独锁**：`requiredPerm` 的 `switch` 末尾是
`_ => denyAll` —— 这是**正确的失败关闭**（新增命令忘记登记时应当拒绝），
但代价是**漏登记不会编译报错**，只在协助会话里表现为"命令被静默拒绝"。
这正是最需要回归锁的那类静默降级。

实现说明：Dart 无运行时反射，故解析源码类体文本 —— **是权衡不是首选**
（已在测试文件注释中写明：若协议改由代码生成，应断言生成产物）。

### 28.3 根因：测量方式与被测路径的性质不匹配

1. **`GT-07` 用裸 `Stopwatch` 单次采样**，而 `test/performance_v2_test.dart`
   文件头与 `test/perf_bench.dart` 的库注释都明确要求：
   > 已统一用 `benchMs` / `benchMsAsync`（**预热 + 取最小值**）
   > …单次采样被噪声支配：GC、调度、页错误都会让单次测量偏大。

2. **`GT-07` 的路径是往返受限的**：`RemoteStore.enqueue` =
   `await _prefs.setString(...)`（**一次平台往返**）+ 对**递增列表**整体
   `jsonEncode`（O(n²)）。按项目既有规矩
   「**往返受限路径的预算必须自归一化**，绝对值只对纯计算成立」，
   它却用了**紧的绝对阈值 400ms**。

### 28.4 实测基线（改造为 `benchMsAsync` = 预热 3 + 取 5 次最小值）

| 场景 | min-of-5 | 说明 |
|---|---|---|
| **全套件负载下** | **51ms** | 与 §27.6 的"CPU 争用"假设**相反**：负载几乎不影响 min-of-5 |
| **单独跑** | **53ms** | 两场景差 **<4%** → min-of-5 高度可复现 |
| （旧写法，单次采样，负载下） | **455ms** | ≈ 真实值的 **9 倍** —— 测的全是噪声 |

### 28.5 修复对照

| 项 | 修复前 | 修复后 |
|---|---|---|
| 测量方式 | 裸 `Stopwatch`，**单次采样** | `benchMsAsync`（预热 3 + **min-of-5**） |
| 阈值 | 400ms（≈ 基线 × 7.8） | **160ms（= 基线 51ms × 3）** |
| 稳定性 | 全套件下约 **50% 假红** | 51/53ms，**不再翻转** |
| 严格度 | 名义 7.8× 余量，却仍假红 | **收紧约 2.5 倍**且不假红 |
| 功能断言 | `d1.length == 200` / `d2.isEmpty` | `d1Len == 200` / `d2Len == 0`（等价，闭包内取长度） |
| 失败可读性 | 无 reason | `reason: '…最优 ${best}ms（基线 51ms × 3）'` |

> 关键认识：**旧阈值"松"并不等于"不假红"** —— 噪声放大倍数（9×）
> 比余量（7.8×）还大。**余量必须与噪声幅度比，而不是与基线比。**

### 28.6 证伪（确认护栏不是恒真）

在 `RemoteStore.enqueue` 注入「按已有条数重复写盘」，

```

  Expected: a value less than or equal to <160>
    Actual: <4595>
  outbox 200 条 + 二次 drain 最优 4595ms（基线 51ms × 3）
```

### 29.2 本轮修的是什么（BUG-050，两个半边）

**症状 A —— 主叫无限等待。** 修前：`startCall` 发出 `rc.call.invite` 之后
**没有任何超时**。被叫未开自动接通、或 invite 被静默丢弃时，主叫**永远停在
"连接中…"**，且**没有任何"未接"反馈**（界面就一直那样）。
**症状 B —— `rc.call` 在 App 内无人消费。** `RcEvt.callState` / `RcEvt.callMissed`
只有 `tool/` 的桌面 E2E 工具看得到 → 主叫既看不到"对方振铃中"，
也收不到被叫判定的"未接"。其中 `RcEvt.callMissed` 是**死常量**：从不发出、无人消费。

**修后**：45s 未应答 → 结束通话 + **"对方无应答"**；
收到对端 `rc.call state=ringing` → **"对方振铃中…"**；
被叫振铃超时 → 端点发出 `rc.call.missed` → 主叫立刻结束等待。

### 29.3 判定逻辑抽成纯函数（可宿主机断言）

新增 `lib/remote/call_lifecycle.dart`：

| 导出 | 作用 |
|---|---|
| `callerAnswerTimeout` / `calleeRingTimeout` = 45s | 两个角色的等待上限 |
| `waitLimitMs({isCaller})` | 按角色取上限 |
| `waitTimedOut({elapsedMs, limit})` | 是否到点 |
| `timedOutMeansMissed({answered, elapsedMs, limit})` | **到点且未接通**才算未接 |
| `parseRemoteCallState(raw)` | `rc.call` 的 `state` → `RemoteCallState`（未知归 `unknown`） |
| `remoteStateStopsWaiting` / `remoteStateEndsCall` | 收到该状态后该做什么 |
| `connectingText(remote)` | 连接阶段文案（"对方振铃中…" / "连接中…"） |
| `CallEndReason`（8 值）+ `callEndText` | 结束原因 → 用户文案 |
| `endReasonFromSignal(raw)` | `call.end reason` → 结束原因（未知归中性） |

### 29.4 四条"不许猜 / 不许覆盖"的规则（都上锁了）

| # | 规则 | 违反的后果 | 锁 |
|---|---|---|---|
| 1 | `rc.call` 的未知 `state` → `unknown` 且**什么都不做** | 协议加一个新 state 就会**挂断所有在途通话** | CL-05 / CL-06 |
| 2 | `call.end` 的未知 `reason` → 中性（`remoteEnded`） | 把"占线"显示成"已挂断"，用户以为是对方主动挂了 | CL-09 |

| 4 | **已接通后绝不报"未接"** | 用户会在**通话进行中**看到"对方无应答" | CL-02 |

### 29.6 BUG-055：压测层第二条假红（min-of-1）

**症状**：`flutter test --tags perf --concurrency=1` → `+23 -1`，
失败项 `PT-灰盒 · 数据层 exec_logs 5000 条写入 + recent ≤ 3s`；
**单独跑该文件** → 13/13 全绿。

**取证手法**：把该用例阈值**临时置 0**，逼它把实测值打进失败信息。

| 场景 | 实测最优耗时 | 阈值 | 余量 |
|---|---|---|---|
| 单文件 ×3 | 953 / 837 / 1010 ms | 3000 ms | 3.3× |
| **全层** ×2 | **4654** / 1117 ms | 3000 ms | **0.64×** ❌ |

**同一份代码、同一种测量方式，5.2× 放大。**

**根因**：该用例是两套性能文件里**唯一的 `runs: 1`**（min-of-1）——
一个采样点被 GC/抢占打中就必红。而它恰好是**最容易被噪声打中的一个**：
5000 次 `await insert` = **5000 个可被抢占的让步点**（其余用例是紧循环，一口气跑完）。

**修法**：回到本文件自己的约定 —— `runs: 1` → `runs: 3`；**阈值 3000ms 不动**。

**顺带发现的第二条同源护栏**：`任务 CRUD 500 次 ≤ 2s` 用 `runs: 2`（min-of-2），
稳态 457–809 ms，但在**连续压性能层**的负载下测到 **2360 ms**（5.1× 放大）
→ 2000 ms 阈值只剩 2.5× 余量 → 一并改 `runs: 3`。

**复跑（runs: 3，全层 ×3）**：838 / 1547 / 1120 ms，全部 PASS。

> **教训（写进 `performance_test.dart` 头注释）**：
> ① 任何用例都不得用 `runs: 1`（min-of-1 = 没有抗噪）；
> ② **余量要和「噪声幅度」比，不是和「基线」比** —— 3000ms 对 900ms 基线
> 看似 3.3× 余量，5× 的噪声照样打得穿（与 BUG-054 的 AOT 护栏同病）；
> ③ **不要并发跑性能层** —— 两个 `flutter test --tags perf` 同时跑 =
> 自己制造 5× 噪声，然后去改阈值（把测量问题当代码问题修）。

### 30.4 决策抽成纯函数 + 穷尽 switch

```dart
enum CalleeAction { autoAccept, ringUser, rejectBusy }

  if (inCall) return CalleeAction.rejectBusy;          // 占线优先于开关

}
```

### 31.2 缺陷本体：基准**自己给自己当基准**

`integration_test/perf_nfr_test.dart` 的 AOT 用例里，那条最重的基准：

```dart
// 修前
var singleMs = 1 << 62;
for (var r = 0; r < 2; r++) { /* 5000 次 logs.append */ }
final perCallUs = singleMs * 1000 / 5000;          // ← 基准 = 它自己的测量值
int budgetFor(int calls) => (perCallUs * calls / 1000 * 3).round();
report('exec_logs 5000 条**逐条**写入 + recent', singleMs, 20000);  // ← 硬编码
```

- 被它归一化的用例（CRUD / 任务逐条写入）**自洽**，因为它们用「append 的每次成本」当单位。
- 但它**自己**没法用 `budgetFor(5000)` —— 那会得到 `≡ 3 × singleMs`，**恒真、等于没测**。
- 于是只能硬编码 `20000ms`（= 4ms/条，按"冷启 2.475ms/次"标定）。

**该标定被实测推翻**：往返成本可到 **4839µs/次** → 该护栏余量在 **2.0× ↔ 0.83×**
之间摆动，**跨过 1.0 就红**。它成了本文件**唯一一条会随机器状态假红**的用例。

> **本轮当场复现**：新探针版第一次跑 AOT 时，该用例实测 **26658ms**
> —— 若仍是旧的 20000ms 护栏，**这一跑就是红的**。

### 31.3 修法（两个坑，第二个是修的过程中才发现的）

**第一步：把基准换成独立探针。** 用 `tasks.get(<缺失 id>)` × 200 当探针
（纯 1 次 SELECT = 1 次平台往返），于是 5000 次那条也能走 `budgetFor(5000)`。

**⚠️ 第二步：发现第一步是错的。** 该探针**低估**了写入路径的单位成本
（写入要 2~3 次往返）→ 余量被结构差异吃掉：

| 用例 | 实测 | 预算 | 余量 |
|---|---|---|---|
| 任务 500 条**逐条**写入（SELECT 探针） | 3534ms | 3728ms | **1.05×** ❌ |
| 同上（**同类写入**探针） | 1287ms | 2108ms | **1.64×** ✅ |

**1.05× 就是把 BUG-054 搬到了另一条用例上。**
→ **归一化的单位必须与被护栏的工作量同量级。**

**最终形态**：探针 = `logs.append` × **200**（与被护栏用例**同类**、但规模解耦），
带 20 次预热，min-of-3。全部往返受限用例走 `budgetFor(calls)`，**不再有任何绝对 ms**。

```dart
const kProbeCalls = 200;
for (var i = 0; i < 20; i++) { await logs.append(/* 预热 */); }
var probeMs = 1 << 62;
for (var r = 0; r < 3; r++) { /* 200 次 append */ }
final perCallUs = probeMs * 1000 / kProbeCalls;
int budgetFor(int calls) => (perCallUs * calls / 1000 * 3).round();
report('exec_logs 5000 条**逐条**写入 + recent', singleMs, budgetFor(5000));
```

**这条护栏的语义（写清楚，免得被误当成绝对性能验收）**：它断言的是
**规模不变性** —— 5000 次调用的**每次成本**不得超过 200 次调用的每次成本的 3×。
**均匀变慢抓不住**（两边一起变），但**超线性退化**（如丢了索引导致 append 变 O(n)）会被抓住。

### 31.4 AOT 实测（本轮跑了两次，数字本身就是证据）

| 用例 | 第 1 次（SELECT 探针，冷机） | 第 2 次（同类写入探针） | 预算 |
|---|---|---|---|
| 基准单次成本 | 2485µs（纯往返） | **1405µs**（含 INSERT） | — |
| exec_logs 5000 条逐条 | 26658ms | **6568ms** | 21075ms（**3.21×**） |
| 任务 CRUD 500 次 | 4189ms | **1669ms** | 4215ms（**2.53×**） |
| 任务 500 条逐条写入 | 3534ms | **1287ms** | 2108ms（**1.64×**） |
| 任务 500 条批量写入 | 126ms | **129ms** | 500ms |
| exec_logs 5000 条批量 | 779ms | **409ms** | 3000ms |

—— 这正是归一化要的效果：**绝对值随机器漂，余量不随机器漂**。

> 最薄余量是 `任务 500 条逐条写入` 的 **1.64×**，成因是**结构性**的
> （task upsert 单次成本 ≈ log append 的 1.96×，与机器状态无关），不是噪声。

### 32.3 修法：判定抽成纯函数，UI 只做薄适配

新增 `lib/remote/script_progress.dart`（纯逻辑，可在宿主机直接断言）：

| 成员 | 作用 |
|---|---|
| `enum ScriptState { running, done, stopped, unknown }` | 端点状态的**本端**表示 |
| `parseScriptProgress(payload)` | 解析 `rc.script`；**未知 `state` → `unknown`**，绝不猜 |
| `shouldApplyProgress(p)` | `unknown` 必须被忽略（把"什么都不做"变成**可断言**的行为） |
| `describeScriptProgress(p, {totalSteps})` | 人类可读文案，**穷尽 switch、无 `default:`** |

为什么"未知状态"要单独抽成函数：把未知值猜成"完成"，进度卡会**假装完成**；
猜成"运行中"则**永远转圈**。两种猜法都比"什么都不做"更坏（BUG-050 判据）。

`RemoteScriptsTab` 的改动（薄适配层）：

- `initState` 订阅事件流，`_onEvent` 只过滤 `RcEvt.scriptState` 并落进
  `_progress[scriptId]`（先过 `shouldApplyProgress`）；

### 32.5 BUG-057：压测层「同一份工作量、两个预算」

**发现方式**：跑标准门禁时压测层红，失败项是
`GT-01 加密 50KB 备份 ≤ 4s`（实测 6213ms）与 `GT-03 错误密码解密 ≤ 1500ms`（实测 3737ms）。

**第一步先怀疑测量**（项目铁律），结果找到真凶：

- `TaskStop` 报"已终止"的那个**端口扫描后台任务并没有真的死** ——
  `/usr/bin/xargs` 仍在持续 fork `timeout` + `bash` 子进程（`ps` 可见 24 个残留）。
- 杀掉之后 GT-01 立刻恢复（6213ms → 通过），**但 GT-03 依然红**（3229ms / 1500ms）。
- 所以这是**两个独立问题**：一个是测量污染，一个是**预算形状不对**。

**预算形状的证据链**：

1. `ExportCrypto.encrypt` / `decrypt` 都走 `_deriveKey` → `Pbkdf2(iterations: 120000)`；
   错密码只是最后 AES-GCM 校验失败，**KDF 一次都不会少跑** → 三条用例工作量完全相同。
2. 用项目既有取证手法（**把阈值临时置 0**）逼出干净机器上的真实耗时：

| 用例 | 预算（修前） | 实测 | 余量 |
|---|---|---|---|
| GT-01 加密 | 4000ms | **1128ms** | 3.55× |
| GT-02 解密 | 4000ms | **1049ms** | 3.81× |
| GT-03 错密码解密 | **1500ms** | **1127ms** | **1.33×** |

3. 三条用例的**标题**都写着「≤ 4s」，只有 GT-03 的断言写 1500 —— 断言与自己的标题矛盾。
4. CPU 争用时耗时被抬到 2.9×（1127 → 3229ms）。**1.33× 的余量低于噪声幅度**，
   所以 GT-03 是最先红的那条 → 典型"同一份代码时红时绿"。

**修法**：抽出 `const kdfBudgetMs = 4000`，三条用例共用；取值依据（实测 ≈1.1s × ~3.5）
写进注释；并用 `test/perf_budget_consistency_test.dart` 锁住"同一份工作量 → 同一个预算"。

⚠️ **这不是放宽阈值**：需求（备份加密/解密 4 秒内）没变，改的是**形状**——
把"拍脑袋定的 1.33×"对齐到"与兄弟用例一致的 3.5×"。绝对性能验收仍在 AOT 层（NFR-04）。

### 32.7 顺带修掉的两个测试工具缺陷

1. **`methodBody()` 抽错范围（会静默失效）**：
   原实现取"签名后的第一个 `{`"，而 Dart 的**具名参数也用大括号**
   （`String f(int a, {int? b}) { ... }`）→ 抽到的是**参数列表**，
   于是 `isNot(contains(...))` 变恒真、`contains(...)` 变恒假。
   中间还试过"取前面是 `)` 的 `{`"，同样错（`) async {` 的 `{` 前面是 `async`）。
   最终实现：**先按括号配对跳过整个参数表，再取其后第一个 `{`**，
   并给工具本身加了自检（SP-11）。
   ⚠️ `test/call_lifecycle_test.dart` 的同名函数**同步修正** ——
   它的现有用法（`_handleCallInvite`，无具名参数）本来是对的，
   但同一个坑留给下一个人就是下一个假绿灯。
2. **`'ScriptState.$v'` 插值成 `ScriptState.ScriptState.running`（恒假断言）**：
   枚举插值必须用 `v.name`。SP-07 初稿就是这么写错的。

### 33.3 厂商安装弹窗：**上一轮结论被证伪**，真实边界是「全新 vs 覆盖」

**上一轮交接写**：「无线调试绕过了厂商 USB 安装弹窗（属 USB 传输路径，非设备级策略）」。
**本轮实测推翻**：截图显示，**即使走无线调试，MIUI 弹窗照旧出现，标题仍是「USB 安装提示」**：

```
USB 安装提示
[声盾]
正在通过 USB 安装此应用，是否继续？
○ 拒绝后下次安装不再提示
[继续安装]   [拒绝（10）]      ← 10 秒倒计时，默认高亮的是「拒绝」
```

（证据：`screencap` 连续抓屏，第 4 张捕捉到弹窗、第 5 张弹窗已消失 —— 倒计时没走完就没了，
说明**有人点了「继续安装」**。上一轮那次"成功且无弹窗"是同一原因：**使用者当时在场**。）

**真实边界（本轮实测，可复现）**：

| 设备上是否已有该应用 | `adb install -r` 的语义 | 结果 |
|---|---|---|
| **无** | **全新安装** | ❌ 弹「USB 安装提示」，10s 倒计时默认拒绝 → `INSTALL_FAILED_USER_RESTRICTED: Install canceled by user` |
| **有** | **覆盖安装** | ✅ **`Performing Streamed Install` → `Success`，全程无弹窗**（安装 15.1s） |

- 「无应用 → 全新」实测 **3 次全部失败**（门禁设备冒烟、门禁设备桥接、手动 `-t -r`）。
- 「有应用 → 覆盖」实测 **1 次成功且无人干预**（`app_smoke_test` 4/4，安装 15.1s）。
- 所以 `flutter test integration_test/…` 之所以在真机上**时好时坏**，取决于**跑之前设备上有没有应用**
  —— 而 `flutter test` **跑完会卸载**（见 33.4），于是**下一次又退回"全新安装"**。

**由此得到的可用工作流（本轮能确证的）**：
1. **人工在设备上点一次「继续安装」**（唯一需要人的一步）；
2. 此后凡是**设备上已有应用**时的 `flutter test integration_test/…` 都是**覆盖安装 → 免弹窗 → 可自动**。

> ⚠️ **`--no-uninstall`（33.4）是这条工作流的关键拼图**：它让第 1 步装上的应用**不被跑完卸载**，
> 从而使后续每一步都落在"覆盖安装"分支。**但本轮未能实测其保留效果**
> （要验证它，必须先完成一次成功的安装，而那一步恰好卡在弹窗上）——
> **因此只记"参数存在、文档语义为保留应用"，不声称已验证。**

### 33.4 门禁工具改进：失败时**落盘完整输出**

第一次真机门禁的设备层只打印了一行：

```
=== 门禁 4/5: 设备冒烟（app_smoke_test，4 例）on adb-960f853-Kmi5Mk._adb-tls-connect._tcp ===
No tests were found.
```

**这一行既看不到 Gradle 阶段、也看不到安装阶段**，无法判断是"没构建"还是"构建了但设备上没跑起测试"
—— 而脚本当时只做 `echo "$out" | tail -1`。**证据在失败的那一刻被丢掉了。**

**修法**：`scripts/gates.sh` 新增 `fail_dump()`，各层失败时把**完整输出**写入
`${GATE_LOG_DIR:-/tmp}/gates_<标签>.log` 并回显尾部 15 行：

```bash
fail_dump() {  # $1=标签  $2=完整输出
  local f="${GATE_LOG_DIR:-/tmp}/gates_$1.log"
  printf '%s\n' "$2" > "$f"
  echo "  ── 完整输出已存: $f ──"
  printf '%s\n' "$2" | tail -15
}
```

**立刻见效**：第二次门禁的设备层失败时，日志直接给出了
`adb.exe: failed to install …: Failure [INSTALL_FAILED_USER_RESTRICTED: Install canceled by user]`
—— 根因（33.3）就是这么拿到的。

> 📌 **教训**：门禁脚本的"失败输出"是**诊断资产**，`tail -1` 等于把资产扔掉。
> 与本仓库既有的「构建落盘，测试转换」是同一条原则。

### 33.5 功能层时间敏感假红：AHW-05 / AHW-06

第二次门禁功能层红了一条：

```
E:/SonicShield/test/assist_host_screen_test.dart: AHW-06 短 TTL 渲染为 00:ss（不出现负数/越界）
Expected: exactly one matching candidate
  Actual: _TextContainingWidgetFinder:<Found 0 widgets with text containing 00:4: []>
```

**根因（不是代码回归）**：两条用例都断言**具体秒数**，而窗口只有 5 秒：

| 用例 | TTL | 断言 | 覆盖窗口 |
|---|---|---|---|
| AHW-05 | 5 分钟 | `textContaining('04:5')` | 300→295s（5 秒） |
| AHW-06 | 45 秒 | `textContaining('00:4')` | 45→40s（5 秒） |

而 `_mmss(s.remaining)` 的 `remaining` 来自**真实墙钟**（该文件注释已写明"FakeAsync 只虚拟化 Timer，
`DateTime.now()` 仍是真实墙钟"）。功能层一次跑 465 例，**慢机器/并发下 `pumpWidget` 一旦耗时 >5s
就会跨过边界**（`00:4x` → `00:3x`）→ `Found 0 widgets`。

**修法**：断言**格式**（保住原意"渲染为 mm:ss / 不越界"），再用**宽窗口**数值断言补回
"绑定的确实是会话真实剩余时间"：

```dart
expect(find.textContaining(RegExp(r'剩余 \d\d:[0-5]\d')), findsOneWidget);   // 格式
expect(s.remaining.inSeconds, greaterThan(240));                            // 宽窗口
expect(s.remaining.inSeconds, lessThanOrEqualTo(300));
```

**验证**：`flutter test test/assist_host_screen_test.dart` → **7/7 通过**。

> 📌 与 BUG-053/055 同族：**"同一份代码时红时绿" = 测量/断言形状问题**，先怀疑测量，不要改产品代码。

### 37.2 BUG-058：`sealed` 上的 `_` 兜底 = 关掉编译器的穷尽性检查

`ActionConfig` 是 **sealed**（8 个子类）。`_kindOfCandidate` 把"随机指令集"的
子动作回填成 `RcStepKind`，原写法只显式处理 4 个，其余走 `_ => RcStepKind.play`：

```
复合动作 CompositeAction  ─┐
声景     SoundscapeAction  ├─→ 被当成 **RcStepKind.play**
嵌套动作组 ActionSetAction ─┘
```

两个后果，一个比一个坏：

1. **静默改配置**：用户打开一个含复合/声景子动作的任务 → **什么都不改直接保存**
   → 编辑器按 `play` 重建 → **原配置被悄悄改成"播放音频"**，无任何提示。
2. **编译器被关掉**：`sealed` 的穷尽性检查只在**不写 `_`** 时才生效。
   写了 `_` 之后，以后新增任何 `ActionConfig` 子类都**静默掉进兜底**，
   不报错、不提醒 —— 这正是项目纪律里"漏登记不编译报错"的那类坑。

**可达性**：编辑器 UI 只提供 play/tts/notify/vibrate/record 五种，造不出嵌套；
但 `ActionConfig.fromJson`（`settings_screen.dart:191` 读库、`ActionSetAction.fromJson`
读导入 JSON）是真实路径 → **导入/备份的任务可以带嵌套子动作**。

### 37.3 修法

1. 抽成顶层纯函数 `stepKindOfAction(ActionConfig)` → 返回 `RcStepKind?`，
   **显式穷尽 8 个子类**（`CompositeAction`/`SoundscapeAction`/`ActionSetAction` → `null`）。
   新增子类时这里**直接编译报错**，逼人登记。
2. 编辑器：不可表示的子动作进 `_setPreserved`，**保存时 `..._setPreserved` 原样带回来**
   → 打开再保存**不丢配置**。
3. UI 显示一张说明卡：「另有 N 个子动作（复合 / 声景 / 嵌套动作组）在此编辑器中
   没有对应控件，已按原配置保留，保存时不会丢失」。
