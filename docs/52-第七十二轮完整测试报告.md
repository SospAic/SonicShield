## 二、相机「无法调用」根因与修复（release 专项）

**根因**：Flutter Gradle 插件在 `FlutterPlugin.kt:218` **写死** `releaseBuildType.isMinifyEnabled = true`
⇒ 只要是 release 包，R8 压缩/混淆**一定**打开（与工程 `build.gradle.kts` 怎么写无关）。
`mobile_scanner 6.0.11` 自带规则是 `-keep class com.google.mlkit.* { *; }`，而 ProGuard 里**单个 `*`
不跨越包分隔符** ⇒ 只保住 `com.google.mlkit` 这一层，`com.google.mlkit.vision.barcode.**` 等**子包照旧被
重命名/裁剪**。ML Kit 组件按 `<meta-data>` + 类名反射加载，类名一变即失效，扫码时原生方法通道抛：

```
E/MethodChannel#dev.steenbakker.mobile_scanner/scanner/method:
  Failed to handle method call
  java.lang.NullPointerException: Attempt to invoke virtual method
  'java.lang.Class java.lang.Object.getClass()' on a null object reference
```

现象即「相机启动失败」（debug 包同机同路径完全正常）。

**修复**：新增 `android/app/proguard-rules.pro`（把口径从单星号收紧到**双星号含子包**）并在
`android/app/build.gradle.kts` 的 `buildTypes.release` 显式 `proguardFiles(..., "proguard-rules.pro")`；
保留 `com.google.mlkit.**`、`com.google.android.gms.internal.mlkit_**`、`com.google.android.libraries.barhopper.**`
等整棵子树与枚举成员。

**机器锁**：`test/release_r8_lock_test.dart`（8 例，含「接入缺失即判红」「规则缺失即判红」等反例，非恒真）。

**release 包取证**（本轮实测）：解包 `app-release.apk` 的 `classes.dex`，按 ASCII 扫描类描述符
`com/google/mlkit/vision/barcode`、`com/google/android/libraries/barhopper`、
`com/google/android/gms/internal/mlkit_` 均 **found=True** ⇒ 这些类**以原名保留在 release DEX 中**。

> 注：`camera.snap`（远程命令）是**有意硬禁用**的能力（见 `docs/22 §1 #18`），与本相机根因**无关**，
> 不在本轮修复范围内。

### 6.3 修复的测试自身缺陷：`fp_local_task_test.dart` FP-L3

- **现象**：首跑 `FP-L3 确定性随机（FR-25）` **失败**（`Expected: true / Actual: false`）。
- **根因**：DPRNG 种子 = `taskId + updatedAt(定义版本) + 计划日`（`ScheduleEngine._seedKey`）。
  用例两次调用 `mkTask(id:'fp-det-a')`，各自取 `DateTime.now()` 作 `updatedAt` ⇒ 实为**两个不同定义版本**，
  计划不同是**正确**行为；是**断言写错了对象**，非产品缺陷。
- **修复**：改用**同一个 `Task` 实例**做两次 `materialize`（不放松断言，仍钉「同版本重算零漂移」）。
- **复跑**：`FP-L1..L7` **7 例全绿**。**`lib/**` 未改**（测试侧修复）。
