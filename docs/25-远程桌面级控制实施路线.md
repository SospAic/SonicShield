## 0. 与 docs/24 的边界（先划清，避免重复建设）

| 能力 | docs/24 | 本文（docs/25） |
|---|---|---|
| 屏幕**画面**采集与回传 | ✅ 已规划（阶段0 授权壳 → 阶段1 单帧 → 阶段2 WebRTC 流 → 阶段3 观看 UI） | **复用**，不重复设计；只在「控制会话」语义上扩展 |
| 远程**输入注入**（触摸/手势/按键/文本） | ❌ 无 | ✅ 本文主体 |
| 会话模型 | 单向（端点 → 控制端 画面） | **双向**（控制端 → 端点 输入 + 端点 → 控制端 画面），同一会话 |
| 授权模型 | 每次 MediaProjection 系统弹窗 | 同上 **+** 输入注入需用户**显式开启无障碍**（系统设置，非应用内可绕过） |

**一句话**：docs/25 = docs/24 的投屏通道 **+** 一条受同一授权/可见性/审计约束的**输入回传通道**。

## 1. 能力边界与红线（不可裁剪，源自 docs/08 精神）

1. **授权**：
   - 画面：每次投屏由 **MediaProjection 系统授权弹窗**发起（Android 强制，docs/24 §第二部分已定）；
   - 输入：需用户在**系统设置**里显式开启本应用的**无障碍服务**（`AccessibilityService`）。
     App 内**不得**提供"自动开启无障碍"或任何绕过路径；未开启时远程输入**如实 `ok:false`**，不静默降级。
2. **可见**：控制会话期间端点必须始终有
   - 前台服务常驻通知（投屏用 `mediaProjection` 类型，docs/24 已定）；
   - App 内**醒目指示**："正在向 X 投屏 / 接受 X 的远程操作"，任何时刻端点可**一键停止**（停止即同时断开画面与输入）。
3. **不破 E2EE 口径**（承 docs/24 §3.2）：
   - 实时画面走 **WebRTC 媒体**（DTLS-SRTP，指纹经 MQTT E2EE 信令交换）；
   - **输入指令走 MQTT rc 信封 E2EE**（小体积、天然有去重与时间窗，且必须经 `RcPermGate` 权限门）；
   - 单帧截屏（docs/24 阶段1）仍走 `rc.photo` 信封。
4. **不得隐蔽**：控制端 UI 必须显著标注"对方屏幕为实时内容且对方可见操作指示"（docs/24 §阶段3 R13 同款文案纪律）。

## 2. 被控端输入注入：三条路径与选型

Android 上"程序化注入触摸/按键"的合法路径（用户调研已列，这里给出**本项目的选型与理由**）：

| 路径 | 原理 | 覆盖面 | 用户负担 | 本项目选型 |
|---|---|---|---|---|
| **A. AccessibilityService**（无障碍） | `dispatchGesture()`（API 24+）/ `performGlobalAction()` / 节点 `ACTION_CLICK` | 全局手势+按键+文本；**无需 root、无需电脑** | 用户到系统设置开启无障碍（一次性） | ✅ **P0 默认路径** |
| B. Shizuku（ADB 授权） | 经 Shizuku 以 shell 身份调 `input` / `InputManager` | 与 ADB 同级，可 `input tap/swipe/keyevent` | 需装 Shizuku 且每次重启后重新授权 | 🟡 P1 可选增强（更高保真、可注入系统级按键） |
| C. Root / ADB | `su -c input ...` | 最全 | 需 root 或常连电脑 | ❌ 不作为产品路径（合规与可维护性），仅调试用 |

**选型结论**：**P0 只做 A（无障碍）**。理由：
- 唯一"纯 App 内、无需 root/电脑"的合规路径（C 端可交付）；
- `dispatchGesture` 足以表达 tap / longPress / swipe / 多指（`GestureDescription` 支持多 stroke）；
- 文本输入可走无障碍节点 `ACTION_SET_TEXT`（聚焦输入框后），或退化为 `input text`（P1 经 Shizuku）。

**能力边界（如实记录，不假装）**：
- `dispatchGesture` **不能**注入系统级按键（电源/音量）——那需要 B/C；
- 部分定制 ROM 的安全输入（密码框、支付页）会**屏蔽无障碍注入**（系统行为，无法绕过，也不应绕过）；
- 注入的坐标是**屏幕绝对像素**，控制端必须把"看到的画面坐标"按分辨率/方向映射到端点坐标（见 §4.3）。

## 3. 媒体传输选型：WebRTC（复用现有栈）

| 方案 | 优点 | 代价 | 结论 |
|---|---|---|---|
| **A. WebRTC**（复用 `flutter_webrtc` + `call.*` 信令） | 传输/NAT 穿透/拥塞控制/DTLS-SRTP 全免费；docs/24 已选；`call.*` 信令链已完整（docs/22 §13–16） | 依赖插件对 `getDisplayMedia`（MediaProjection token 交接）的支持，**是本方案最大不确定点**（docs/24 R12） | ✅ **推荐** |
| B. scrcpy 式原始 H.264 over 自建 socket | 编码效率高、延迟低（局域网） | 需自建传输 + NAT 穿透 + 加密 + 拥塞控制；与现有栈重复 | 🟡 仅当 A 的 `getDisplayMedia` spike 失败时的降级 |

**推荐 A**：与 docs/24 一致，避免重复造传输层。**开工首日必须先做 A 的技术验证 spike**（docs/24 R12），
失败则降级 B（原生 libwebrtc AAR 直写，信令仍复用 MQTT）。

**编码**：默认 **720p / 15fps / 动态码率**（docs/24 R10）；端点侧可调；不传设备音频（独立开关，默认关）。

## 4. 协议扩展（`lib/remote/protocol.dart`）

> 纪律同 docs/24 阶段0：**先加常量与文档注释，不加发射方**；实现随阶段推进。

### 4.1 新命令（控制端 → 端点，`RcCmd`）

| 常量 | payload | 回执 | 权限位 |
|---|---|---|---|
| `screen.cast.request` | `{castId, kind:'view'|'control', maxW?, maxH?, fps?}` | `rc.ack` + 会话建立后 `rc.screen{state}` | `script`（有副作用的全局操作，同 `run.master.set` 一档） |
| `screen.cast.stop` | `{castId, reason?}` | `rc.ack` | `script` |
| `input.tap` | `{castId, x, y, durationMs?}` | `rc.inputAck{ok}` | `script` |
| `input.swipe` | `{castId, x1,y1,x2,y2, durationMs}` | `rc.inputAck{ok}` | `script` |
| `input.key` | `{castId, keyCode}`（仅无障碍可表达的导航/返回/Home/最近任务；电源/音量需 Shizuku） | `rc.inputAck{ok}` | `script` |
| `input.text` | `{castId, text}` | `rc.inputAck{ok}` | `script` |

**坐标口径（`input.*` 的 x/y）**：统一为**归一化 0..1 浮点**（相对端点屏幕宽/高）。
端点按当前屏幕实际像素换算 —— 这样控制端不必知道端点分辨率，旋转/分辨率变化也不失效。
（`input.tap` 的 `x,y` 是归一化坐标，不是像素。）

### 4.2 新事件（端点 → 控制端，`RcEvt`）

| 常量 | payload | 说明 |
|---|---|---|
| `rc.screen` | `{for, castId, state: requesting|streaming|stopped|denied, kind}` | 会话状态机镜像（与 `rc.call` 同形） |
| `rc.inputAck` | `{for, castId, ok, message?}` | 单条注入回执（不并入通用 `rc.ack`，避免与命令级 ack 混淆） |
| `rc.screen.frame` | `{for, castId, photoB64}` | **可选**：docs/24 阶段1 单帧路径的载体（复用 `rc.photo` 亦可，二选一，实施时定） |

### 4.3 会话与占线

- 一个 `castId` 一条控制会话；与 `call.*` 通话会话**互斥**（同时只允许一个实时媒体会话，`call.end{busy}` 同款）。
- 会话生命周期审计：`screen.cast`（start/stop/denied/timeout/时长），两端可查（承 docs/24 阶段3 E3）。
- 撤销配对 / 关闭引擎 / 用户点"停止" ⇒ **立即**停画面 + 停输入（并入 `decideRevokeCleanup` 的 stop 项，docs/24 C6 同款）。

## 5. 分阶段路线（P0 → P3）

### P0 · 被控端骨架（授权 + 注入 + 可见性；**无画面传输**）

| 文件 | 改动 |
|---|---|
| `android/app/src/main/AndroidManifest.xml` | `FOREGROUND_SERVICE_MEDIA_PROJECTION` 权限；投屏前台服务声明（`mediaProjection` 类型）；**无障碍服务**声明（`android.permission.BIND_ACCESSIBILITY_SERVICE` + `accessibility-service` meta） |
| 新增原生 `ScreenCastService.kt` | `mediaProjection` 前台服务；Android 14+ 纪律：**先 `createScreenCaptureIntent` 拿同意 token，再 `startForeground`**（反了 `SecurityException`，docs/24 §阶段0） |
| 新增原生 `RemoteInputService.kt` | `AccessibilityService`；`dispatchGesture` / `performGlobalAction` / 文本注入；**归一化坐标 → 像素**换算；无授权时如实返回 false |
| `lib/remote/protocol.dart` | §4 的常量（只加常量） |
| `lib/services/native_bridge.dart` | `screenCastStart/Stop`、`inputTap/Swipe/Key/Text`、`isAccessibilityEnabled`（探测，用于 UI 引导） |
| 端点 UI | "正在投屏/接受远程操作"指示 + 一键停止（先接**真实**服务状态，不接假状态源） |

**P0 验收判据**：① 请求 → 系统授权弹窗 → 同意后前台服务带通知常驻；② 用户开启无障碍后，
本机自测 `input.tap` 能点到目标控件；未开启无障碍 → `rc.inputAck{ok:false}` 且**不静默**；
③ 拒绝授权 → 服务不启动、回执 `ok:false`；④ 停止 → 通知与指示**≤1s** 消失。
**无任何画面传输即算 P0 完成。**

### P1 · 单帧 + 点击（docs/24 阶段1 与 P0 合并验收）

- 复用 docs/24 阶段1（`VirtualDisplay → ImageReader → JPEG → rc.photo`）；
- 控制端：收单帧 → 显示 → 用户点画面 → 发 `input.tap`（归一化坐标）。
- 验收：docs/24 C1–C6 + **本机自测**"点画面 = 点到端点对应控件"（坐标映射正确性）。

### P2 · 实时流 + 手势/按键（docs/24 阶段2 的扩展）

- 画面：WebRTC 实时流（docs/24 阶段2）；
- 输入：`input.swipe`（拖拽/滑动）、`input.key`（导航键）、`input.text`；
- 占线：与 `call.*` 互斥；断线重连（ICE）后输入通道**自动重绑定**新会话。

### P3 · 控制端观看/控制 UI

- `RTCVideoView` 渲染 + 手势识别（tap/swipe → 归一化坐标）+ 软键盘/按键条 + 会话状态条 + 停止；
- 入口：遥控主面板"请求远程控制"（文案：**'需对方设备确认并已开启无障碍'**）；
- 审计：会话记录可查（含被拒绝的请求）。

## 6. 与现有安全模型的衔接

| 资产 | 通道 | 控制功能是否触碰 |
|---|---|---|
| 输入指令 | MQTT rc 信封 E2EE（配对码派生密钥） | **是**——每条注入指令都走 E2EE + `RcPermGate` 权限位 + 时间窗/去重 |
| 实时画面 | WebRTC DTLS-SRTP（指纹经 E2EE 信令） | 是——同 docs/24 §3.2（等价强度、不同体系） |
| 授权 | MediaProjection 系统弹窗（画面）+ 系统无障碍开关（输入） | 是——**双授权**，均不可应用内绕过 |
| 审计 | `screen.cast` / `input.*` | 新增（start/stop/denied/每条注入可留痕，按需采样） |

**新增攻击面**（必须锁）：
- 输入注入是**高危能力**（可代用户操作任意 App）。缓解：① 仅**已配对**控制端可用；② 权限位 `script`；
  ③ 会话必须**端点显式授权**（画面弹窗 + 无障碍开关）；④ 端点**一键停止**且停止后**立即失效**（旧 castId 的 input 一律拒）；
  ⑤ 审计留痕。
- 变异证伪锁（P0 起）：**未授权（无 MediaProjection token / 无障碍未开）直接调注入桥 → 必须失败**。

## 7. 验收判据汇总（含变异证伪）

| # | 场景 | 判据 |
|---|---|---|
| G1 | 端点拒绝投屏授权 | `rc.ack{ok:false}`；控制端 UI 明示"对方拒绝"，**不重试轰炸**（docs/24 C2 同款） |
| G2 | **变异证伪（授权锁）** | 未走授权弹窗直接调截屏/注入桥 → 必失败（平台保证 + 代码断言无 token/无无障碍即抛） |
| G3 | **变异证伪（可见性锁）** | 会话进行中端点前台通知/指示不存在 → 判红（任何像素出屏/任何注入生效前，端点必须有可见指示） |
| G4 | **变异证伪（会话失效锁）** | 停止会话后，携旧 `castId` 的 `input.*` → 必拒（不得"停了还能操作"） |
| G5 | 配对撤销时会话在跑 | ≤1s 内画面与输入同时停（并入 `decideRevokeCleanup`） |
| G6 | 通话中请求控制（或反之） | `busy` 占线，两者不并发 |
| G7 | 坐标映射 | 控制端在**不同分辨率/方向**下点同一 UI 元素，端点命中同一控件 |
| G8 | 无障碍未开启 | `rc.inputAck{ok:false}` + 控制端明示"请让对方开启无障碍"，不静默 |
