# 05 · 后台保活与电源管理方案

> 目标：应用在后台/锁屏/Doze/进程被杀/重启五种状态下仍能按计划可靠触发，
> 同时把电量消耗控制在用户可接受范围。这是本项目的工程核心。

---

## 1. Android：双通道触发架构

```
                    ┌──────────────────────────────┐
                    │  occurrences 表（唯一事实源）  │
                    │  pending → done/failed/skip  │
                    └──────────┬───────────────────┘
                               │ executeDue() 幂等
        ┌──────────────────────┼──────────────────────┐
        │ 通道A：Dart Timer     │ 通道B：原生精确闹钟    │
        │ 引擎隔离内 15s tick   │ AlarmManager          │
        │ 应用存活时亚秒级精度   │ setExactAndAllowWhileIdle│
        └──────────┬───────────┴──────────┬───────────┘
                   │                      │ 闹钟唤醒
                   ▼                      ▼
        ┌──────────────────────────────────────────┐
        │ ForegroundService（flutter_background_service）│
        │ type = mediaPlayback（第 35 轮起：不含 microphone/dataSync）│
        │ 常驻通知（引擎状态 + 合规文案）                 │
        └──────────────────────────────────────────┘
```

### 1.1 通道A（进程内，精确）

- 引擎隔离内 `Timer.periodic(15s)` 扫描到期条目；
- 另设滚动续算：pending < 12h 时重新物化 48h 计划并同步原生闹钟；
- 局限：Doze 深睡时 Dart Timer 被冻结 → 必须有通道B。

### 1.2 通道B（原生看门狗，可靠）

- 物化完成后，把未来计划的前 64 条（`maxNativeAlarmsPerTask`）逐条
  `setExactAndAllowWhileIdle(RTC_WAKEUP)`；
- `AlarmWatchdogReceiver` 收到闹钟 → `startForegroundService()` 拉起引擎 →
  启动即 `executeDue()`；
- 全部 PendingIntent 使用 `FLAG_IMMUTABLE`，请求码由时间戳散列保证稳定；
- 清除：新排布前记录集合，覆盖式更新。

### 1.3 生命周期恢复矩阵

| 场景 | 恢复机制 |
|---|---|
| 用户返回桌面/锁屏 | 前台服务持续运行（不受影响） |
| Doze 深睡 | AllowWhileIdle 闹钟穿透（标准豁免窗口） |
| 进程被系统/LPA 杀死 | 下一发精确闹钟重新拉起前台服务 |
| 设备重启 | `BootReceiver`（BOOT_COMPLETED / QUICKBOOT / MY_PACKAGE_REPLACED），仅当 `should_run` 标志为真 —— **不直接拉 FGS**，改排 **30s 延迟**后的一次性**精确闹钟**（越过 `BOOT_COMPLETED` 的 20s 临时白名单窗口），再由 `AlarmWatchdogReceiver` 拉起引擎（第 70 轮修复，见 §1.4） |
| 应用升级 | MY_PACKAGE_REPLACED 同上 |

### 1.4 Android 版本适配

| 版本 | 关键约束 | 应对 |
|---|---|---|
| **7.0–7.1（API 24–25，本项目最低支持）** | 无 `VibrationEffect`（API 26 起）；无前台服务类型语义；Java 8 API 需脱糖 | 振动走 `vibrate(long[], int, AudioAttributes)`（**自 API 21 可用，仍带属性**）；FGS 用两参 `startForeground`；已开 core library desugaring |
| **8.0–11（API 26–30）** | Doze 下 `setExact` 被推迟到维护窗口；`SCHEDULE_EXACT_ALARM` 尚未引入 | 通道B 一律 `setExactAndAllowWhileIdle`（**自 API 23 可用**）；`canScheduleExact()` 对 `SDK_INT < 31` 直接返回 true |
| 12 (API 31) | SCHEDULE_EXACT_ALARM 特殊权限 | 运行时检测 `canScheduleExactAlarms()` + 引导页直达授权 |
| 13 (API 33) | POST_NOTIFICATIONS 运行时权限 | 启动守护前统一申请 |
| 14 (API 34) | FGS 类型必须逐个声明权限 | `FOREGROUND_SERVICE_MEDIA_PLAYBACK`、`FOREGROUND_SERVICE_MICROPHONE`（`FOREGROUND_SERVICE_DATA_SYNC` 已于第 35 轮随 dataSync 类型位一并移除，见下行） |
| 15 (API 35) | ① `BOOT_COMPLETED` **禁止**启动 `mediaPlayback`/`dataSync` 型 FGS；② `dataSync` 型 FGS 有「24h 内累计 6h」上限，到点回调 `Service.onTimeout` | ① **第 70 轮已修复**：根因 = 插件 `AndroidConfiguration.autoStartOnBoot` **默认 `true`**（`platform_interface` 5.1.2 `configs.dart:73`）⇒ 自带 `BootReceiver` 在 `BOOT_COMPLETED` 直接 `startForegroundService(mediaPlayback)`，Android 15+/`targetSdk=36` 必抛 `ForegroundServiceStartNotAllowedException`（进程崩溃反复重启）。修 = ① Dart 显式 `autoStartOnBoot: false`；② `BootReceiver.kt` 改排 **30s 延迟**后的一次性精确闹钟（`setExactAndAllowWhileIdle`，Android 12+ 未授权 `canScheduleExactAlarms()` 时降级 `setAndAllowWhileIdle`）。**关键取证：`BOOT_COMPLETED` 只有 20s 临时白名单窗口 —— 闹钟在窗口内触发会归因回 `BOOT_COMPLETED`（10s 延迟实测必崩），窗口后才归因 `ALARM_MANAGER_WHILE_IDLE` 而豁免（30s 实测成功）**；三机（API 36 x86_64）实测 `isForeground=true types=0x00000002` 全绿。⚠️ `am force-stop` 造成 `stopped=true` 会阻断 `BOOT_COMPLETED`，验证前不得先 `force-stop`；② 第 35 轮已从类型位移除 `dataSync`（插件 `flutter_background_service_android 6.3.1` 全文件 0 处 `onTimeout` ⇒ 到点必抛 `RemoteServiceException` 杀进程），只保留 `mediaPlayback`。证据见 `docs/12 §103` / `docs/17 §100`、`_pt/audit/E1-silent-fix.md`、`_pt/audit/SEC1-gaps.md` |
| 16 (API 36) | edge-to-edge 强制 | 已适配 enableOnBackInvokedCallback 与 Material3 |

### 1.4.1 最低支持版本裁决：API 24（Android 7.0 Nougat）

**这是地板，不是随手取的数** —— 由多方共同锁死，取最大值：

| 约束来源 | 声明的下限 |
|---|---|
| Flutter 3.47.3 SDK（`FlutterExtension.kt:26`） | **24** |
| `flutter_plugin_android_lifecycle` 2.0.35 | **24** |
| `flutter_tts` 4.2.5 | **24** |
| `record_android` 2.2.0 | **24** |
| `shared_preferences_android` 2.4.28 | **24** |
| `geolocator_android`（用 `flutter.minSdkVersion`） | 24 |
| 其余 14 个含 android/ 的包 | 16–21 |

⇒ **不可能再低**：AGP 清单合并会在「app 的 minSdk 低于某个库声明的 minSdk」时直接报错。
所以「向低版本兼容」的落点是**让 API 24/25 上的运行时行为真正正确**，
而不是继续降 `minSdk`。表决由 `test/android_compat_lock_test.dart`（FLOOR 组）机器钉住。

⚠️ **ABI 不要收窄**：Flutter 的 Gradle 插件会在 `plugins{}` apply 时
`abiFilters.clear() + addAll(PLATFORM_ABI_LIST)`（FlutterPlugin.kt:591-600），
`PLATFORM_ABI_LIST = [armeabi-v7a, arm64-v8a, x86_64]` ⇒
在 `android{}` 里写 `abiFilters` **完全无效**（只追加重复项）。
更要紧的是：收窄成功就会排除 `armeabi-v7a`，而这个时代的低端机大量是 32 位，
会 `INSTALL_FAILED_NO_MATCHING_ABIS` 直接装不上。要减体积用 `--split-per-abi`。

**麦克风后台访问**：Android 11+ 要求前台服务以 microphone 类型
**在前台时启动**——应用内「守护」开关在前台被点击，符合平台要求；
状态栏会出现系统麦克风图标（隐私可见性）。

## 2. 厂商保活（国内生态专项）

国产 ROM 的「省电杀后台」是可靠性最大威胁。应用内置引导页（设置 →
后台保活），按厂商深链直达对应设置页：

| 厂商 | 引导要点 |
|---|---|
| 小米/红米（MIUI/澎湃） | 省电策略→无限制；自启动 |
| 华为/荣耀（EMUI/MagicOS） | 应用启动管理→手动管理三项全开 |
| OPPO/一加/realme（ColorOS） | 关闭应用速冻；允许自启动/关联启动/后台运行 |
| vivo/iQOO（OriginOS） | 允许后台高耗电；自启动 |
| 三星（One UI） | 移出"睡眠中"应用列表；电池→无限制 |
| 魅族（Flyme） | 后台保活 + 自启动 |

深链失败的兜底：`ACTION_APPLICATION_DETAILS_SETTINGS` 应用详情页。
同时申请系统级电池白名单（`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`，
用户主动点击申请，符合 Play 政策的"用户操作豁免"路径）。

## 3. 电源管理策略

### 3.1 三档模式（设置页可切换）

| 模式 | 行为 |
|---|---|
| performance | 全能力：精确闹钟排布上限拉满、守卫常开、无降级 |
| balanced（默认） | 正常运行；低电量自动降级 |
| saver | 暂停随机类任务与守卫，仅保留固定定时；不排布非必要闹钟 |

### 3.2 自动降级规则

- 电量 < 15% 且未充电 → 自动进入 saver（用户模式恢复后自动切回）；
- 守卫"仅充电时启用"选项（FR-53）：守卫耗电大户（麦克风常开），
  移动场景默认关闭；
- 播放期间由 just_audio 持有唤醒锁，播完即释放；
- **性能优先档（`performance`）额外持有常驻 `PARTIAL_WAKE_LOCK`**（FR-84，v1.9.1）：
  锁屏 / Doze 下**不让 CPU 休眠**，使通道 A（应用内 Dart Timer）也能持续运行，
  而不只依赖通道 B（精确闹钟）。**代价是持续耗电**，故默认（balanced）**不持**，
  仅在用户显式选「性能优先」时持有，且引擎停止时**对称释放**（不留耗电副作用）。

### 3.3 电耗预算（目标 NFR-05：日耗 ≤ 3%）

| 开销项 | 估算 | 缓解 |
|---|---|---|
| 前台服务常驻 | ~0.5%/日 | 通知低优先级、无唤醒 |
| 引擎 tick | ~0.3%/日 | 15s 周期仅查内存索引 + 单次 DB 查询 |
| 麦克风守卫 | ~1.5%/日 | 16kHz 单声道；仅充电选项；阈值前置短路 |
| 播放本体 | 与使用强度线性 | 随机时长本身限制单次播放 |
| 原生闹钟 | 每条一次唤醒 | 64 条上限；批量合并 |

### 3.4 保活自检与精确闹钟强引导（FR-84，v1.9.1）

「锁屏后功能全部失效」的常见根因**不在普通权限列表里**：

1. **精确闹钟特殊权限**（`SCHEDULE_EXACT_ALARM`，属系统「**闹钟和提醒**」特殊权限）
   —— Android 14+ 对 `targetSdk ≥ 34` 的应用**默认拒绝**，而它是**通道 B 的前提**；
   被拒时原生 `pushExactAlarms` 直接返回 `denied` 且**不排任何闹钟** ⇒ 锁屏后只剩
   被 Doze 冻结的通道 A，表现为「全部失效」。它**不在**运行时权限弹窗里。
2. **厂商省电策略**（小米 / 红米须设「省电策略 → 无限制」+ 开启「自启动」，见 §2）。

因此应用侧新增三重显性化（对应 FR-84）：

- 设置页「保活与备份」新增**保活自检面板**：精确闹钟 / 电池优化白名单 / 通知 /
  前台服务 **四项状态 ✓✗**，每项带**一键跳转**（精确闹钟 → 系统设置页、
  白名单 → 系统申请框、通知 → 应用设置、引擎 → 首页开关）；
- **首页**保活清单在精确闹钟未授权时**常驻提示行**（比瞬时 SnackBar 更可靠）；
- **开引擎时** `permission_flow.requestAllPermissions` 回传 `exactAlarmDenied`，
  供调用方在可操作位置引导（此前是**空分支** —— 检查了却不做任何事）。

## 4. iOS 方案（平台限制下的最优解）

iOS 不存在"系统级常驻"的合法途径，设计原则是**诚实降级 + 组合覆盖**：

| App 状态 | 触发能力 | 机制 |
|---|---|---|
| 前台 | 完整（含随机时长/音量） | 引擎隔离直接运行 |
| 后台（播放中/守卫中） | 完整 | UIBackgroundModes=audio（播放期间系统不挂起；守卫用 playAndRecord 会话） |
| 后台（空闲） | 计划刷新 | BGAppRefreshTask / BGProcessingTask（夜间） |
| 被用户杀掉 | 通知兜底 | UNUserNotificationCenter 日历触发：到点弹通知，可带 ≤30s 自定义提示音 |

落地要点：
1. BGTaskSchedulerPermittedIdentifiers 注册 `…refresh` 任务 id；
2. 计划物化结果同步注册为未来 64 条本地通知（与 Android 闹钟同构）；
3. App Store 审核关注点：后台音频模式必须名副其实（申请即声明用途），
   守卫模式的麦克风用途字符串需具体明确（已在 Info.plist 声明）。

## 5. 可靠性验证方法（与 docs/09 联动）

```bash
adb shell am kill com.sonicshield.sonic_shield      # 杀进程 → 闹钟自愈
adb shell dumpsys deviceidle step                    # 逐步进入 Doze
adb shell dumpsys deviceidle force-idle              # 强制深度休眠
adb shell dumpsys deviceidle exit
adb shell cmd alarm set-whitelist true com.sonicshield.sonic_shield
adb logcat | grep -E "AlarmWatchdog|flutter"         # 观察看门狗
```

长跑验收（M4）：主流厂商真机 × 开启守护 × 24h，执行成功率 ≥ 99%，
电池白名单 + 厂商引导完成后存活率 ≥ 95%。
