## 4. 代码与任务流分析

### 4.1 主调度链路（健康）

```
Task 定义 ──materialize(now, 48h)──► PlannedEntry ──幂等提交──► occurrences(pending)
   ▲                                                                    │
   │ 续算：pending < 12h                                                  │ executeDue()
   │                                                                     ▼
通道A：引擎 isolate Timer(15s) ──────────────────────────────► runAction()
通道B：AlarmWatchdogReceiver ──startForegroundService──► 引擎 ─►  Playback/TTS/Notify/Record/Vibrate
                                                                        │
                                                              exec_logs（全量审计）
```
链路自洽：occurrences 状态机保证双通道幂等，已由 61 例功能测试与单测覆盖。

### 4.2 远程链路（**断裂**）

```
控制器A                                            端点B
  subscribe  A/cmd  ✔（仅此一条）                    subscribe  B/cmd  ✔
  publish    ────────── B/cmd（密文） ─────────────► 解密 → _dispatch
                                                          │
  ✘ 无任何订阅 ◄──────── B/evt（rc.pong/rc.ack/ ─────────┘ _send() → B/evt
                          rc.status/call.answer/…）
```
**B 把回执发到 `B/evt`，而 A 只订阅了 `A/cmd` —— 回执永远收不到。**
后果：Ping 无往返、状态/任务/定位无回执、指令组无步骤进度与终止回执、
PTT 无回执、**视频通话 `call.answer` / `call.candidate` 收不到 → 永远停在 connecting**。
这解释了 HANDOVER §5「双设备互通未实测」为何始终无法推进。

### 4.3 v1.6 远程中心可达性（**孤儿**）

`git show 1a92111` 的文件清单**不含 `lib/core/router.dart`**。实测：
- `RemoteHomeScreen` / `RemoteConsoleTab` / `RemoteScriptsTab` / `PttTab`
  仅被彼此引用，**全库无第二个引用点**；
- `router.dart:44` 仍为 `GoRoute(path:'/remote', builder: … const RemoteScreen())`，
  即 v1.2 旧总览页；
- 设置页入口 `context.push('/remote')` 同样落到旧页。

→ 控制台（含 device.status / location.get / volume.set / camera.snap 按钮）
**用户永远点不到**；v1.6 的功能实质是未交付状态。

### 9.2 本轮新增缺陷

| 编号 | 级别 | 现象 | 证据 |
|---|---|---|---|
| **BUG-022** | P1 | 冷启动时主 isolate（`_wireRemoteEndpoint` 的 `AppDatabase.open()`）与后台服务 isolate 同时打开同一 DB 文件 → `SQLITE_BUSY: database is locked`，`[sonic_shield][engine]` 记为 unhandled | `adb logcat` 实机日志 |

互斥。端点侧 DB 操作实测正常，**受影响的是后台引擎**。

**BUG-023 修复**：新增 `rcPayloadOf()`（`protocol.dart`）统一取值，控制台与新
「任务」子页全部改用之。

#### BUG-026 专述：`flutter test` 拦不住、只有设备实测能抓的 P0

**现象**：BUG-022 修复（加 WAL/`busy_timeout`）后，**115 个单测全绿、analyze
零问题**，但装到模拟器上启动 → **永久白屏**。

**日志**：
```
DatabaseException(unknown error (code 0 SQLITE_OK):
  Queries can be performed using SQLiteDatabase query or rawQuery methods only.)
  sql 'PRAGMA busy_timeout = 5000'
  → AppDatabase._onConfigure (app_database.dart:53)
  → AppDatabase.open (app_database.dart:30)
  → _wireRemoteEndpoint (main.dart:88)
  → main (main.dart:35)        ← 在 runApp 之前
```

**根因（两层）**：

1. **SQL 层**：`PRAGMA busy_timeout` / `PRAGMA journal_mode` 都会**返回一行结果**。
   Android 插件的 `execute()` 走 `execSQL`（`SQLiteStatement.executeUpdateDelete`），
   遇到返回行的语句直接抛错；而 `sqflite_common_ffi`（单测所用实现）的
   `execute` **容忍**返回行 —— 因此**这个缺陷在 `flutter test` 里永远不出现**。
   → 统一改用 `rawQuery`（对"有行/无行"两类 PRAGMA 都稳妥）。
2. **架构层（更根本）**：`main()` 在 `runApp` **之前** `await _wireRemoteEndpoint()`，
   任何异常都会让 `runApp` 永不执行 —— 用户看到的是白屏，且**无法自救**
   （没有任何 UI 可点）。远程模块是可选附加能力，不该有能力让主应用起不来。
   → `main()` 对远程装配与后台服务注册各自 `try/catch` 降级，只禁用对应模块。

**教训**：
- **单测全绿 ≠ 能启动**。平台插件的 SQL 语义差异、以及"启动路径上的 await"
  这两类风险，只有**装到设备上跑一次**才会暴露。
- 回归锁：`test/db_repository_test.dart` 新增 PRAGMA 断言组（校验 `busy_timeout`/
  `foreign_keys`/`journal_mode` 确实生效），并在注释中**显式写明 FFI 无法复现
  Android 行为**，避免后人误以为已覆盖。

### 17.4 BUG-041 的实质：把"读不到"误报成"不满足"

`networkType()` 的 `unknown` 语义是**无法判定**（原生取不到 `ConnectivityManager`、
或拿到活跃网络却读不出 capabilities；桥不可用时 Dart 侧也回落到它）。
原实现 `if (t == null) return null; return t == 'wifi';` 让 `unknown` 落到 `false`，
而 `false` 在条件层是**"确定不在 Wi-Fi 下"** → 任务被拦下，审计写 `不在 Wi-Fi 下`
（一个我们并不知道的原因）。

这正好违反 `TaskCondition` 类文档写明的约定：

> `inCall` / `onWifi` 传 `null` 表示本平台无法判定……此时按"条件满足"处理……
> 这样不会因为某个平台读不到状态就把全部自动化静默停掉。

**"读不到"被误报成了"不满足"** —— 静默跳过自动化 + 错误审计原因，
两者都是最难排查的形态。修复：`if (t == null || t == 'unknown') return null;`，
并把 `none`（确实没有活跃网络 → `false`）与 `unknown`（读不出来 → `null`）
的差别写进文档。

### 18.3 BUG-042 的实质：原子性 > 速度

旧实现 `for (…) await repo.upsert(t)` 中途失败会**留下半批数据**：设置页提示"导入失败"，

### 18.4 BUG-043：AOT 门禁的"绝对值"在往返受限路径上不成立

**现象**：模拟器冷启后首跑 AOT，`任务 CRUD 500 次: 3340ms / 预算 2000ms → OVER`。

**判据（先怀疑测量，别急着怪机器）**：

| 证据 | 冷启 | 热机 | 上一轮记录 |
|---|---|---|---|
| 每次平台往返 | 2475µs | 1565µs | 1550µs |
| 任务 CRUD 500 次 | 3340ms | 1764ms | 1477–1679ms |

- 同一机器、同一 APK，仅冷暖不同；
- **本轮未改动的** `exec_logs` 逐条路径**同步**劣化 1.55 → 2.475ms/次（1.6×）
  → 机器级劣化，非代码回归；
- 热机复跑落在上一轮记录区间内。

**根因**：成本 ∝ 往返次数，而单次往返成本随机器状态浮动 1.6×；
2000ms 预算热机余量仅 **1.13×** → **冷启必红**。与 BUG-034/036 同源（阈值口径 ≠ 测量条件）。

**修法**：基准测量提前，逐条路径预算改为 `本次实测往返成本 × 调用次数 × 3`。
基准行自身保留绝对护栏（否则"3× 自己"恒真）。归一化后复跑，该次往返成本 2587µs
**比冷启那次还慢**，旧预算仍会红，新预算 7762ms → **PASS**。

### 18.5 本轮经验（可复用）

- **批量 API 的第一收益是原子性，第二才是速度。**
- **证伪的注入点必须落在"修复所改变的那个瞬间"**：原子性要注入在 `commit()` **之前**。
- **AOT 红灯的交叉判据**：看同一次运行里**你没改过的那条路径**有没有同步劣化 ——
  这是区分"代码回归"与"机器状态"最省事的证据。
- **往返受限路径的门禁一律归一化**，绝对值只对纯计算成立。
- 冷启模拟器会**系统性**抬高单次往返成本 ≈1.6×。

### 19.3 BUG-044：成本随任务数线性增长

一次条件评估读 4 次平台状态（电量/充电/通话/网络），每次 = **一次平台通道往返**。
`executeDue()` 一轮遍历所有到期计划 → **4N 次往返**：
1 个任务 ≈12ms 可忽略，**50 个 ≈580ms，500 个 ≈5.8s**，
且全部花在**重复读取同一个物理环境**上。

**修法**：把"读平台"与"判定条件"解耦 ——
`readConditionEnv()`（读一次）+ `conditionFailedIn(task, env)`（纯判定），
两个遍历循环（`executeDue` / `onSoundEvent`）各持一个 `RoundConditionEnv` 快照。
**`now` 刻意不进快照**（本地时钟无平台开销，实时取值让时段窗口更准）。

`RoundConditionEnv.readCount` 是"每轮只读一次"的**可断言出口** ——
没有它，这个优化只能靠读代码相信。

### ② 本轮闭环

**BUG-052（P2，验证工具级）—— 探针用错密钥身份 + 以"密文到达"冒充"链路闭环"**

`tool/rc_probe.dart` 原本这样派生**命令**密钥：

```dart
final cmdKey = await RcCodec.deriveKey(selfCode, '$selfId|cmd');   // ❌ 自身身份
```

而协议（docs/14）规定密钥按**接收方身份**派生，端点侧是：

```dart
final key = await RcCodec.deriveKey(ownCode, '$ownId|cmd');        // 端点身份
```

两者**永不相等** → 端点 `RcCodec.decode` 返回 null → `_handleRaw` **静默 return**
（协议有意如此，见 BUG-021 注释）。于是**命令从未被处理过**。

更糟的是**通过判据**：原探针只检查"`evt` 主题上出现了任意密文"，
而端点每 **60s** 发一条 `rc.heartbeat` 到自己的 evt 主题 ——
20s 的观察窗有约 1/3 概率落进心跳周期，**心跳足以让判据恒真**。
上一轮交接据此宣布的"`ping` 探针 ✓ 全链路闭环"就是这么来的。

修复：

| 项 | 修复前 | 修复后 |
|---|---|---|
| 命令密钥 | `(selfCode, '{selfId}\|cmd')` | `(**endpointCode**, '{endpointId}\|cmd')` |
| 回执判据 | 任意密文到达 | **解密成功 + 类型对 + `for` 与命令 id 一致** |
| 心跳 | 会被当成回执 | **显式剔除**，另行计数 |
| 失败输出 | "无回执" | 附带"密文 N / 心跳 N / 解密失败 N"，区分**离线**与**密钥不匹配** |

**CHANGELOG 章节顺序 + 版本四处同步（as-found 修复）** ——
`[1.8.0-alpha]` 从 `[1.7.2]`/`[1.7.1]` 之间移回顶部；pubspec / `AppMeta.version` /
CHANGELOG 顶部 / HANDOVER 标题四处对齐。

### ⑧ 本轮经验（可复用）

- **`WITH_DEVICE=1` 会污染压测层**：它把**开着的模拟器**一起带进功能/压测层，

  **红灯先怀疑测量与阈值**这条老规矩本轮又救了一次。

### ⑨ 追加闭环：压测层假红 —— BUG-053（测量方式缺陷）

**现象**：`bash scripts/gates.sh` → `EXIT=1`，压测层 `GT-07` 红：

```
GT-07 outbox 200 条 + 二次 drain 幂等 ≤ 400ms
  Expected: a value less than or equal to <400>
    Actual: <455>
```

**先按老规矩怀疑测量**（本轮未改动任何 `lib/` 业务代码，只改了文档）：
单独跑 `GT-07` **6/6 全绿且 <1s**；连跑三次全套件 → **2 绿 1 加载错**。
**同一份代码红绿翻转** → 判定为阈值/测量问题。

**根因（两处叠加，都在测试自身）**：

1. `GT-07` 用**裸 `Stopwatch` 单次采样**，而 `test/performance_v2_test.dart`
   文件头与 `test/perf_bench.dart` 都明确要求
   "统一用 `benchMs`/`benchMsAsync`（预热 + 取最小值）"。
   单次采样测的是 **JIT 编译 + GC + 调度噪声**，不是该路径成本。
2. `GT-07` 的路径是**往返受限**的（200 次 `enqueue` = 200 次
   `prefs.setString` 平台往返 + 对递增列表整体 `jsonEncode`），
   而它却用了**紧的绝对阈值 400ms** —— 与项目自己的规矩
   「往返受限路径的预算必须自归一化」相悖。

**实测（改造后，`benchMsAsync` = 预热 3 + 取 5 次最小值）**：

| 场景 | min-of-5 |
|---|---|
| 全套件负载下 | **51ms** |
| 单独跑 | **53ms** |

→ min-of-5 **高度可复现（两场景差 <4%）**；而旧的单次采样在负载下是 **455ms**，
**同一份代码被噪声放大约 9 倍**。

**修复**：改用 `benchMsAsync`，阈值按本套件约定取「实测基线 × 3」→ **160ms**。

| | 修复前 | 修复后 |
|---|---|---|
| 测量方式 | 裸 Stopwatch，单次采样 | `benchMsAsync`（预热 3 + min-of-5） |
| 阈值 | 400ms（≈ 基线 × 7.8） | **160ms（= 基线 51ms × 3）** |
| 稳定性 | 全套件下 ~50% 假红 | 两场景 51/53ms，**不再翻转** |
| 严格度 | 松（7.8× 余量）却仍假红 | **收紧约 2.5 倍**且不再假红 |
| 断言 | `d1.length` / `d2.isEmpty` | `d1Len == 200` / `d2Len == 0`（等价，闭包内取长度） |

**证伪（护栏不是恒真）**：在 `RemoteStore.enqueue` 注入
「按已有条数重复写盘」（把 1 次往返放大成 O(n) 次）→ `GT-07` 红，
`Actual: <4595>`（预算 160ms）→ 还原后 `grep -rc "PROBE-"` = **0**。

**遗留观察（未改，诚实登记）**：同文件 `GT-01/02/03` 也是**异步 + 裸 Stopwatch**
（`ExportCrypto` 的 KDF 12 万次，预算 4000/4000/1500ms）。四轮实测未抖，
且预算余量远大于 4×，故本轮**不动**；若日后抖动，按 GT-07 同样方式改造。

### ⑪ 追加经验

- **"假红"和"假绿"是同一类问题：判据本身没被验证过。**
  本轮前半段修的是**假绿**（探针以"任意密文到达"冒充链路闭环，被 60s 心跳喂饱），
  后半段修的是**假红**（压测用例用单次采样冒充路径成本，被 GC/调度噪声喂饱）。
  **共同点：判据测的不是它声称要测的东西。**
  凡看到"同一份代码时红时绿"或"只要出现 X 就算成功"，**先验证判据本身**。
- **测量方式要与被测路径的性质匹配**：纯计算 → 单次采样尚可（噪声占比小）；
  **往返受限 / 有 GC 压力 → 必须预热 + 取最小值**，否则测的是噪声。
  本项目的 `test/perf_bench.dart` 早已把这个道理写成工具，**问题是有用例没接上它**。
- **阈值"松"不等于"不假红"**：旧阈值 400ms 已是基线 7.8 倍，照样红 ——
  因为**噪声放大倍数（9×）比余量（7.8×）还大**。
  **余量必须与噪声幅度比，不是与基线比。**
- **文件头写的规矩，要有人在代码里执行**。`performance_v2_test.dart` 头部
  白纸黑字要求"统一用 benchMs/benchMsAsync"，而 GT-07 违反了一整个版本没人发现 ——
  **约定只有变成门禁（或至少被扫描）才成立**，这与"三向覆盖靠人记就是下一个 BUG"同源。
- **提交前的"陈旧值扫描"应当机器化**：本轮是靠人工 grep 才逮到 §1/§3 的陈旧值。
  可固化为：`grep -n "旧版本号\|旧用例数\|旧 §编号" HANDOVER.md docs/00-*.md`。
- **真机阻塞点会"换位置"**：第十五轮是"开关关着"，第十六轮是"弹窗没人点"，
  本轮是"设备根本不在 `adb devices` 里"。**报告阻塞时必须写清当前卡在哪一层**，
  否则下一会话会去修一个已经不存在的问题。

### ⑫ 互通复验 + 一个会伪装成"应用启动 hang"的环境陷阱

**复验结果（冻结代码 + 冷启动模拟器 + 真 debug 包）**：仿真多机连通 **9/9 通过**
（8 条单命令 + 远程任务 CRUD 8/8）；`evt 密文 24（其中心跳 1、解密失败 0）`、

**但复验一开始是失败的，而且症状极具误导性**：

```
装上 build/app/outputs/flutter-apk/app-debug.apk → monkey 拉起
→ 应用**永久停在 Flutter 闪屏**（截图确认）
→ databases/ 目录从未创建 → AppDatabase.open() 没跑完
→ /proc/net/tcp 里端点零连接 → 探针必然全灭
```

**A/B 对照排除了"注入 prefs 导致"**：`pm clear` 后不带任何 prefs 启动，

**真因**：`build/app/outputs/flutter-apk/app-debug.apk` 在跑过
`flutter test integration_test/…` 之后，**已被替换成 integration_test 的
"测试入口包"** —— 它的 Dart 入口是测试文件而不是 `lib/main.dart`，
`monkey` 拉起后它在等 driver 连接，表现为"闪屏不动"。

| 判据 | 真应用包 | integration_test 测试包 |
|---|---|---|
| 体积 | **245 MB** | **144 MB** |
| 用 `monkey` 拉起 | 正常进入守护仪表盘 | **永久闪屏** |
| `databases/sonic_shield.db` | 会创建 | 从不创建 |
| 恢复方式 | — | `flutter build apk --debug` 重新构建 |

**交叉验证**：同一台模拟器上 `flutter test integration_test/app_smoke_test.dart`
→ **4/4 全绿（23s）**（该路径会用测试包，所以能跑）；
换成真包 + `monkey` → 立刻 `databases/` 出现、
`/proc/net/tcp` 出现 **ESTABLISHED(`01`) → broker.emqx.io:1883**。

> **教训**：`app-debug.apk` 这个**路径**不是"真应用包"的同义词 ——
> 它的**内容**取决于最后一次构建它的是谁（`flutter build apk` 还是
> `flutter test integration_test` / `flutter drive`）。
> **凡"应用起不来"的诊断，先 `ls -l` 看体积**：144MB 就别再查代码了。
> 这个陷阱能把人骗去读 `main.dart` 的 await 链、怀疑 sqflite、怀疑 prefs 注入 ——
> 本轮三条全试过，**真因在构建产物层**。

### ① 修的是什么（BUG-050 的两个半边）

| 半边 | 修前 | 修后 |

| 主叫**无限等待** | 发出 `rc.call.invite` 后**没有任何超时**。被叫未开自动接通、或 invite 被静默丢弃时，主叫**永远停在"连接中…"**，且没有任何"未接"反馈 | 45s 未应答 → 结束通话并给出 **"对方无应答"** |
| `rc.call` / `rc.call.missed` **App 内无人消费** | 只有 `tool/` 的桌面 E2E 工具看得到 → 主叫看不到"对方振铃中"，也收不到被叫判定的"未接" | `CallService.attach(events)` 消费两者；UI 显示"对方振铃中…"并弹出结束原因 |
| `RcEvt.callMissed` 是**死常量** | 从不发出、无人消费 | 被叫振铃超时后由**端点**发出（`_wireCall()`） |

### ② 手法：判定链抽成纯函数（沿用 `remote_playback.dart` 范式）

新增 `lib/remote/call_lifecycle.dart`（纯逻辑，无 WebRTC / Timer / 平台通道依赖）：
超时上限与判定、`rc.call` 的 `state` 解析、结束原因 → 用户文案、是否该弹提示。

**为什么必须抽出来**：这段逻辑原先埋在 `CallService`（依赖 `flutter_webrtc` + 真实信令）
里，**宿主机无法实例化 → 整整一个版本没被任何用例覆盖过**。

`CallService` 只剩薄适配层：`Timer` 启停、信令收发、`Stream` 广播。

### ③ 三条**不许猜**的规则（本轮的设计要点）

| 场景 | 错误做法 | 本轮做法 |
|---|---|---|
| `rc.call` 的 `state` 是未知值 | 猜一个状态去改本地阶段 → 协议加一个新 state 就会**挂断所有在途通话** | 归 `unknown` 并**什么都不做**（不取消等待、不结束通话） |
| `call.end` 的 `reason` 是未知值 | 默认成 `hangup` → 把"占线"显示成"已挂断"，用户以为是对方主动挂了 | 归 `remoteEnded`，文案保持中性 |
| 本端点了"拒接" | 复用 `rejected` 的文案 → 拒接的人自己看到 **"对方已拒接"**，以为被拒的是自己 | 新增 `CallEndReason.declined`（'已拒接'）与 `rejected`（'对方已拒接'）分开 |

**收尾副作用不得覆盖真正的原因**：`_pc.close()` 会让 `onConnectionState` 变 `closed`
并再调一次 `_teardown()` —— 那条路径必须传 `reason: null`，否则会把"对方无应答"
冲成空白。`_teardown({CallEndReason? reason})` 用**可空参数**表达"这次没有原因"。

**已接通后绝不能报"未接"**：`timedOutMeansMissed` 必须带 `!answered` 守卫，
否则用户会在**通话进行中**看到"对方无应答"。

> 3000ms 对 900ms 看着有 3.3× 余量，5× 的噪声照样打得穿。

> ① 任何用例都不得用 `runs: 1`；② 余量与噪声幅度比；③ **不要并发跑性能层**

## §26. 第十七轮**续三**（2026-09-20）：被叫手动接听闭环 + 「自动接通」开关失效（BUG-056）

> 本轮做的是 §25 ⑩ **建议下一步的第 1 条**（"被叫手动接听闭环"）。
> 开工时以为这是"代码已就绪、只差接线"的一条 —— 结果它下面压着一个**隐私级缺陷**。

### ① 修的是什么（BUG-056：隐私开关静默失效）

**症状**：设置页的「自动接通」开关**关掉也照样自动接通**。

`endpoint_service._handleCallInvite` 把 `onManualRing` 实现成**立刻
`acceptIncoming`**（注释写着"v1.4 简化"）：

```dart
// 修前（BUG-056）
await CallService.instance.onIncomingCall(msg.payload, peer, _store!,
    onManualRing: (payload, p, s) => acceptIncoming(payload, p, s, video: video));
```

**为什么这是隐私问题而不是"功能没做完"**：那个开关是使用者**唯一**能表达
"别自动接我的电话"的地方（设置页文案：*仅限已配对设备呼入时自动接通，
用于家人守护*）。开关失灵意味着**来电被静默接通、摄像头/麦克风被打开**，
而使用者以为自己已经关掉了。

> 这类缺陷的特征：**开关存在、有 UI、能保存、读得到值 —— 但值没人用。**
> 与 BUG-048（`sound.play` 点名被静默替换）同族：**"静默降级"**。

### ② 顺带挖出的前提缺陷：被叫**根本没有来电界面**

即使把 `acceptIncoming` 删掉、改成"振铃等用户"，用户**也接不到电话** ——
因为来电 UI 原先挂在**通话页**上（`OverlayEntry` 需要一个**已挂载的页面 context**），
所以**只有用户已经站在通话页上才可能看到来电**。

两个必须一起修的点：

| 点 | 修前 | 修后 |
|---|---|---|
| 挂载位置 | 通话页（`OverlayEntry`） | `MaterialApp.builder` 上的 `CallOverlayHost`，**与当前路由无关** |
| 树结构 | 直接 return 通话视图 | **`Stack`**，保住 `child`（直接 return 会**卸载 Navigator**） |

⚠️ 另外两个容易踩的细节：
- `alignment: Alignment.topLeft` 必须是**非方向性**的 —— `builder` 在应用根部，
  **不保证有 `Directionality`**（用 `topStart` 会在某些路径上抛异常）。
- `scaffoldMessengerKey` 要抽到 `lib/core/app_keys.dart`：否则
  `app.dart ↔ call_incoming_overlay.dart` **import 成环**。

### ③ 决策抽成纯函数：`calleeActionFor`

```dart
enum CalleeAction { autoAccept, ringUser, rejectBusy }

CalleeAction calleeActionFor({required bool autoAnswer, required bool inCall}) {
  if (inCall) return CalleeAction.rejectBusy;
  return autoAnswer ? CalleeAction.autoAccept : CalleeAction.ringUser;
}
```

**为什么必须是穷尽 switch 而不是 `if/else`**：`CallService` 的调用点写成
`switch (action) { ... }`（**无 `default`**）→ 将来新增 `CalleeAction` 值会
**编译报错**，而不是静默落进"振铃"这条臂。见 §26⑤ 的 CA-07 故事。

**默认分支必须是 `ringUser`**：把"读不到开关"或"将来新增分支"的兜底做成
`autoAccept`，等于把"隐私开关默认关闭"这件事**做反**。

### ④ 回归锁：`test/call_lifecycle_test.dart` **+11 例**（CA-01…CA-11，共 31 例）

| 组 | 用例 | 断言 |
|---|---|---|
| CA 被叫接听动作 | CA-01…CA-04 | 四个（开关 × 占线）组合全覆盖；**默认值必须是 `ringUser`** |
| | CA-05 / CA-06 | 来电文案带对方名字并区分视频/语音；只有振铃才能接听 |
| 接线锁 | CA-07 | `CallService` 的被叫分支**必须走 `calleeActionFor`**（不得另写一套判断） |
| | CA-08 | 【回归锁】**来电处理里不得出现 `acceptIncoming`** |

## §27. 第十七轮**续四**（2026-09-20）：BUG-054 闭环 —— AOT 基准护栏改为**同类独立探针**归一化

> 本轮做的是 §26 ⑨ **建议下一步的第 1 条**（"BUG-054 改成自归一化预算"）。
> 判据在 §26⑦′ 已被实测钉死，本轮负责落地 + 上锁。

### ① 缺陷本体：基准**自己给自己当基准**

```dart
// 修前（integration_test/perf_nfr_test.dart）
for (var r = 0; r < 2; r++) { /* 5000 次 logs.append */ }
final perCallUs = singleMs * 1000 / 5000;   // ← 基准 = 它自己的测量值
int budgetFor(int calls) => (perCallUs * calls / 1000 * 3).round();
report('exec_logs 5000 条**逐条**写入 + recent', singleMs, 20000);  // ← 硬编码
```

- 被它归一化的用例**自洽**；但它**自己**不能用 `budgetFor(5000)`（`≡ 3 × singleMs`，恒真）。
- 于是只能硬编码 `20000ms`（按"冷启 2.475ms/次"标定），而实测可到 **4839µs/次**
  → 余量在 **2.0× ↔ 0.83×** 摆动，**跨 1.0 就红**。

> **本轮当场复现**：新探针版第一次跑 AOT 时该用例实测 **26658ms** ——
> 旧护栏（20000ms）下**这一跑就是红的**。

### ② 修法踩了两个坑，第二个是修的过程中才发现的

**第一步（错）**：探针换成 `tasks.get(<缺失 id>)` × 200（纯 1 次 SELECT = 1 次往返）。
→ 它**低估**了写入路径的单位成本（写入要 2~3 次往返）→
`任务 500 条逐条写入` 实测 **3534ms / 预算 3728ms = 1.05×**，
**等于把 BUG-054 搬到了另一条用例上**。

**第二步（对）**：探针换成**与被护栏用例同类**的 `logs.append` × 200（带 20 次预热、min-of-3）。

```dart
const kProbeCalls = 200;
for (var i = 0; i < 20; i++) { await logs.append(/* 预热 */); }
final perCallUs = probeMs * 1000 / kProbeCalls;
int budgetFor(int calls) => (perCallUs * calls / 1000 * 3).round();
report('exec_logs 5000 条**逐条**写入 + recent', singleMs, budgetFor(5000));
```

> ⚠️ **通用教训（可复用）**：**归一化的单位必须与被护栏的工作量同量级。**
> 用一个"更便宜的操作"当单位，3× 安全系数会被**结构差异**吃掉 ——
> 表面上"自归一化了"，实际余量比硬编码还薄。

### ③ 这条护栏的语义（写清楚，免得被误读）

它断言的是**规模不变性**：5000 次调用的**每次成本**不得超过 200 次调用的每次成本的 3×。
**均匀变慢抓不住**（探针与被护栏用例一起变），但**超线性退化**（如丢索引 → append 变 O(n)）会被抓住。
**这不是绝对性能验收** —— 绝对值随机器漂，余量不随机器漂。

### ④ AOT 实测（两次跑的对比本身就是证据）

| 用例 | 第 1 次（SELECT 探针，冷机） | 第 2 次（同类写入探针） | 余量 |
|---|---|---|---|
| 基准单次成本 | 2485µs（纯往返） | **1405µs**（含 INSERT） | — |
| exec_logs 5000 条逐条 | 26658ms | **6568ms** | **3.21×** |
| 任务 CRUD 500 次 | 4189ms | **1669ms** | **2.53×** |
| 任务 500 条逐条写入 | 3534ms | **1287ms** | **1.64×** |
| AOT 总体 | 6/6 | **6/6** | — |

**绝对值差 4×（26658 → 6568ms），余量都在安全侧。**
最薄的是 `任务 500 条逐条写入` **1.64×**，成因是**结构性**的
（task upsert 单次成本 ≈ log append 的 1.96×），与机器状态无关。

## §28. 第十七轮**续五**（2026-09-20）：`rc.script` 接进 App（缺口登记表可闭环项清零）+ BUG-057

### ④ BUG-057：压测层「同一份工作量、两个预算」

跑门禁时压测层红：`GT-01` 6213ms/4000ms、`GT-03` 3737ms/1500ms。

**先怀疑测量**，找到真凶：`TaskStop` 报"已终止"的**端口扫描任务并没有真的死** ——
`/usr/bin/xargs` 仍在 fork 子进程（`ps` 见 24 个残留）。杀掉后 GT-01 恢复，
**但 GT-03 依然红**（3229ms）→ 两个独立问题。

预算形状的证据链：

1. `encrypt`/`decrypt` 都走 `Pbkdf2(iterations: 120000)`；错密码只是最后 GCM 校验失败，
   **KDF 一次都不会少跑** → 三条用例工作量完全相同；
2. 用**把阈值临时置 0** 逼出干净机器实测：GT-01 **1128ms**、GT-02 **1049ms**、GT-03 **1127ms**；
3. 于是 GT-03 的 1500ms 只剩 **1.33×** 余量，兄弟用例是 3.5×+；
4. 三条用例**标题都写「≤ 4s」**，只有 GT-03 的断言写 1500 —— 断言与自己的标题矛盾；
5. CPU 争用把耗时抬到 2.9× → **1.33× 的余量低于噪声幅度**，GT-03 必然最先红。

**修法**：抽 `const kdfBudgetMs = 4000` 三条共用（依据写进注释），并上锁
`perf_budget_consistency_test.dart`（PB-01 同组预算必须唯一 / PB-02 必须是命名常量 /
PB-03 红灯必须自带实测值 / PB-04 不得低于基线×3）。

⚠️ **不是放宽阈值**：需求没变（4 秒），改的是**形状** ——
把"拍脑袋的 1.33×"对齐到"与兄弟用例一致的 3.5×"。绝对验收仍在 AOT 层（NFR-04）。

### ③ 证伪：厂商弹窗在无线调试下**依然存在**

上一轮交接（§28 ⑨ 第 2 条）本身写得谨慎 ——"**换传输不必然消除厂商弹窗，必须实测**"，
**但本轮执行时我先基于一次 `adb install -r` 的成功就下了"绕过了"的结论**，这是错的。

**实测（截图铁证）**：即使走无线调试，弹窗照旧出现，**标题仍叫「USB 安装提示」**：

```
USB 安装提示
正在通过 USB 安装此应用，是否继续？
○ 拒绝后下次安装不再提示
[继续安装]   [拒绝（10）]      ← 10 秒倒计时，默认高亮「拒绝」
```

> 📌 **教训（与 §16 同一条）**：`INSTALL_FAILED_USER_RESTRICTED: Install canceled by user`
> 里的 "by user" **必须截图抓现行**再下结论。本轮第一次的"成功且无弹窗"，
> 真正原因是**使用者当时在设备旁点了「继续安装」**（抓屏显示弹窗 6 秒内消失，
> 而倒计时是 10 秒 → 有人点了）。**单次采样 + 20 秒间隔的 `mCurrentFocus` 观察，
> 不足以证明"没有弹窗"。**

### ④ 真实边界：**全新安装**弹窗 / **覆盖安装**免弹窗

| 设备上是否已有该应用 | `adb install -r` 语义 | 结果 |
|---|---|---|
| **无** | 全新安装 | ❌ 弹窗 → 10s 默认拒绝 → `INSTALL_FAILED_USER_RESTRICTED` |
| **有** | 覆盖安装 | ✅ `Success`，**全程无弹窗**（安装 15.1s） |

- "全新 → 失败"实测 **3 次**（门禁冒烟、门禁桥接、手动 `-t -r`）。
- "覆盖 → 成功且无人干预"实测 **1 次**（`app_smoke_test` 4/4）。
- 这解释了 `flutter test integration_test/…` 在真机上**时好时坏**：取决于**跑之前设备上有没有应用**；
  而 `flutter test` **跑完会卸载** → 下一次又退回"全新安装"。

**可用工作流**：**人工点一次「继续安装」** → 此后设备上有应用时，设备测试都走覆盖安装（可自动）。
`flutter test --[no-]uninstall`（`--no-uninstall` = 跑完保留应用）是这条链的关键拼图，
**但本轮未实测其保留效果**（要验证它得先完成一次成功安装，而首次恰好卡在弹窗）→
**只记"参数存在、语义为保留应用"，不声称已验证。**

### ⑤ 门禁工具改进：失败必须落盘

第一次真机门禁设备层只留下一行 `No tests were found.`，**看不到 Gradle/安装阶段**
（脚本只 `tail -1`）→ 无法定位，且**已无法回溯**。

新增 `fail_dump()`：各层失败时把**完整输出**写入 `${GATE_LOG_DIR:-/tmp}/gates_<标签>.log`
并回显尾部 15 行。**立刻见效** —— 第二次门禁直接给出
`Failure [INSTALL_FAILED_USER_RESTRICTED: Install canceled by user]`，根因（④）由此拿到。

> 📌 与既有的「构建落盘，测试转换」同一条原则：**门禁的失败输出是诊断资产，`tail -1` 等于扔掉它。**

### ⑥ 功能层时间敏感假红：AHW-05 / AHW-06

`AHW-05` 断言 `'04:5'`（5 分钟 TTL）、`AHW-06` 断言 `'00:4'`（45 秒 TTL）——
**窗口都只有 5 秒**，而 `_mmss(s.remaining)` 读的是**真实墙钟**
（该文件注释本来就写明 FakeAsync 不虚拟 `DateTime.now()`）。
功能层一次跑 465 例，慢机器/并发下 `pumpWidget` 一旦 >5s 就跨过边界 → `Found 0 widgets`。

**修法**：改**格式断言** `RegExp(r'剩余 \d\d:[0-5]\d')` + **宽窗口数值断言**（`s.remaining`），
既保住原意（mm:ss / 不越界）又不依赖具体秒数。验证：该文件 **7/7 通过**。

### ② 门禁脚本 `scripts/gates.sh` 设备层大改（做了什么 / 为什么）

| 新增 | 作用 | 为什么必须 |
|---|---|---|
| `ensure_device_app()` | 跑设备用例前先确保**设备上已有应用**；没有就先 `adb install`（引导人工点一次确认框，`PREINSTALL_TRIES` 次重试） | 厂商弹窗的触发条件是"设备上有没有这个应用"（§29④）。不预装 → `flutter test` 自己的安装必然撞弹窗 |
| 设备用例一律加 `--no-uninstall` | 跑完**保留应用** → 下次直接走**覆盖安装**（无弹窗） | `flutter test` 默认 `--uninstall`，跑完卸载 → 下次又退回"全新安装" → 每个用例文件都要人工点一次 |
| `device_alive()` / `is_transport_failure()` / `run_device_test()` | 把"传输链路掉了"从"用例失败"里**分出来** | 见 ④：真机无线调试会掉线，报 `device '…' not found` / `Unable to start the app`。读成"桥接用例失败"就是**假红** |
| `BLOCKED` 计数器 + **退出码 3** | 代码全绿但有环境阻塞（**未执行 ≠ 失败**） | 原来只能给 EXIT=1，和"代码回归"混在一起 |
| `ONLY_DEVICE=1` / `SKIP_PREINSTALL=1` / `APP_ID=` / `PREINSTALL_TRIES=` | 设备层可独立复跑、分支可被证伪 | 迭代设备用例不该重跑 465 例宿主测试；`APP_ID` 可覆盖才能**验证 BLOCKED 分支真的会红** |

> 📌 **退出码语义**：`0`=全绿；`1`=有门禁失败（代码回归）；`3`=代码全绿但有**环境阻塞**。

### ④ 新发现：真机**无线调试链路不持久**（本轮最重要的一条环境事实）

第一次设备层全绿之后，**紧接着再跑一次**，桥接用例红了：

```
Running Gradle task 'assembleDebug'...   68.6s
Installing build\app\outputs\flutter-apk\app-debug.apk...   85ms   ← 85ms = 根本没装
Error: ADB exited with exit code 1
adb.exe: device 'adb-960f853-Kmi5Mk._adb-tls-connect._tcp' not found
Failed to load "…/native_bridge_test.dart": Unable to start the app on the device.
```

排查：

| 检查 | 结果 |
|---|---|
| `adb devices` | **空** |
| `adb mdns services` | **空**（mDNS 广告也没了） |
| `adb kill-server; adb start-server` | daemon **本来就不在跑**了 → 重建后 emulator 出现、真机仍无 |
| TCP 握手 `192.168.2.11:39715 / :38659 / :5555` | **三个端口全部 refused（10061）** |

**结论**：不是"桥接用例坏了"，而是**设备侧无线调试已关闭**（或设备离开了该网络）→
链路消失，`adb server` 也一并死掉。**再次使用需要设备侧重新开启无线调试**。

> ⚠️ **这条如果不单独判据化，下次一定被读成"桥接用例回归"** —— 因为报错文本长得像
> "应用起不来"。已固化为 `is_transport_failure()`（匹配 `device '…' not found` /
> `Unable to start the app` / `ADB exited with exit code`）→ 归入 `BLOCKED`（退出码 3）。
> 📌 与既有的"**红灯先怀疑测量与阈值**"同族：**环境红灯要和代码红灯分开计数**。

### ⑤ 顺带修掉脚本自身的两个 bug（都是本轮新引入、当场发现）

1. **字符串里的反引号被当命令替换执行**：
   `echo "…`input tap` 代点不可用…"` → 实际执行了 `input tap`，
   报 `scripts/gates.sh: line 139: input: command not found`。
   → 去掉反引号。（**"我以为只是文案"，但 shell 不这么认为**。）
2. **`adb install … | tail -1` 把失败原因吞成空行**：
   第一次预装 3 次尝试的输出**全是空行**，看不到任何原因 ——
   **这正是本项目早就总结过的 `tail -1` 教训**（§29⑤ 的 `fail_dump`），
   结果自己在新增代码里又犯了一次。
   → 改为捕获完整输出、无输出时显式打印 `[adb install] 无输出（RC=…）`。
   修完立刻可见：`adb.exe: device '…' not found`。
