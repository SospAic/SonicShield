## 1. 现状盘点：配对流程与失败态

> ⚠️ **本节是整改前的只读盘点（第 34 轮）。** 截至第 35 轮：
> **P0-1 / P0-2 已闭环**（识别去抖 + 停流、权限分级引导 + 面板内手输出口均已落地）；
> **P0-3 / P0-4 本轮实施中**（由另一 Agent 落地）。
> 下表"现状"列请按此口径阅读，逐项状态见 §3 整改清单。

### 1.1 URI 协议（protocol.dart:381-397）

```
sonicshield://pair/{deviceId(16位hex)}/{name(urlencoded)}/{code(8位Base32)}
```

- 配对码：8 位 Crockford 风格 Base32（去 0/1/I/L 等易混字符），展示带连字符 `XXXX-XXXX`，约 40bit 熵（protocol.dart:344-349）。
- `parseUri` 校验：前缀、三段字段、ID 16 位、码 8 位；码剥连字符转大写（protocol.dart:393-394）。
- 配对码**持久且永不过期**（`ensurePairingCode` 首次生成后固定，pair_qr_screen.dart:82-83），支持多台控制器重复扫码。
- 有轮换函数 `rotatedPairingCode`（protocol.dart:354-369），但 **UI 无任何入口**（全库 grep 无调用方）。

### 1.2 流程步骤与失败态（pair_qr_screen.dart）

| 步骤 | 行为 | 失败态与现状 |
|---|---|---|
| 进页加载 | 自动生成/读取身份与配对码，渲染 `QrImageView`（:75-90, :169-188） | 加载中仅一个 `CircularProgressIndicator`，无失败兜底 |
| 展示本机码 | 二维码 + 设备名 + `SelectableText` 配对码（:175-185） | 配对码可选可复制，但**页面自身无「复制」按钮**；无「刷新/轮换配对码」 |
| 点「扫描对端二维码」 | 请求相机权限（:210-219） | **权限被拒 = 一条 SnackBar「需要相机权限进行扫码」后结束**，无分级引导、无跳系统设置、不提示手输兜底 |
| 进入扫描 | `MobileScanner` 覆盖 420px 区域（:145-159） | **没有任何去抖/暂停**：`onDetect` 每帧触发，同一码会反复走 `_pairFromUri`；无扫描框/暗光提示/手电筒 |
| 识别 | 前缀过滤 `sonicshield://pair/`（:152） | 非声盾码被**静默忽略**——用户对准了别家二维码会毫无反馈，看起来就是「扫不了码」 |
| 解析+落盘 | `parseUri` → `addPaired` → 刷新订阅（:104-120） | 解析失败仅结果卡一行文字；**落盘发生在对端确认之前**（先配对再通知，R-2 的 `notifyPeerOfPairing` 在 :129 才发） |
| 双向补齐 | `notifyPeerOfPairing` → 端点回执（:129-135） | 8 秒超时未确认时 `_resultWarn` 标红（`PairConfirmOutcome.message`），但**没有任何重试按钮** |
| 结果展示 | 结果卡（:195-206） | 成功文案含对端 ID+名字；失败文案单一 |

### 1.3 手输兜底现状（关键确认结论）

- **手输入口存在，但不在扫码页**：在 `remote_screen.dart:385-389` 的「手输」按钮 → `_addPairDialog`（:157-199），要求用户**同时手输 16 位设备 ID + 设备名 + 8 位配对码**，三项全对才能配对。
- **不好用**：16 位 ID 只能在对端页面上看/复制（对端是另一台手机，无剪贴板同步），人工转录 16 位 hex 极易出错；校验失败只有一条 SnackBar，不指明哪个字段错。
- **扫码页内没有任何手输/相册入口**：扫不了码的用户被卡死在扫码页，必须自己发现要**退出本页**去远程遥控页找「手输」。

### 1.4 既有测试锁定（test/pair_qr_screen_test.dart）

- PQR-01/02：身份与配对码生成、持久化（二次进入同码）。
- PQR-03：权限被拒 → SnackBar + 不进扫描态 + 「我的二维码」不被顶掉。
- PQR-04~08：`parseUri` 边界（前缀、16 位 ID、8 位码、字段数、归一化）。
- **注意**：任何整改不得破坏 PQR-02（配对码持久 = 已配对设备不失联）与 PQR-08 语义。

## 2. 行业对标与本项目落法

### 2.1 微信/支付宝扫码

| 行业做法 | 本项目落法 |
|---|---|
| **多帧识别去抖**：识别成功即停流/遮罩，避免一码多次触发 | `_pairFromUri` 入口加 `_pairing` 状态锁 + 识别成功后 `MobileScannerController.stop()`；落盘前先「请确认配对」 |
| **暗光手电筒**：检测亮度低自动点亮手电筒按钮 | `MobileScanner` 有 `torchEnabled`/曝光事件；P1 做「扫描页常驻手电筒开关」，P2 做自动提示 |
| **相册识码兜底**：扫不了活码可从图库选图识别 | mobile_scanner 无内置图片解码；用 `image_picker` 选图 → `zxing`/`mobile_scanner` 的静态解析（或 `MobileScannerController.analyzeImage`）→ 走同一 `_pairFromUri`。成本低、价值高（用户反馈「扫不了」的很大比例是屏幕反光/贴膜/低分辨率屏对屏） |
| **扫码成功即时反馈**：振动 + 音效 + 结果页 | `HapticFeedback.mediumImpact()` + 结果卡强化；当前只有文字卡片 |

### 2.2 Matter（智能家居配对）

| 行业做法 | 本项目落法 |
|---|---|
| **短码人工兜底**：扫不了 QR 就手输 11 位配对码，一样能配 | 本项目的 8 位配对码 + 16 位 ID 拆得太散。对标做法：**扫码页内置「手动输入配对码」入口**，只需要输**码**（8 位），ID 从对端通过配对请求带回——协议上 `pair.request` payload 已含 `deviceId/name`，端点侧收到后即完成双向登记。这需要一个小协议增强（先发码、对端回 id），属于把「物理在场 = 持有配对码」的信任模型用足 |
| **配对失败原因分级**：错误码具体到「码输错 / 设备离线 / 已被配走」 | 当前失败文案只有「二维码不是有效的声盾配对码」+ 超时 message。应分级：① 码错（校验失败）② 对端离线（`notifyPeerOfPairing` 超时）③ 对端拒绝（重复配对/密钥不符，端点 `pair.request` 的 rc.ack `ok:false` 原因透传） |
| 过期/重置流程 | Matter 配对码有窗口期。本项目码永不过期是**刻意设计**（多控制器复扫），可保留，但应提供**「轮换配对码」按钮**（函数已存在，只差 UI），并在文案里说明轮换后旧码失效 |

### 2.3 AirDrop / 快速配对（远期）

- 思路：附近发现（BLE 广播 / NSD/mDNS 同局域网）→ 列出附近声盾设备 → 点击配对，替代二维码。
- 本项目落法：远期 P2。短期不做网络发现，但可在「尚未配对」文案中先给出「两台设备连同一 Wi-Fi」的前置提示，为将来 NSD 发现铺路。MQTT 依赖公网 broker，局域网直发现是自然的 v3 方向。

### 2.4 银行/政务 App 权限分级引导

| 行业做法 | 本项目落法 |
|---|---|
| 被拒 ≠ 结束：先弹 Dialog 解释用途 → 「去设置」跳 `AppSettings` → 返回后自动重查权限继续 | 当前是一条 SnackBar 就没了（pair_qr_screen.dart:213-216）。改为：`permanentlyDenied` → 弹窗说明 + `openAppSettings()`；普通拒绝 → 弹窗解释 + 再试；**并在两个弹窗里都放「改用手动输入配对码」按钮**，保证权限全拒也能完成配对 |
| 返回前台自动续流程 | `WidgetsBindingObserver` 的 `didChangeAppLifecycleState`：从设置回来 `Permission.camera.request()` 一次 |

### 2.5 企业 MDM 双端可视化确认

| 行业做法 | 本项目落法 |
|---|---|
| 两台设备都显示**对方名字**再点确认（如 macOS→iPhone「信任此设备」双向弹窗） | 现在 A 扫 B 后 A 立即落盘，B 端**无感知**直到收到 `pair.request`。对标改法：A 扫码 → A 显示「发现设备 B，确认配对？」→ B 收到 `pair.request` 弹「设备 A 请求配对」确认框 → B 确认后回执 → 双端各自显示对方名字。改动面较大（端点侧要加确认 UI），**至少先做到 P1 简化版：双端配对成功后各自常驻展示对方设备名（已配对列表已有，缺的是配对瞬间的对端可见性）** |

### 三个重点问题的直接回答

1. **手输兜底存在吗？** 存在但不在扫码页（remote_screen.dart:385），且要求手输 16 位 ID，几乎不可用——这是「扫不了码」用户被卡死的直接原因。**P0-3 必做**。
2. **相册识码值不值得做？** 值得。屏对屏扫码（手机扫手机屏幕）是本项目**唯一**的扫码场景，反光/条纹失败率高，相册识码正好兜住；且 mobile_scanner 自带 `analyzeImage`，改动面小（P1-5）。
3. **配对码过期/重复/上限文案**：当前全部缺失——码永不过期未说明、重复扫码静默覆盖、无上限未声明。集中到 P1-9 一次补齐。

## 4. 实施红线（来自既有测试与注释）

- 不得破坏 PQR-02：配对码必须持久，任何「每次进页换码」的实现都是回归。
- 解析器**单点复用** `PairQrProtocol.parseUri`，禁止再拷贝（pair_qr_screen.dart:96-102 的教训）。
- 手输路径与扫码路径必须共用 `notifyPeerOfPairing`，否则回执 payload 两份漂移（pair_qr_screen.dart:34-36 门禁）。
- 权限引导改造后，PQR-03（被拒不进扫描态）仍须通过。
