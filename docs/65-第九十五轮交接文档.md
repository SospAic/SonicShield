## 1. 本轮做了什么

### 1.1 R88 审计遗留 7 条缺陷全部修掉

R88 只读审查 `lib/remote/**` + `lib/services/**`（47 文件 / 20 005 行）留下 7 条
「只登记不修」的缺陷（`_pt/audit/r88_bugscan_remote_services.md`）。本轮全部修掉。

**P1-1 · `R88-AUD-01`「用户点了停，振动才刚刚开始」**

`VibrateSession.start()` 在真正下发首片之前有**三处平台往返**（`capabilities()` /
`environment()` / `battery()`）。若 `stopAll()` 落在这段窗口里：`_active` 还是空的
⇒ 停止请求被当成「当前没有进行中的振动」、原生 `cancel()` 先发完，随后 `start()`
恢复执行**照常下发首片** ⇒ **用户点了「停止」，振动才刚刚开始**。

- 修法：`VibrateSession` 加**停止代次闸门** `_stoppedGen`。所有"停止"入口
  （`stopAll` / `stopFor` / `dispose` / `recoverAfterRestart`）在**同步段**里自增；
  `start()` 入口同步取快照，最后一处 `await`（`battery()`）之后复核 ——
  不等即记 `skipped · 启动过程中收到停止请求，已取消下发` 并返回 false。
- 同源第二处：`_pump()` 在 `await battery()` 之后用**快照里的旧会话**续发/摘表
  ⇒ 被记成「振动完成」的会是**已接管的新会话**。修法：`identical` 身份复核。
- 回归锁：`R97-VS-01~03` 是**行为锁**（可卡住的 `battery()` 替身确定性地复现时序），
  不是源码锁。

**P1-2 · `R88-AUD-02`「关引擎不停止振动」+ `dispose()` 是死代码**

`VibrateSession.dispose()` 是 BUG-127 为"引擎关停"补的出口，但全仓**零调用点** ——
那次修复是空转的。本轮在 `service.on('stop')` 清理链里 `vibrate.stopAll()` 之后
**显式接上 `vibrate.dispose()`**。

**P1-3 · `R88-AUD-03`「守卫关了但麦克风还在采」**

`service.on('guard')` 是独立 async 监听器、**没有任何串行化**：用户快速「开 → 关」时，
开启那一支停在 `guard.start()` 的取流 `await` 里，关闭那一支完整跑完（此时 `_sub == null`
⇒ 实际是空操作），随后开启那一支恢复执行 ⇒ `guardEnabled=false` 而
`guard.isRunning=true`：麦克风继续采流、`onSoundEvent` 继续被调用。

- 修法两层：① 服务侧 `_starting` / `_stopRequestedWhileStarting` 旗，取流窗口内收到停止
  ⇒ **不置** `_running`、不挂监听、立刻释放刚拿到的流；② 引擎侧**命令代次** `guardGen`
  复核，不成立立刻 `guard.stop()` 并如实记审计。

**P1 同族 · `R88-AUD-07`「重开守卫时 UI 立刻判启动失败」**

`guardError` 到 `await guard.start()` **之后**才更新 ⇒ 窗口内的每次 `broadcast()` 都还带着
**上一轮的失败文案**。修法：在**第一条语句**就 `guardError = null`。

## 6. 本轮踩到 / 复用的教训

- 🔴 **「停止」必须能被「还没开始的启动」感知**。所有 `start()` 里跨 `await` 的窗口，
  都要问一句：如果这期间用户按了「停」，恢复执行后会发生什么？
  本项目已因此修过 4 处（PA-05 / RS-ND4 / AUD-01 / AUD-03），**判据是通用的**：
  **在 await 之后、动作之前，复核一个"同步段里置位的意图"（代次 / 旗子 / 身份）**。
- 🔴 **零调用点的"出口函数"是空转的修复**。`VibrateSession.dispose()` 为 BUG-127 而写，
  却没人调 ⇒ 修了等于没修。**写出口的同时必须接上调用点，并配一条断言调用点存在的锁。**
- 🔴 **`finally` 优于"在每个 catch 里各写一遍清理"**。`background_service_manager` 的
  `on Object` 分支恒不可达（没有 `completeError`），而正常路径反而没在这里摘表 ——
  三个出口写三遍，必有一遍是死的或漏的。
- 🔴 **`pumpAndSettle` / 固定轮数，遇到"不会自己停"的东西都必须换有界轮询**。
  本轮 3 处（PA-05 / RS-ND4 / SLB-24）全是同一族。
- 🔴 **整机满载下"数轮数"的等待会假红**。他项目（WSL2 + SD-WebUI + pytest）占满 CPU/内存时，
  Dart VM 会 `Out of memory`（门禁按 RC=3 报环境阻塞，不是回归）。
  **判据：先看 `tasklist` 与内存，再怀疑代码。**
