## 三、🔴 BUG-079：升级路径缺陷（本轮主要缺陷）

| 项 | 内容 |
|---|---|
| 现场发现 | 真包在模拟器上 logcat **每分钟**刷 `replan 失败：DatabaseException(no such column: quiet_exempt ... DELETE FROM occurrences ...)` |
| 根因 | v1.9 的 DB 迁移 v2→v3 只给 `tasks` 补了 `quiet_exempt`，但 `deletePendingQuietExempt()` 查询的是 `occurrences` 表 —— `onCreate` 有列、`_onUpgrade` 漏补 |
| 影响 | v1.9 之前老库升级的用户：**关闭夜间豁免主开关的 fail-safe 清除从未生效**（每次必抛），replan 整链失败 |
| 修复 | `_onUpgrade` 的 `if (oldV < 3)` 追加 `ALTER TABLE occurrences ADD COLUMN quiet_exempt INTEGER NOT NULL DEFAULT 0`（`lib/data/db/app_database.dart`） |
| 回归锁 | **MIG-06**（`test/app_database_migration_test.dart`）：复刻设备现场 v2 库 → 升级 → 断言列补上/旧行保留/默认 0/`deletePendingQuietExempt()` 真实可调用 |
| 红绿闭环 | 修复过程中 MIG-01/02 假库先暴露"少造 occurrences 表"（`no such table`）→ 修正假库为真实 v1 schema（v1.0 起 onCreate 就有 occurrences，git 考古证实）→ **MIG 5/5 全绿**（`_pt/bc6_mig.txt` MIG_RC=0，analyze No issues） |

**模式确认**：升级路径回归（BUG-078 FGS 类型位、BUG-079 DB 迁移列）宿主测试**永远抓不到**，
只有模拟器/真机现场才能暴露 —— 这正是设备层常规化的价值。

## 四、多模拟器：实测结论（诚实，不虚报"双机全绿"）

1. **双机并发跑 Gradle 集成套件不可行**（BC1）：两个 qemu + Gradle daemon（-Xmx4G）并发 ⇒
   构建挤到 2663.5s 未完成 ⇒ `timeout 2700` 打穿 ⇒ 连环 `RC=124`（非编译错误）。
2. BC2 期间两台 qemu 进程消失（死因无法确证；内存充足 47.8GB，负载疑凶）—— 如实留痕。
3. **可行形态 = 通路分工**（本轮闭环）：一台模拟器跑功能套件 + AOT；
   端点用**同机切换**（真包 + 配对 prefs 注入 + 公网 broker），宿主 `rc_probe` 打 9/9。
4. 流程抓漏 ×2：①作业脚本 `APK="$ROOT/..."` 引用未定义变量 ⇒ 空路径 ⇒ `install_app.sh`
   误判 missing 拒装 ⇒ probe 0/2（BC3）→ 改绝对路径（BC4）全链打通；
   ②`flutter drive` 结束默认卸载应用 ⇒ 端点基座消失 —— 设备编排铁律已写入 `docs/17 §83.4`。
