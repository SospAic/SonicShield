### 0.1 离线补发链路现状（Q3.C 的起点）

| 环节 | 位置 | 行为 |
|---|---|---|
| 入队 | 控制端 `sendTo` → `store.enqueue` | 端点不可达时命令落控制端 outbox |
| 补发 | `endpoint_service.dart:1998` `flushOutbox` | **只读 + 成功后删**（绝不用 drainOutbox）；坏条目丢弃并审计（`outbox.drop`） |
| 重放 | `endpoint_service.dart:2356` `prepareOutboxReplay` | 以 3650 天超宽窗解旧信封 → **重盖时间戳与 ID** 再编码（否则被 ±90s 时间窗/去重丢掉） |

| 传输 | `_connect`（`endpoint_service.dart:253`） | MQTT TLS 8883，**fail-closed**（不传 `onBadCertificate`），QoS1，`startClean()` |

**盲区（Q3.C 要解决的唯一问题）**：补发的全部触发点都在**控制端的 MQTT 连接**上。

命令在 outbox 里躺着，"端点上线后自动执行"依赖用户手动打开端点 App。

# 第一部分 · Q3.C 离线命令可达性（推送门铃）

## 设计总纲：推送只当门铃，命令仍走 MQTT

```
控制端 outbox ──(现有链路不变)──► MQTT cmd 主题
                                    ▲ 端点上线后照常订阅收取
手机厂商推送通道 ──"叮咚，有命令"──► 端点被拉起 ──► 前台服务 _connect() ──► 照常拉命令
```

**为什么门铃模型必须坚持**：
1. E2EE 信封由「配对码 + deviceId」派生密钥加密（docs/14），推送通道若携带密文，
   密钥就得交给厂商服务器侧可感知的路径，**破口**；
2. 厂商推送有大小限额（小米/华为通知消息体量 KB 级）且不可靠有序，命令走推送
   会复刻"离线补发"问题本身；
3. 门铃是幂等噪声——丢一条门铃只等于"晚一点上线"，下一条门铃/用户手动打开照样补齐。

| Broker 侧/服务端 | **需要一个发推送的出站口**：最小做法是控制端 App 直发（FCM HTTP v1 需要 OAuth 服务账号——见风险 R3） |

### 行为规格

1. **门铃 payload（唯一允许的形态）**：
   `{"v":1, "type":"doorbell", "deviceId":"<端点ID>", "seq":<单调递增>}`
   —— 不含命令内容、不含密钥、不含主题。端点收到后：比对 seq 去重 → 起前台服务 → `_connect()`。
   现有链路自然接手：订阅 `cmd` + 心跳冲刷 outbox（控制端侧心跳本来就在重试）。
2. **FCM 用 data message（非 notification message）**：App 被杀时 data 消息进
   `onBackgroundMessage`，不弹通知、不依赖用户点击；notification message 只能点通知启动，
   不满足"无人值守拉起"。
3. **优先级 high**：保证 Doze 下投递；端点被拉起后走既有前台服务保活（docs/05）。
4. **门铃不改变任何安全判定**：拉起后命令照走 `_handleRaw` 的解密、准入、审计全链路。

### 测试与验收判据（含变异证伪）

| # | 场景 | 判据 |
|---|---|---|
| A1 | 端点进程被杀（`adb shell am force-stop`）→ 控制端下发命令 → 门铃到达 | 端点前台服务启动、MQTT 连上（`rc.heartbeat` 出现）、outbox 命令被执行、审计留痕 |
| A2 | 门铃到达但 outbox 为空 | 端点上线后无任何命令执行、无残留状态（幂等噪声验证） |
| A3 | **变异证伪（安全锁）**：门铃 payload 塞入伪造 `{"cmd":"sound.play"}` | 端点**必须忽略**之：不执行、不报错；测试断言"门铃通道携带命令字段时不产生任何副作用"——防止后人把门铃升级成命令通道 |
| A4 | **变异证伪**：seq 重复的旧门铃 | 不重复拉起（去重生效） |
| A5 | Doze 深度休眠（充电静止 + 熄屏 >30min）后门铃 | 仍能拉起（high priority data message）；若失败记录为 R2 证据 |
| A6 | 门铃丢失（飞行模式开关模拟）→ 60s 内第二条命令再发门铃 | 第二条门铃补齐，命令最终执行（门铃可丢、命令不丢） |
| A7 | `rc_transport_lock_test` 回归 | TLS 8883 fail-closed 不被本次改动破坏 |

### 风险

- **R1 国内可达性（阶段 1 的根本局限）**：谷歌服务在国内 ROM/网络常不可用。
  阶段 1 只承诺"国际场景可达"，国内可达性靠阶段 2。验收 A1 在国内 ROM 上可能直接失败——
  **这不是缺陷，是阶段 2 的立项证据**，如实记录即可。
- **R2 电池白名单**：未加白名单的设备，high priority 也可能被国产 ROM 二次拦截。
  验收 A5 需在"已授权忽略电池优化"（docs/05 既有引导页）与未授权两种状态下各测一次并记录。
- **R3 发送方凭证**：控制端直发 FCM 需要 OAuth2 服务账号 token（HTTP v1 API）。
  两个选项：① 控制端内嵌服务账号（**密钥入库风险，不推荐**）；② 自建轻量中转
  （一个小 HTTP 服务持服务账号，控制端调它发门铃）。**阶段 1 默认选 ②**，
  该服务的部署属于"需要用户提供"的外部项（一台可达的 VPS/云函数即可）。
- **R4 FCM 频控**：门铃有 seq 去重 + 控制端节流（同端点 30s 内最多 1 条），防轰炸。

### 接入要点（各家差异巨大，逐家记录）

| 厂商 | 接入件 | 被杀进程可达的消息类型 | 关键坑 |

### 降级顺序（运行时判定，写进 `push_service.dart` 的唯一决策点）

```
设备 ROM 判定（Build.MANUFACTURER / hasSystemFeature）：
  华为/Honor ROM 且已注册 HMS token → 华为通道
  小米 ROM 且已注册 MiPush token    → 小米通道
  其他（含类原生/海外）              → FCM（阶段 1）
全部注册失败                        → 现状降级：无推送（门铃缺失 = 用户手动打开 App，命令仍不丢）
```

- token 注册发生在端点 App 运行期：`push_service.dart` 按上述顺序注册，把
  `{deviceId, channel, token}` 上报给门铃发送方（同 R3 的中转服务）。
- **发送方按 channel 路由**：中转服务持各家 AppSecret，按端点上报的 channel 调对应 API。

# 第二部分 · Q7.C 受控实时投屏

## 设计总纲：端点用户显式授权 + 全程可见指示 + 媒体走 DTLS

三不可裁剪红线（源自 docs/08 精神）：
1. **授权**：每次投屏由 MediaProjection 系统授权弹窗发起（Android 强制），App 内不得
   提供"免确认/自动续授"绕过；
2. **可见**：投屏期间端点有前台服务通知 + App 内醒目指示（"正在向 X 投屏"），任何
   时刻端点可一键停止；
3. **不破 E2EE 口径**：投屏媒体**不进入** MQTT rc 信封加密体系，走 WebRTC 自带
   DTLS-SRTP 端到端加密；信令仍走 MQTT E2EE。见第三部分 §3.2 的风险评估。

## 阶段 1 · 单帧截屏（B 方案，投屏的第一级）

### 设计

复用 MediaProjection 授权流（阶段 0），一次授权截一帧：
`VirtualDisplay → ImageReader(RGBA) → JPEG 压缩 → base64 → 现有 `rc.photo {photoB64}`
回传通道（`protocol.dart:223`，**该载体已声明无发射方，本次是它的第一个生产发射点**）。
媒体字节走 MQTT E2EE 信封（单帧体量小，与 ptt.voice 同模式），信令/回执全走现有链路。

|---|---|---|
| C1 | 控制端请求 → 端点同意 | 控制端 3s 内收到一帧，图像可辨识；审计留痕 `screen.cast` |
| C2 | 端点拒绝授权 | `rc.ack{ok:false}`，控制端 UI 明示"对方拒绝"，**不重试轰炸** |
| C3 | **变异证伪（隐私锁）**：未走授权弹窗、直接调用截屏桥 | 必须失败（Android 平台保证 + 代码层断言无 token 即抛）——这是"不可绕过授权"的机器锁 |
| C4 | **变异证伪**：截屏时刻端点前台服务通知不存在 | 测试判红（可见性红线：任何像素出屏前必须已有可见指示） |
| C5 | 单帧体量超限（超大分辨率） | 降采样/重压到 MQTT 单消息上限内，宁可糊不可失败 |
| C6 | 配对撤销（docs/08 §4 / RcRevokePlan）时投屏服务在跑 | 立即停（并入 `decideRevokeCleanup` 的 stop 项） |

### 风险

- **R8 隐私**：屏幕可能含密码/通知内容。缓解：系统授权弹窗本身已告知"将捕获屏幕内容"；
  文档明示；阶段 0 红线落位是前置条件。
- **R9 性能**：单帧一次性成本，可控；重点是 C5 的降采样兜底。

## 阶段 2 · H.264/WebRTC 实时流（复用 `call.*` 信令的可行性评估 + 实施）

### 可行性评估结论（本次预研结论，实施前需复核）

| 维度 | 结论 |
|---|---|
| 信令 | **可完整复用**：`call.invite/answer/candidate/end` 四件套已是通用 WebRTC 会话信令（docs/16），投屏只在其上增加一个会话类型区分。建议 `call.invite` 的 `video` 字段扩展为枚举或新增 `kind:'screen'`（不破坏旧字段语义，向后兼容） |

# 第三部分 · 与现有安全模型的衔接

## 3.1 推送：门铃模型下 E2EE 零破口

| 资产 | 现有通道 | 推送是否触碰 |
|---|---|---|
| 命令密文 | MQTT TLS 8883 + rc 信封 E2EE（配对码派生密钥，`RcCodec`） | **不触碰**——推送 payload 仅 `{deviceId, type:'doorbell', seq}` |
| 密钥材料 | 终端内存，永不出端 | 不触碰 |
| 配对/撤销/准入判定 | `_handleRaw` 全链路 | 不触碰——门铃只负责"让 `_connect()` 提前发生" |
| 审计 | `outbox.drop` / `pair.revoke` 等 | 新增门铃收发审计（到达/去重），可选 |

**攻击面新增项**（阶段 1 A3 锁定）：门铃通道被伪造充放量 → 端点反复被拉起（耗电攻击）。
缓解：seq 去重 + 拉起节流（同 token 5 分钟内最多一次无命令拉起）+ 厂商侧推送鉴权
（发送方持凭证）。文档明示这是**可用性攻击面**而非机密性攻击面。

## 3.2 投屏媒体不走 MQTT E2EE 会话：风险评估与替代

**风险表述**：rc 信封加密（`RcCodec`）覆盖的是 MQTT 上的命令/回执/单帧；
实时流走 WebRTC 后，媒体**脱离了配对码派生密钥的管辖**。直觉上"两套加密"像破口，
实际上不是：

| 维度 | rc 信封（MQTT） | WebRTC 媒体 |
|---|---|---|
| 密钥来源 | 配对码 + deviceId 派生 | DTLS 握手临时协商（SDP 里的指纹经 MQTT E2EE 信令传输） |
| 加密对象 | 信封明文 | RTP/SRTP 媒体流 |
| 端到端性 | 是 | **是**——DTLS 指纹经 E2EE 信令通道交换，中间人若篡改指纹即解密失败（fail-closed，与 `_connect` 不传 `onBadCertificate` 同一纪律） |
| broker 可见性 | 只见密文 | broker 只见密文信令，媒体 P2P 不经 broker |

**结论**：投屏媒体的机密性由「DTLS + 指纹经 E2EE 信令绑定」保证，等价强度、不同体系。
**替代方案被否决的理由**：把实时 H.264 流塞进 rc 信封逐包加密 = 自己实现 SRTP，
工程量与出错面远大于复用 libwebrtc 的 DTLS。

**保留的一条口径**：单帧截屏（阶段 1）**仍然走 rc 信封**（体量小、复用 `rc.photo`），
只有实时流（阶段 2 起）切 WebRTC——两阶段加密口径在文档与代码注释中都写明。
