# SonicShield 全量代码审查与能力提升方案

> **审查日期：** 2026-10-03  
> **项目版本：** v1.9.0-alpha  
> **审查方式：** 汇总 7 条首轮专项审查报告；随后另将 12 条独立补审并发提交，10 条返回可用报告、2 条未获可用输出；高优先级结论已对照源码核验。

## 1. 结论先行

项目已形成较扎实的功能和防回归底座：Dart/Flutter + SQLite，Android 原生前台服务/闹钟，MQTT over TLS 8883 + AES-GCM 端到端加密，WebRTC 通话；远程授权、夜间护栏、执行审计及“真实链路优先于源码文本锁”的测试理念均已有实现。历史报告记录第七十轮宿主门禁 **RC=0、功能层 2099、压测 24、可测面 99.21%（9552/9628）、全局 94.43%（9554/10118）**，设备层记录 **集成 7 文件 22 例、AOT 6 例、远程探针 9/9（CRUD 8/8）**。这些数字是仓库既有证据，不是本次重跑结果。

本次未发现可在静态审查中确认的 P0，但发现多个需要先处理的 P1：**关闭引擎后旧闹钟仍能唤醒服务、精确闹钟权限拒绝可能被误当作排布成功、随机计划重算会改变已生成时间且只追加不对账、操作失败却可能记成成功、联网重连/连接失败的状态不可见、iOS 后台能力与产品承诺不匹配、共享配对码模型存在已知身份伪造旁路**。它们分别影响任务正确性、可用性、授权可信度和跨平台发布。

**最可行方向不是推翻现有架构或换协议，而是先统一状态和结果语义，再补全平台调度能力边界、联网状态机与真实 E2E 门禁。** 用户已在 `docs/23` 裁决的 FCM+厂商推送（Q3.C）和“端点显式授权、全程可见”的受控投屏（Q7.C）应排在基础可靠性与权限闭环之后，不应先扩展隐蔽后台能力。

## 3. 迭代演进与当前结构判断

1. **安全与传输先收敛。** 第三十四轮记录将明文 MQTT 改为强制 TLS 8883，并保留证书 fail-closed；端到端 AES-GCM、配对、定位权限门控、回执与审计逐轮补齐。`docs/14` 说明 TLS 保护链路、E2E 保护载荷，两者不能相互替代。
2. **从功能测试走向真实链路测试。** 第四十三至四十七轮的项目记录多次发现“源码锁绿不代表业务路径执行过”，推动 WebRTC、指令组、远程服务、后台插件替身与反面样本测试。这是有价值的工程资产；但常规 CI/设备门禁还没有覆盖全部生产端到端路径。
3. **后台与升级路径反复遇到 OS/状态边界。** BUG-078（Android 15+/target 36 开机广播直接拉起 mediaPlayback FGS）通过延后闹钟方案修复并有三台 API 36 模拟器记录；BUG-079 暴露旧数据库升级缺列并在第七十轮补 v4 幂等迁移。说明本项目应继续以 OS/API 版本矩阵和旧数据迁移作为产品能力，而非发布前手工补测。
4. **最新一轮收口但仍有关键决策未变更。** 第七十轮记录新增配对码轮换 UI、数据库 v4 迁移、测试锁质量规则及 F-3 修复。`docs/14` 同时明确 `msg.from` 仍是发送方自报字段；现密钥模型不能单独撤销某个共享配对码持有者。这是已披露的模型级缺口，不应因“诚实登记”而视作风险已消失。
5. **现状判断：** 业务广度已高，最大的增益来自状态一致性、失效可见、跨端能力诚实表达、后台任务正确性；不是继续冲覆盖率（项目已在 `docs/17 §81.3` 规定稳态轮不再为覆盖率写测试）。

## 4. 发现总表与建议

### 4.1 P1：先处理正确性、安全边界与核心可用性

#### P1-01｜撤销配对不能抵抗伪造发送身份（已知模型缺口）

- **证据：** `lib/remote/endpoint_service.dart:2570-2588`；`docs/14` 配对/撤销段；`test/unpair_revoke_test.dart` 对诚实移除场景的锁定。
- **现状：** `msg.from` 在密文内由发送方自报；仍持共享配对码的一方可构造 `from` 为仍在表内的 ID。现 `decideRcAdmission` 以该 senderId 判断是否 paired。`docs/14` 已明确写出此旁路并注明需改密钥模型。
- **影响：** “删除设备”对恶意/泄露凭据情形不是可靠撤权。该项目涉及执行命令、录音、位置和通话信令，不能把列表删除等同于密码学撤销。
- **方案：** 下个协议版本采用每个控制端独立密钥/配对凭据，服务端身份绑定不可由载荷自报；支持单设备撤权、全局轮换、旧协议迁移和恢复流程。旧码轮换入口已有，但不替代独立身份。若短期不能迁移，界面和安全白皮书明确“撤销强度”边界，避免夸大承诺。
- **验证：** 对抗测试：已撤销控制端用共享码、伪造仍配对的 `from` 发命令，必须拒绝；旧码/旧 ID/重装端点/多控制端并存都纳入协议迁移测试。

#### P1-02｜合规须知点“不同意”后，仍能开启后台引擎

- **证据：** `lib/services/permission_flow.dart:20-62` 将拒绝写入 `compliance_accepted_v1=false`；`lib/features/dashboard/dashboard_screen.dart:141-159` 开启分支未调用 `isComplianceAccepted()`，继续设置 `shouldRun=true` 并 `mgr.start()`。
- **影响：** 用户明确不同意时仍可启动自动化；首次“合规门”不是有效准入闸。
- **方案：** 将同意状态置于引擎启动唯一准入层（UI 与服务边界都拒绝）；拒绝时开关保持关闭，提供重新阅读与接受入口，不覆盖或篡改历史日志。
- **验证：** 首次拒绝、重启后拒绝、从其他入口启动三种情境都断言服务启动次数为 0；接受后才允许启动。

#### P1-03｜关掉引擎不会撤销计划闹钟；Watchdog 仍无条件启动服务

- **证据：** `lib/services/background_engine.dart:1074-1092` stop 处理停止 Dart 守卫/播放器并 `stopSelf()`，没清理原生闹钟；`packages/native_bridge/android/.../AlarmWatchdogReceiver.kt:18-26` 收到闹钟后直接 `startForegroundService()`，没有检查持久化启用态；引擎启动会立即 `executeDue()`/`replan()`（`:1249-1275`）。
- **触发：** 用户关闭引擎时仍有旧 AlarmManager 项，之后旧闹钟响。
- **影响：** 用户以为自动化已关，系统却可能再次拉起前台服务并运行到期任务；是“停止”语义与后台行为不一致。
- **方案：** 同步 stop 流程清数据库与原生闹钟；Receiver 在拉起前再次验证启用代次/开关；闹钟 Intent 带 generation，旧代次永远 no-op。启动入口与回调双层校验，避免竞态。
- **验证：** 关闭、删除最后一个任务、改计划、快速停启后检查 `dumpsys alarm` 与执行日志；手工触发旧 generation Intent 必须不启动/不执行。另在 Android 13+ 用系统“活动应用/Task Manager → Stop”停止 FGS（不是 `am force-stop`），检查后续已排闹钟是否会重新启动服务；该用户停止入口也必须通过 generation/启用态拒绝复活。

#### P1-04｜精确闹钟被拒返回 `0`，应用没有识别为失败或降级

- **证据：** Android 原生 `NativeBridgePlugin.kt:212-218` 权限不足返回 `0`；`lib/services/background_engine.dart:660-677` 只区分 `null` 与抛错，不判断 `0`/部分排布数。`permission_flow.dart:70-75` 读取能力但拒绝分支无用户反馈。
- **影响：** UI 可继续显示运行中和计划数，但系统级定时唤醒未排布；服务被系统回收后，15 秒 Timer 不能承担进程复活职责。
- **方案：** 返回结构化 `AlarmScheduleResult(expected, scheduled, unsupported, denied, error)`；状态进入“降级/需授权”，在用户可操作的位置解释“进程仍在时可执行，但被系统回收后不保证准点”，恢复权限后重排。精确闹钟仅用于用户明确设置的时间敏感提醒，非必要后台维护交给 WorkManager。
- **验证：** API 31+、34+、36 权限允许/拒绝/撤销/恢复，断言排布数、页面状态、日志和任务实际结果一致。

#### P1-05｜随机计划续算以变化中的 `now` 重采样，只追加不同 occurrence

- **证据：** `lib/domain/scheduling/schedule_engine.dart:261-325` 每次用当前时间裁剪窗口后重新抽样；`lib/services/background_engine.dart:1249-1256` 低于阈值周期 `replan`；`OccurrenceRepository.commitAll` 使用 `ConflictAlgorithm.ignore`（`lib/data/repositories/occurrence_repository.dart:12-20`），不对账不同时间的新 ID。
- **影响：** 续算时刻变化使同一天的候选时间漂移，旧条目被保留、新条目追加；每次样本自身受 `timesPerDay/maxPerDay` 限制，但跨多次续算总数不一定受该限制。未在本次设备复现，属代码可推导的 P1 调度风险。
- **方案：** 用固定“任务 ID + 当地日期 + 计划版本”种子生成当天完整计划；将计划作为可重算投影：数据库事务中对同一任务未来 pending 做 replace/reconcile，保留 done/failed/skipped；同步撤销旧原生闹钟。跨时区/DST 明确使用的日历时区。
- **验证：** 同一天多次重算结果稳定；在计划中途改触发器时只取消/替换未来 pending；最终每天次数、最小间隔、免打扰均不超界。

#### P1-06｜播放任务编辑器未提供音源选择；新任务通常没有 `assetIds`

- **证据：** `lib/features/tasks/task_editor_screen.dart:792-842` 播放输入只编辑音量、时长、闹钟通道、循环等；保存路径（约 `:1510-1520`）新任务 `assetIds` 默认为空；`lib/services/background_engine.dart:373-383` 空列表无法选出音源并记 `无可用音源`。
- **影响：** 用户可保存并启用一个到点必然失败的“播放”任务，日志失败但任务 UI 可能仍像可执行。
- **方案：** 加入可搜索多选音源/“全库随机”模式，保存前验证；缺音源时禁用提交或明确显示不可执行状态。点名音源不存在必须 fail，不可随机替代。
- **验证：** 创建/编辑任务的音源往返与执行 E2E；空库、文件丢失、被删除音源都应给可理解的错误。

#### P1-07｜声音事件分支绕过概率门；部分动作失败仍被报告为成功

- **证据：** 定时 `executeDue` 有 `probabilityGateMissed`（`background_engine.dart:825-836`），但声音守卫 `runGuardPlan`（`:883-910`）未见该门；`playAndLog` 会记录失败但返回 `void`，`runSingle` 播放/TTS/录音/声景分支固定返回 `true`（`:496-505` 等）；`runGuardPlan` 忽略返回值并无条件 commit `OccurrenceStatus.done`（`:900-908`）。
- **影响：** 设置的概率条件对声音触发无效；用户看到失败日志，但计划/远程 ack/Occurrence 可能称成功。这是强烈破坏可用性和可诊断性的语义不一致。
- **方案：** 统一 `ExecutionOutcome{success|failed|skipped, reason, sideEffects}` 从动作 helper 到调用方/ack/occurrence；所有触发入口（定时、声音、远程立即执行）共用同一条件/概率裁决管线。
- **验证：** 对播放缺文件、TTS 超时、录音失败、振动不支持、概率 0/100，断言日志、任务状态、回执三者一致。

#### P1-08｜iOS 不能承诺当前 Android 式计划后台准点执行

- **证据：** `packages/native_bridge/pubspec.yaml:17-23` 只声明 Android；`NativeBridge.exactAlarmSupported()` 在无平台通道时回落；`background_service_manager.dart:77-80` iOS `onBackground` 是空操作，插件只提供机会性 `BGAppRefresh`；`notification_service.dart` 只有即时通知，没有计划级本地日历通知。`Info.plist:32-45` 却注释了 BGProcessing 与计划通知兜底方案。
- **影响：** iOS 后台挂起/用户强制退出后，不能依靠 Dart Timer 或 `earliestBeginDate` 保证每条计划执行；播放/录音/振动/远程 MQTT 也不是一个统一的 iOS 后台能力。
- **方案：** 先定义平台能力矩阵。可由 OS 独立送达的提醒用 `UNCalendarNotificationTrigger`；系统择机维护用 BGTask；需要持续 Dart/麦克风/远程控制的任务明确要求 App 活跃或受支持的音频会话，不承诺系统不允许的常驻。清理或实现 `Info.plist` 中未落地的 processing 声明。
- **验证：** macOS 构建后在真实 iPhone 测前台、后台空闲、锁屏、强制退出、通知拒绝、Background App Refresh 关闭；检查“提醒通知”和“实际动作执行”是否区分。

#### P1-09｜iOS 交付链未闭环：工程 15.0 与插件最低 15.5 冲突

- **证据：** `ios/Runner.xcodeproj/project.pbxproj:367`（多组配置为 15.0）；Pub 缓存 `mobile_scanner 6.0.11` podspec 声明 15.5。项目无本次 Xcode/Archive 结果，`RunnerTests` 仍是空模板；当前 CI 无 macOS/iOS job。另 Apple 官方 [Upcoming Requirements](https://developer.apple.com/news/upcoming-requirements/) 规定自 **2026-04-28** 起提交 App Store Connect 的应用须由 Xcode 26+ 与 iOS 26 SDK 构建。
- **影响：** 当前不能声称 iOS 可构建、可签名或可发布；部署目标冲突可能阻断插件依赖/Archive，而旧 Xcode/SDK 会直接不满足当前 App Store 提交要求。静态配置冲突已确认，实际失败未实测。
- **方案：** macOS 上统一最低部署版本，选定 CocoaPods/SPM 集成方式，生成并构建插件注册；CI 显式使用 Xcode 26+/iOS 26 SDK，完成签名 Archive/IPA 导出。Release 产物与依赖锁都要归档。
- **验证：** iOS Simulator Debug/Profile/Release + 真机 Archive 安装；如保留 iOS 15.0 则逐依赖证明兼容；上传前打印并保存 Xcode/SDK 版本。

#### P1-10｜连接失败没有稳定状态流；远程界面可能永久“连接中”或显示已开启

- **证据：** `endpoint_service.dart:496-505` MQTT connect 异常只安排重连并 return；不产出连接失败状态；`remote_screen.dart:133-154` `_toggleEnabled` 没有 `try/finally`，任一异步异常会让 `_connecting` 不复位。另 `main.dart:46-60` 虽对远程装配异常降级启动，但 `runApp()` 前仍等待 `_wireRemoteEndpoint()`（`:120-124`）结束；若连接调用挂起，首帧也可能被延迟。应分别测“连接失败”和“连接挂起”路径。
- **影响：** broker/TLS/认证错误时用户无法辨认“功能开启但不可达”；抛错路径当前页无法重试。
- **方案：** 明确 `stopped/connecting/online/retrying/degraded/error` 状态机、错误码、lastConnected 与 nextRetry；关闭时取消重连；UI 将“已启用”与“在线”分开并给出可执行诊断。
- **验证：** 假 broker、错误证书、鉴权拒绝、网络切换、连接挂起、停止时重连回调并发，验证状态转移与重试入口。

#### P1-11｜心跳在一次断连后被取消，自动重连不恢复周期维护

- **证据：** `endpoint_service.dart:529-542` heartbeat 检测未连接时 `t.cancel()`；自动重连回调只补订阅与 flush（`:467-470`），没有重建 heartbeat；Timer 只在完整 `_connect()` 成功尾部建立。
- **影响：** 重连后在线状态广播、周期补订阅和补发可能永久停摆，直到远程模块被手动重启。
- **方案：** 把 heartbeat/订阅/outbox pump 作为明确的连接代次 lifecycle，与连接事件绑定；不要用一个周期定时器兼任重连/补发多个职责。
- **验证：** 断开一次 → 自动重连 → 观察后续多轮 heartbeat/flush 都仍发生；再 stop/start 并发不重复创建 timer/client。

#### P1-12｜重连使用固定 10 秒且 Timer 不可取消，可能旧回调重建/覆盖客户端

- **证据：** `endpoint_service.dart:576-581` Timer 未保存引用；stop 不能取消该定时器；同时 MQTT 库 `autoReconnect=true`（`:462`），有两套重连路径。
- **影响：** 固定间隔无抖动，公共 broker 故障时可能同步重试；快速 stop/start 时旧 Timer 可能触发过期 `_connect()`，造成重复客户端/泄漏。
- **方案：** 选择唯一重连 owner；有上限指数退避 + jitter + retry budget；持有取消句柄与 generation token；恢复网络后立即做一次受控探测。
- **验证：** 使用假时钟检验退避边界、上限、抖动范围、取消、重复 start 与旧 generation no-op。

#### P1-13｜配对确认迟到时，盐可能没有落盘，配对呈现“成功但没回音”

- **证据：** `endpoint_service.dart:2310-2339` 默认等待确认 8 秒；只在 `_awaitAck` 返回 ack 后处理其 `kdfsalt`，且只在 `ok == true` 时保存（`:2325-2336`）。超时后 `_awaitAck` 在 `finally` 取消事件订阅（`:2346-2366`）；若该 ack 随后到达，本次请求不会再消费它，可能留下双方盐版本不一致。
- **影响：** 弱网下新配对的回执/通话信令不可解，UI 容易让用户重复配对，形成半连接。
- **方案：** 把 pair-request/ack 设计为有 requestId 的幂等状态机；迟到 ack 仍可完成绑定，重复 hello 可重放当前盐，不把“8 秒 UI 超时”当作密钥状态终止。
- **验证：** 延迟 ack 超过 8 秒、重复 pair、端点重装后重配、乱序回执，断言两端最终盐版本一致且旧盐失败可见。

#### P1-14｜Release 在缺少正式 keystore 时回退 Debug 签名

- **证据：** `android/app/build.gradle.kts:52-84` 注释与代码明示缺正式 keystore 时 Release 用 debug 签名。
- **影响：** 开发构建方便，但误把该产物发布会造成应用身份/升级签名不匹配。当前未检查现有 APK 签名，故这是发布流程风险，不是已证实已发布错误包。
- **方案：** 仅 CI/正式 Release fail-closed；本地 debug-only build 可继续回退；CI 注入密钥或使用签名 secret，发布后 `apksigner verify --print-certs` 对照已知证书指纹。
- **验证：** 无发布密钥的 release job 必须失败；有密钥时安装旧版后覆盖升级。

#### P1-15｜离线 outbox 重放没有业务期限，旧命令会被重新签成“刚发出”

- **证据：** `lib/remote/remote_store.dart:465-474` 保存 `at` 但不按年龄过期；`lib/remote/endpoint_service.dart:2370-2413` 补发时遍历 outbox；`prepareOutboxReplay`（`endpoint_service.dart:2771-2793`）特意忽略旧时间窗并生成新 `ts` 与新 `id`。
- **触发：** 端点离线很久，重连后命令才补发。
- **影响：** 原命令本身的时间新鲜度已被抹掉，诸如音量/振动/状态修改等过去有效但如今过时的动作仍可能执行。现有“换新 ID/时间戳”解决的是密码包过窗，不等于业务授权仍有效。
- **方案：** 入队时写 `expiresAt` 与命令新鲜度类别；重放前先检查 TTL/当前任务与授权版本。过期条目移入失败审计，不改签、不执行。实时通话/PTT/ICE/stop 等时效消息禁止离线补发；需要长期执行的业务命令须明确用户语义并保证幂等。
- **验证：** 假时钟覆盖 TTL 前后、设备重配对/撤权后、重复重放；过期命令不得发布且用户可见原因，未过期安全命令仍有序补发。

#### P1-16｜远程 `task.toggle` 只改 enabled 位、不触发立即重排

- **证据：** `lib/remote/endpoint_service.dart:874-881` 远程 toggle 调 `tasks.setEnabled()` 后记日志/回执，没有触发 `replan`；`lib/data/repositories/task_repository.dart:70-78` 只更新任务行。对照本地 `lib/features/tasks/task_list_screen.dart:132-138` 会请求 `replan()`。后台仅在全局 pending 数低于阈值时周期重排（`background_engine.dart:1249-1255`）。
- **触发：** 远程启用一条没有 pending occurrence 的有限日期/固定一次任务，而其它任务让全局 pending 数维持在续算阈值以上。
- **影响：** 目标任务可能没有原生闹钟；若唯一计划时刻在下一次重排前已过，任务静默漏执行。远程回执只确认启用标志，易让控制端误以为排程已经生效。
- **方案：** 远程启用/停用与本地入口调用同一任务变更用例：事务写状态、使过期 pending 失效、请求引擎立即重排并返回排程结果；在新的结果产生前回执区分“已启用”和“已排程”。
- **验证：** 用其它任务填满 pending 阈值，远程启用近期有限任务；立即断言 occurrence + 原生闹钟出现。停用、删任务与重复 toggle 也需验证对账。

#### P1-17｜并发收到同一 QoS 1 命令时，ID 去重有 check-then-act 窗口

- **证据：** `lib/remote/endpoint_service.dart:506-522` 的 `updates.listen` 中 `async` 回调会 await 入站处理；`_handleRaw` 在多次异步 key derive/decode 后才于 `:634-650` 检查并记入 `seenIds`；`lib/remote/protocol.dart:326-337` 的解密只读 seen set，不预占 ID。异步 stream 回调并不因前一回调返回 Future 就天然串行。
- **触发：** 同一条有相同非空 ID 的 QoS 1 命令在第一次解密/处理尚未完成时重投或并发到达。
- **影响：** 两次都可能在 `_rememberSeen` 前通过查重，重复执行播放、立即运行或指令组等副作用；当前“ID 去重”可能不能覆盖并发重复投递。
- **方案：** 在解密确认后、授权/限流/副作用前原子登记唯一 ID（单 isolate 同步段或 keyed serial queue），并将状态标成 in-flight；失败语义明确决定是否允许有限重试，完成态保留去重窗口。
- **验证：** 让第一次解密/dispatch 可控挂起，在挂起期间注入相同 envelope 两次，断言副作用计数严格为 1、重复请求获得稳定 ack。

29. **日期范围遍历用固定 24 小时步长，DST 回拨时可能重复前一日并漏掉末日。** `lib/domain/models/trigger.dart:63-69` 的 `DateRange.days()` 以 `d.add(Duration(days: 1))` 遍历当地日期；`schedule_engine.dart:225-233,261-325` 的 daily/random-window/random-interval 触发都复用它。在有夏令时的设备本地时区跨回拨日时，午夜到下一午夜可能是 25 小时，固定加 24 小时仍落在前一日 23:00；循环会重复该日期并可能跳过日期范围末日。建议按 calendar date 构造下一天午夜（保留 zone/local semantics），用 America/New_York 2026-11-01 至 11-02 日期范围验证每日任务产出两天各一次。
30. **远程协助 accept 回执没有核对 `for` 是否属于当前 hello。** `assist_host.dart:467-478` 回执会写 `payload.for=hello.id`；`assist_join.dart:344-371` 收到 `assist.accept` 后没有核对当前 join 发出的 hello ID，就直接置 `phase=active`。重复接入/旧 QoS 回执迟到时，旧 accept 可能被当成新接入成功，造成界面权限/TTL/session 状态与当前尝试不一致（端点仍有权限校验，未观察到越权执行）。保存本轮 hello ID 集合，仅接受匹配回执；回归测试注入旧 `for` 的合法密文时维持 opening。
31. **远程通话关键按钮缺无障碍名称。** `call_incoming_overlay.dart:241-255` 接听/拒绝按钮和 `call_screen.dart:289-296` 主叫挂断按钮只有图标，无 `tooltip`/语义标签；TalkBack/VoiceOver 无法可靠区分接听、拒接、挂断。补 `tooltip` 或 `Semantics(label: ...)`，用 widget semantics 测试检查来电振铃/呼叫中各按钮名称。
32. **iOS 把配对秘密、配对码和 broker/TURN 凭据放在 SharedPreferences。** `remote_store.dart:39-47,182-195,234-256,271-331` 保存相关字段；该插件在 iOS 映射到 NSUserDefaults，而不是 Keychain。OWASP MASTG 的 iOS 备份测试建议核对设备备份中的敏感数据（[MASTG-TEST-0058](https://mas.owasp.org/MASTG/tests/ios/MASVS-STORAGE/MASTG-TEST-0058/)）。影响取决于 iOS 备份/设备数据可取得情况；当前未证实发生泄露。把秘密迁入 Keychain（按业务选择 ThisDeviceOnly 可访问等级），备份/恢复只保留非敏感设置；升级迁移后清除旧 pref，做备份检查与凭据轮换测试。
33. **重新授予 Android 精确闹钟权限没有对应的自动重排 receiver。** Manifest 的 BootReceiver 只监听 `BOOT_COMPLETED`、`QUICKBOOT_POWERON`、`MY_PACKAGE_REPLACED`（`android/app/src/main/AndroidManifest.xml:159-167`）；本仓未发现处理 `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED` 的 receiver。用户撤销精确闹钟授权后系统取消未来闹钟，再重新授权时闹钟可能保持空集直到用户重开引擎/重排。按平台 action 增 receiver，在授权恢复后只重排不重复启动不需要的 FGS；API 31+ 真机验证撤销→重授→无需手动重开即恢复排布。

### 4.3 P2：测试与交付体系的“假绿”风险

- **CI 未执行覆盖率 ratchet。** 本地 `scripts/gates.sh` 第四步调用 `coverage_report --gate/--min-covered`；`.github/workflows/ci.yml:26-33` 只跑 `flutter test --coverage` 并上传产物。PR 可能全绿但覆盖分数下降。把同一 coverage gate 加到 CI，并锁命令一致性。
- **设备测试有通过即跳过的路径。** `integration_test/guard_toggle_device_test.dart:57-62` 找不到 `Switch` 时直接 `return`，用例会绿。改成失败断言；搜索测试中其他“没找到就 return / continue”且仍报告通过的路径。
- **后台引擎生产链未被 device E2E 完整驱动。** 现有设备用例直接测 schedule materialize、通道振动或页面可达，不等同于“启动后台 isolate→DB 到期→执行动作→Occurrence/日志提交”的闭环。覆盖率的设备豁免需有对应实际链路测试，否则明确为未验证。
- **普通配对遥控的真实 MQTT E2E 主要是一次性探针，不是常规门禁。** fake MQTT 测试能驱动 `_handleRaw`，但不覆盖 TLS、证书错误、broker ACL、实际 QoS/reconnect；assist E2E 与普通遥控不是同一链路。将受控 TLS broker 测试纳入 CI/设备分层，不依赖公网服务稳定性。
- **探针回执关联不足。** `tool/rc_probe.dart` 有回执缺少 `for` 时只按类型匹配的可能；迟到/无关同类 ack 可能满足等待。为所有指令添加 requestId/correlationId；反例测试确认旧 ack 不会使新命令通过。
- **PowerShell/Bash/CI 设备套件不一致。** `gates.sh`、`gates.ps1` 和 workflow 的设备测试清单不同，AOT 设备名有硬编码差异；维护一份 suite manifest，未执行必须标 BLOCKED 而非绿。
- **真机和 iOS 未闭环。** 手持设备不在线时不得把模拟器结论推广至 MIUI/HyperOS、真实麦克风/扬声器、NAT/TURN、耗电或 iOS；保留“已跑 / 未跑 / 环境阻塞”三态证据。

## 5. 性能与可用性评估

### 5.1 性能风险排序（无本轮性能实测）

1. **计划重算与任务列表查询**：随机任务重算会增加多余 occurrence；任务卡片当前逐任务查询。先修确定性、批量查询和正确索引，再做 profile。
2. **长时间媒体资源**：声景每轨独立 AudioPlayer；录音哈希全文件进内存；播放器/麦克风/通话共享系统音频资源，需要统一生命周期。
3. **UI 可响应性**：音源库重建时重复全量 list/decode；大型备份 JSON 解析路径应设输入上限并 profile，确认超过帧预算后再移到 isolate。
4. **常驻后台耗电**：每 15 秒 tick 与 60 秒心跳在产品上有成本；`AlarmManager.setExactAndAllowWhileIdle` 只留给用户真正要求精准的时钟，不用作泛化“保活”。当前无本次 `batterystats`/MetricKit 实测，不能编造耗电改善幅度。
5. **网络恢复效率**：固定 10 秒重连、双重 autoReconnect/Timer 与未取消 callback 有连接风暴/泄漏风险；退避应有 jitter、deadline 和用户状态。

**可复核的历史性能基线（非本轮）：**`docs/12 §31.4`（第十七轮续四，2026-09-20）记录 AOT 测量：同类探针下 `exec_logs` 5000 条逐条写入 **6568 ms**，任务 500 条逐条 **1287 ms**、批量 **129 ms**（预算分别 21075/2108/500 ms）。同节说明早期与后续绝对耗时可相差约 4×，因此这些值只作为当时相同工作量下的设备观察，不当作当前机器的绝对性能目标。本轮无新的 Profile 性能测量。

### 5.2 建议的测量门禁

先在低配 Android 真机、主流 Android 真机及 iPhone 设基线，再设阈值；至少采集：冷启动到可交互 p50/p95、任务列表 50/500/5000 条加载 p50/p95、计划物化规模/耗时、远程命令端到端 ack p50/p95、弱网恢复时间、通话建连成功率、后台误触/漏触次数、连续 24 小时 CPU/电量/内存增长。所有结论标设备型号、OS、网络、构建模式、样本数；使用 Flutter Profile/DevTools 或系统 Profiler，而不是 Debug 模式/模拟器猜生产性能。

## 6. 最可行的实施路线（按依赖排序）

### 阶段 A｜一致性止血（先做，避免继续堆功能）

1. 统一 `ExecutionOutcome`，修正概率门所有入口、动作失败到 ack/Occurrence 的传播。
2. 修 `task` 更新语义（避免 REPLACE 级联删历史）、任务编辑器固定日期/跨午夜/候选权重、播放音源选择。
3. 计划使用固定版本/日期输入生成；新增 pending 对账事务；设置变化清除受影响计划及闹钟；引擎 stop 对称清理并由 Receiver 再校验启用代次。
4. 合规同意准入、精确闹钟失败状态、Android 麦克风 FGS、RemoteScreen `finally`/错误状态，补行为用例。

### 阶段 B｜联网端到端可靠性（本项目最应优先投入）

建立单一网络生命周期协调器：`stopped → connecting → online → retrying → degraded/failed`。连接变化用 generation token；唯一重连 owner；指数退避 + Full Jitter + retry budget；stop 可取消全部 timer/订阅/客户端。日志脱敏，不打印配对码、密码、密文载荷或证据内容。

每个命令建立 `requestId`、`createdAt`、`expiresAt`、`targetId`、`state`：`queued → published → received → executed/failed/expired`。区分“写入本地 outbox”“MQTT publish accepted”“broker QoS ack”“对端执行完成”。命令去重键持久化；重试只针对可安全重放操作。Live call/PTT/ICE/stop 等时效信令禁止离线过期后补发。outbox 限额必须返回被拒绝/丢弃结果并留审计。

配对协议升级为端点独立凭据、单设备撤权和盐版本；pairing ack 使用 requestId，迟到/重复确认幂等，双端显示配对完成。真实普通遥控 E2E 覆盖正常配对、撤权伪造、无效 TLS 证书、双端点回执定向、权限拒绝/允许、离线 outbox、过期信令及网络恢复。

### 阶段 C｜平台能力矩阵与音频会话

Android：清楚区分精确闹钟、可延后维护工作、FGS 与通知权限；旧报警在停止/任务变更后失效；前台通知要可感知且有停止/状态。只在 Android 系统允许且产品理由成立时启动相应 FGS 类型。

iOS：承认 `BGAppRefresh` 是系统择机调度，不做精确时间承诺；可用本地日历通知承接纯提醒，真正需要动作的计划必须有明确的 App 前后台可用性声明。若实现 iOS VoIP 推送，只用于合法来电并落实 PushKit + CallKit；普通遥控不能伪装成 VoIP。统一 AVAudioSession 与 Android AudioFocus 管理，监听 interruption/route changes，录音、播放、WebRTC 建立优先级和恢复规则。

### 阶段 D｜测试/发布门禁

- PR：analyze + 行为单测 + 覆盖率 ratchet 同时执行；测试需失败可见，不允许“找不到控件就 return”。
- 集成：后台生产 engine + SQLite 真闭环；Android API 24、31、33、34、35/36；macOS iOS build、模拟器与真机三段分开标证据。
- 远程：CI 启动 ephemeral TLS MQTT broker 或专用测试 broker；将 fake 行为测试、TLS/ACL 合约测试、真设备/网络探针分层。
- 音频/WebRTC：两台不同网络真机含 TURN relay，压力/断网/权限/中断测试；真扬声器/麦克风人工设备取证标注机器型号，不以“测试完成”代替物理结果。
- Release：Android release 无正式签名密钥则 fail；iOS Archive/签名/最低部署版本检查必过；保留 symbols、mapping、协议版本和迁移回滚说明。

## 7. 可扩展功能与具体方案

以下在现有架构和既有产品裁决上推进，不扩大到隐蔽监控/未经授权设备控制：

1. **端点健康面板（近期）**：每设备显示启用态、在线态、最后心跳、broker/证书错误、最后命令执行状态、outbox 队列长度/最早过期；所有指标本地可见并支持脱敏导出。它直接解决“开启但其实不在线”。
2. **可靠离线推送门铃（按 `docs/23` Q3.C）**：系统推送只携带不敏感唤醒/同步标识，App 醒来后再通过受信 TLS MQTT 拉取有期限、有授权的命令；Android FCM + 已裁决厂商通道分阶段实现，iOS 走普通 APNs 通知而非滥用 PushKit；服务端保存幂等操作 ID 与过期时间。Phase 0 先验证国内服务可达、密钥/推送 token 生命周期与隐私声明。
3. **端点用户可控投屏（按 `docs/23` Q7.C / `docs/24`）**：必须端点侧明确授权，每次会话显示常驻指示/倒计时/立即停止；建立会话级 scope、拒绝与撤销、截图/录屏审计策略；先做一次性授权探针与平台政策评估，之后再实时投屏。禁止静默后台截屏或伪装辅助功能控制。
4. **端点能力协商与协议版本化**：配对时交换能力清单（平台版本、支持动作、最高协议版本、可用通道）；UI 对未支持功能置灰/解释，协议兼容通过 schema version 与向后兼容测试管理；避免 iOS 上“能发送但永远失败”的命令。
5. **证据包与数据生命周期**：本地生成可校验的日志索引/哈希摘要、关联触发和音频文件；用户明确导出，导出包默认脱敏设备 ID/地址，不上传音频；设置中提供文件大小、导出与逐项删除，明确备份、保留与清理规则。
6. **局域网优先（远期、可选）**：`docs/25` 已提出同 Wi-Fi 前置提示与后续 NSD/BLE 发现；仅做设备发现/扫码辅助，不替换现有端到端认证，不广播配对秘密，发现后仍需显式配对确认。先做隐私威胁建模与局域网断开/切换测试。

## 8. 行业理念、先进做法与可迁移案例

- **Flutter 官方 Offline-first 指引**强调本地数据源、Repository、网络同步分离；本项目已有 SQLite 本地库和离线 outbox，应进一步把“本地队列”为事实源、状态可观察、重放幂等，而不是每个 UI 各自猜连接是否成功。参考：[Flutter Offline-first](https://docs.flutter.dev/app-architecture/design-patterns/offline-first)、[Android Offline-first architecture](https://developer.android.com/topic/architecture/data-layer/offline-first)。
- **AWS Builders’ Library**讲 timeout、retry、backoff+jitter 和幂等的组合：重试不等于可靠，未知是否执行成功时必须用稳定 request/idempotency key。可直接用于 MQTT 命令、outbox 与配对 ack；避免固定 10 秒重试。参考：[Timeouts, retries, and backoff with jitter](https://aws.amazon.com/cn/builders-library/timeouts-retries-and-backoff-with-jitter/)、[Retry with backoff pattern](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/retry-backoff.html)。
- **Android 平台当前后台规则**：Android 14 对大多数新安装应用默认不预授精确闹钟权限；FGS 类型、启动时机和用户通知都受平台限制。使用 `AlarmManager` 只服务精准用户提醒，不把 WorkManager/FGS 当无条件保活。参考：[Exact alarm permission](https://developer.android.com/about/versions/14/changes/schedule-exact-alarms)、[FGS background-start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)、[foreground service types](https://developer.android.com/develop/background-work/services/fgs/service-types)。
- **Apple 后台规则**：`earliestBeginDate` 是“不早于”，不是“保证这时执行”；纯通知可以使用本地日历触发；VoIP PushKit 必须用于真实通话并与 CallKit 配合。参考：[BGTask earliestBeginDate](https://developer.apple.com/documentation/backgroundtasks/bgtaskrequest/earliestbegindate)、[Local notification scheduling](https://developer.apple.com/documentation/usernotifications/scheduling-a-notification-locally-from-your-app)、[PushKit/CallKit](https://developer.apple.com/documentation/pushkit/responding-to-voip-notifications-from-pushkit)。
- **音频可用性**：Android 用 Audio Focus 协调多个应用；Apple 要处理 AVAudioSession interruption 与 route change。当前多轨声景、取证录音、WebRTC 同应用并存，适合做统一“音频会话协调器”，而不是各 service 单独设置播放器属性。参考：[Android audio focus](https://developer.android.com/media/optimize/audio-focus)、[Apple audio interruptions](https://developer.apple.com/documentation/avfaudio/handling-audio-interruptions)。
- **移动安全基线**：OWASP MASVS 将 Storage、Crypto、Network 等分域；用于把共享配对秘密、日志、录音、备份和设备撤权按可验证要求列入威胁模型。参考：[OWASP MASVS](https://mas.owasp.org/MASVS/)。
- **行业案例来自项目既有调研，不是本次重新评测**：`docs/15` 对照 Home Assistant/MQTT、KDE Connect、Zello、Tasker/MacroDroid、Sleep as Android；适合借用的是本地自动化、设备显式配对、消息保序/过期、平台边界内运行，不是照搬其商业策略。`docs/23/24` 已记录的 Q3.C 和 Q7.C 是用户裁决，不需另作假设。
- **性能优化遵循测量优先**：Flutter 官方建议在 profile mode 观察帧时间和列表构建；使用真实设备的 integration performance trace，不对 debug/emulator 数字做结论。参考：[Flutter rendering performance](https://docs.flutter.dev/perf/rendering-performance.md)、[measure performance with integration tests](https://docs.flutter.dev/cookbook/testing/integration/profiling)。
